# S16 — isolated identity security spike

**This is not product code.** It is not imported by the dashboard, not built by
`frontend/`, not deployed, and not a dependency of anything that ships. It is a
separate npm package on purpose: `better-auth` never enters
`frontend/package.json`, so it cannot reach a bundle or a Vercel build.

Its one job is to make gate **G3 — accept or change the Auth candidate** —
decidable on evidence about the mechanism alone, before identity is entangled
with the product. The evidence and the recommendation live in
`docs/platform-ops/g3-auth-candidate-go-no-go.json`; the session record is
`docs/implementation-handoffs/N-S16.md`.

The candidate under test is **self-hosted Better Auth 1.6.25**, the initial
`IdentityProvider` adapter accepted at G0 on 2026-07-31.

## What runs where

| suite | command | touches |
|---|---|---|
| clean room | `npm test` | a local Docker `postgres:17-alpine` container, created and destroyed per run |
| live mapping | `npm run test:neon` | the Neon project, **read-only**, plus the same container for the candidate's own tables |

Both fail loudly rather than skipping. A green identity suite that reached no
database would be worse than a red one.

### Clean room

`src/cleanRoom.ts` starts a container and applies the **actual immutable
baseline files**, unmodified, through the same principals
`postgres/tests/portable_identity_roles_rls_cleanroom.sh` uses. The tables,
roles, grants and RLS policies the spike is measured against are byte-for-byte
the ones a tenant gets. It needs the Docker daemon and the `postgres:17-alpine`
image already present locally; it refuses an implicit network pull.

A normal run removes its container. A run interrupted mid-setup can leave one
behind; they are labelled, so:

```bash
docker rm -f $(docker ps -aq --filter label=s16-identity-spike)
```

The candidate's own tables go in a dedicated `identity_spike` schema owned by a
dedicated `identity_store` login role with **no grant on `public`** — and
`app_runtime` gets no grant on `identity_spike`. `tests/storeIsolation.test.ts`
measures both directions.

### Live Neon

```bash
set -a && . ~/.config/neon-s11-datastore.env && set +a
npm run test:neon
```

Read-only. It uses the three identity fixtures the baseline already ships
(`provider = 'fixture'`, subjects `subject-one` / `-two` / `-three`) and tells
the candidate to mint accounts whose ids are exactly those subject strings, so
the mapping is proven against the live project without writing a row to it. The
resolution runs through the **product's own driver and `identity.resolveSelf`
operation** — the spike supplies the subject, the product supplies the mapping.

## Layout

```
src/cleanRoom.ts       ephemeral container + the real baseline
src/spikeAuth.ts       the candidate's configuration, and only that
src/canonicalActor.ts  subject → canonical users.id, two resolvers
src/handler.ts         (Request) => Response, the serverless shape
src/harness.ts         node:http → Web Request, a stand-in for the runtime
src/cookieJar.ts       RFC 6265 storage/sending rules — not a browser
sql/candidate_identity_resolver.sql     a PROPOSAL for S17. Applied nowhere permanent.
sql/better_auth_generated_schema.sql    the candidate's own DDL, regenerated by a test
```

## Two things that will bite whoever reads this next

1. **The candidate disables its own CSRF defence when `NODE_ENV=test`.**
   `skipOriginCheck` resolves to `disableOriginCheck ?? (isTest() ? true :
   false)`, and skipping the origin check also skips the CSRF check. Vitest sets
   `NODE_ENV=test`. Every world here sets `enforceOriginChecks: true` for that
   reason; `tests/csrf.test.ts` also builds one with it off, to show the same
   hostile-origin request returning 200.
2. **A password reset does not revoke existing sessions by default.**
   `revokeSessionsOnPasswordReset` is only consulted when set. Both behaviours
   are measured in `tests/inviteResetDisable.test.ts`.

## What this spike deliberately does not do

No page, no route, no `DataContext`, no `AuthContext`, no existing handler, no
change to `frontend/api/` — the serverless-function count is still 12, asserted.
Nothing is created on any provider: no Auth tenant, no project, no domain, no
deployment, no Auth user, and no schema change to the tenant baseline. The
running dashboard still signs in through Supabase Auth exactly as before.
