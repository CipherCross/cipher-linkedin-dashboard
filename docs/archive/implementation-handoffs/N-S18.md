## The dependency S18 was supposed to have, and half did not

The spec gives `S18` the dependencies `S17, S13`. S17 is done and applied. S13

## What was built

### `VITE_AUTH_PATH` — the browser's path flag

`frontend/src/lib/authPath.ts`. Copies `deploymentAiPath`'s shape exactly: only
the string `identity` enables the new path, so unset, empty, `true`, `1`, `neon`
and every typo resolve to `supabase`. That direction is the safe one — a build
that fumbles the flag keeps the authenticator that works instead of losing
sign-in altogether. `VITE_`-prefixed because the browser reads it, and safe to
expose: it names a sign-in surface and carries no credential.

### `identityAuth.ts` — everything the path decides

The default test run is `environment: 'node'` over `tests/**/*.test.ts`: no DOM,
no `.tsx`, nothing renders. So every rule lives in a plain module with an
injectable `fetch`, and `AuthContext.tsx` holds only React state. A rule that
exists only inside a component is a rule this repo cannot test.

What it covers: `session.current`, `session.signIn`, `session.signOut`,
`password.requestReset`, `team.roster`, and the three admin ops. Load-bearing
decisions, each proven:

- **Four outcomes for `session.current`, not two.** 401 anonymous; **403 signed
  in but no longer an active member**, kept distinct because a deactivated
  person holds a *valid* session and bouncing them to sign-in would succeed and
  change nothing; 200 active; and **unavailable** — a 500 or a network failure
  is a deployment fault, not a sign-out, and rendering it as one throws away a
  working session.
- **The payload is validated, not cast.** A 200 missing `actor.role`, or
  carrying a role that is neither `member` nor `admin`, resolves to
  *unavailable*. A cast would let `undefined` flow into `role === 'admin'`.
- **`credentials: 'same-origin'` on every call**, and `Origin` set on none. It
  is a forbidden header the browser stamps itself, which is exactly what makes
  the server's C1 check worth having.
- **Admin actions are keyed on the canonical uuid.** `team_roster()` returns two
  identifiers per row that name different things — `id` is
  `team_members.id` (bigint), `userId` is `users.id` (uuid) — and the three SQL
  functions take the uuid while the Supabase path keys on the bigint. Crossing
  them type-checks and is silent, so nothing in the module passes a
  `RosterMember.id` to an admin call.
- **An unreadable roster row is dropped, not repaired.** Half a directory is a
  visible gap; a row with an invented key is an admin action aimed at nobody.

### `AuthContext.tsx` — two providers, one value

`AuthProvider` reads the flag once per mount and renders `IdentityAuthProvider`
or `SupabaseAuthProvider`. Everything below the context sees one
`AuthContextValue` and cannot tell which answered — which is why `user` widened
from Supabase's `User` to a neutral `{id, email}`, and why `authPath` is on the
value for the two places that legitimately need to know.

The Supabase provider's logic is unchanged, moved verbatim. What differs on the
identity path, and is not smoothed over:

- **`isAdmin` comes from the session, never from `member`.** The roster supplies
  a display name; the resolver supplies authority. A stale or unreadable roster
  therefore costs a name in the sidebar and cannot widen anyone's access.
- **A roster failure does not escalate.** Status stays `ready`, the error is
  surfaced beside it.
- **`unavailable` is a new `AuthStatus`** with its own screen and a retry, and
  on a *revalidation* an already-ready session stays ready — a blip must not
  evict a working session.
- **Hydrations carry a generation counter.** Two ordinary things make a stale
  answer possible: the heartbeat and the visibility handler overlapping, and —
  the one that matters — a sign-out landing while a revalidation issued *before*
  the cookie was cleared is still in flight. That request returns 200 and would
  otherwise re-ready a UI the person has just left. `signOut` bumps the counter
  and every state write checks that its own run is still current.
- **`setting_password` is unreachable** and `setPassword` throws a stated
  message. A Supabase invite link returns to the SPA with `token_hash`; the
  identity path has no such callback and no email delivery, so there is no
  recovery session to set a password against. Silently resolving would look like
  it had worked.

### Route gates

`AdminOnly` in `App.tsx` and the nine `isAdmin` call sites needed no change:
they key on the context value, which on the identity path is now the resolver's
`role` from `session.current`. That is the whole gate — the database is the
authority, and every admin endpoint re-checks `is_app_admin()` regardless.

### `authFetch`

Branches on the flag. Supabase: read the session, attach a bearer, raise the 401
locally rather than spend a round trip. Identity: attach nothing,
`credentials: 'same-origin'`, and **do not pre-empt** — the server distinguishes
401 from 403 and a guess made in the browser could only collapse them.

### The Team page

Split into `IdentityTeam` and `SupabaseTeam` rather than one page with a
different transport, because the two models genuinely differ and pretending
otherwise would misreport what an admin is looking at:

| | Supabase | Identity |
|---|---|---|
| roster source | `DataContext` → `team_members` | `team.roster` → `public.team_roster()` |
| assignment-only teammates | exist (`auth_user_id` nullable), and the invite form can link one | **cannot** — `team_members.user_id uuid NOT NULL` in the portable baseline; every member is a login |
| what an admin may change | name, role, active in one `/api/pipeline` call | role and active, as the two separate admin functions they are; **no rename op exists**, so no name field is offered |
| action key | `team_members.id` | `users.id` uuid |

Three further things it renders honestly rather than hiding: the invite toast
says the teammate *cannot sign in yet* (the account is created with a random
passphrase nobody — including whoever ran it — ever sees, and there is no
delivery); a `setActive` that disabled someone but could not revoke their live
session is reported as the partial success it is; and `hasMore` on the 200-row
roster read is stated instead of showing a truncated directory as the whole
team.

Role is saved before activation, deliberately: disabling revokes sessions, so an
admin editing their own row would otherwise revoke themselves before the role
change was made, leaving the second call to fail with the first committed. The
roster is reloaded even on failure, because one of the two calls may have landed.

## What was NOT done

1. **No handler or page was driven in a browser.** `npm run build` is the only
   typecheck and nothing renders in the test run, so the two providers' *React*
   wiring — effect ordering, the heartbeat, the sign-out transition — is covered
   by construction and review, not by measurement. Everything either provider
   *decides* is in `identityAuth.ts` and is measured; what is not is the shell
   around it. Driving it live would need `VITE_AUTH_PATH=identity` against a
   deployment with the three identity variables set, which is C5 and still open.
   The generation guard above is in that uncovered half: it is the kind of race
   only a rendered test could observe, and this repo cannot render one.
2. **The transitional bearer path stays.** `acceptLegacyBearer` in
   `identity.ts`, `activity-daily.ts` and `neonWrites.ts` is untouched, and must
   be: while any deployment runs `VITE_AUTH_PATH` unset — all of them do — the
   Supabase JWT is how the browser authenticates to the API. `N-S17.md`'s item 4
   is a **cutover** action, not an S18 one.
3. **`DataContext` still reads Supabase.** Unchanged, and the reason the flag
   exists. See above.
4. **No password-change surface on the identity path.** `password.change` is
   exposed by the endpoint and is not called from the browser. It needs the
   *current* password, so it does not solve the invited-teammate problem (SMTP
   does), and adding UI for it was outside this slice.

## Known limits

- **`VITE_AUTH_PATH=identity` is not deployable today**, and not because of a
  defect here: with reads still on Supabase, a person who signs in through the
  identity path holds no Supabase session and the dashboard has no data. The
  flag is built so the slice can be reviewed and tested now and enabled at
  cutover, exactly as `NEON_AI_PATH_DEFAULT` is.
- **SMTP is an external gate**, as the spec's slice row says. Until it exists,
  an invited teammate on the identity path cannot reach their account: the
  account is created with a passphrase nobody knows and the reset link is not
  delivered. The UI states this in both places rather than implying an email is
  on its way.
- `password.requestReset` sends a same-origin `redirectTo`. An off-origin one is
  refused 403 `INVALID_REDIRECT_URL` (F14), so it is built from
  `window.location.origin` and never from form input.
- The identity path's `user.email` is `null`: `session.current` returns no email
  and the roster is unreadable to a 403 caller, so the "access isn't active"
  screen omits the address rather than showing a stale one.
- `frontend/tsconfig.tsbuildinfo` is a tracked build artifact and moves with any
  build. It is committed here as previous sessions have committed it.
- **The bootstrap passphrase is still live.** The smoke used
  `~/.config/neon-s17-first-admin.env`. S17's limit 11 stands: it should be
  replaced through `password.change` and the file deleted.
- No `supabase db push`, no `deploy.sh`, no ledger step applied, and no
  credential, connection string or provider identifier entered the repository.
  The push and the deploy **were** performed, at the owner's explicit
  instruction, and are recorded above rather than left implicit.
