# N-S19 — the object storage provider, built to the edge of the owner's gate

S19 owns `ObjectStorageProvider`, signed operations and tenant key isolation.
Its acceptance list in the spec is six words — allow, deny, missing, expiry,
type, size — plus one constraint: production bytes are not copied. The bucket,
the token and the credential file are all owner gates this session may not open,
so the slice is built up to exactly that line and stops there deliberately.

## The design calls

### 1. The SigV4 signer is written here, not taken from `@aws-sdk/*`

The obvious alternative is `@aws-sdk/client-s3` plus `@aws-sdk/s3-request-presigner`.
Rejected, on a reason specific to this slice rather than a general preference
for writing things twice:

**The SDK would not have bought verification.** S19 may not create a bucket, a
token or a credential file, so no adapter written this session can be pointed at
a real endpoint either way. What *is* checkable offline is whether the bytes we
sign match the algorithm — and that is checkable precisely because SigV4 is a
published, deterministic function with a published worked example.
`tests/objectStorageSigv4.test.ts` reproduces AWS's own documented presigned-GET
signature `aeeed9bbccd4d02ee5c0109b86d86835f995330da4c265957d157751f604d404`
from its own example credentials, and asserts the published canonical request
line for line. An SDK call with fake credentials would have produced a URL no
test in this repository could grade.

Two supporting reasons, neither sufficient alone: R2 and S3 take the *same*
signature, so one signer serves the selected provider and the fallback G0
retained; and this runs in a serverless function whose cold start is on the
request path for a lead photo.

**The trade, stated plainly:** a hand-written signer is a thing that can be
wrong. What makes it acceptable is that it is wrong *loudly* — a canonicalization
mistake changes all 64 hex characters — and that five of the twenty-nine
mutations below attack exactly that surface and all five redden.

The credentials in the test files are `AKIAIOSFODNN7EXAMPLE` and its published
partner. They are AWS's own public documentation values and grant nothing.

### 2. `get` and `put` are signable; `head` and `delete` are not

R2 can presign all four, so this is a product decision rather than a provider
limit. The test applied was *who has to perform the request*: the browser
fetches image bytes and uploads replacements directly, and proxying those
through a function would spend execution time and memory for no security gain.
Nothing in a browser needs to stat or destroy an object.

Signing a DELETE would mint a durable, unrevocable capability to destroy a
tenant's objects and hand it to the least trusted party in the system, in
exchange for nothing the server cannot do itself. So the port exposes
`statObject` and `deleteObject` as server-performed methods.

The adapter still authenticates those with a presigned URL — 30 seconds of life,
minted and consumed inside one private method, never returned, logged or
serialized. That keeps exactly one signing path in the codebase rather than
adding header-based signing, which differs in the payload hash and the header
set and would double the surface the known-answer test covers only half of. The
policy's concern is who *holds* a capability, not which HTTP mechanism carried it.

### 3. The upload size limit works by signing `content-length`, not by checking it

This is the non-obvious mechanism in the slice, and the reason `presignPut`
demands an exact byte count instead of treating one as optional.

A presigned PUT URL constrains only what its signature covers. A size checked in
application code before the URL is minted is a number the client supplied and
can now ignore — the resulting URL accepts a body of any length. There is no
`X-Amz-Max-Length` query parameter; the `content-length-range` condition belongs
to the browser-POST form policy, a different upload mechanism.

So `content-length` is signed as a required header with an exact value, and the
upload must arrive carrying exactly that many bytes or the signature does not
verify. That converts "at most N bytes" into "exactly the M bytes you declared,
and M ≤ N was checked here" — strictly stronger. `content-type` is signed for the
same reason, against a specific attack: an object stored under an image key but
served as `text/html` is a same-origin script.

`image/svg+xml` is deliberately absent from the allowlist and must stay absent.
SVG is a script container and an avatar is the one place a stored script would
render against every team member's session.

### 4. Expiry is bounded at both ends, and neither bound clamps

The maximum is the obvious half. The **minimum** is not a security limit but a
correctness one: a URL that expires in two seconds is indistinguishable in
production from a permissions bug — images fail intermittently, on slow
connections first, and the failure looks like anything but a TTL. R2's own floor
is one second, which is not a floor worth inheriting.

Neither bound clamps. Silently shortening a caller's 24-hour request to 15
minutes produces URLs that expire long before the caller believes, which is the
same intermittent failure arrived at by being helpful.

### 5. Tenant isolation is enforced twice, by mechanisms that fail differently

G0 specifies a private bucket per tenant, so the bucket boundary is already one
mechanism. `keys.ts` is a second, and the argument for paying for both is that
neither covers the other's failure mode:

- The **bucket** boundary fails if a token is minted too broadly. An
  account-scoped R2 token instead of a bucket-scoped one is one mis-click in a
  dashboard, and nothing in the application can detect it.
- The **key prefix** fails if `keys.ts` is wrong, which a test can detect.

The grammar is an allowlist, not a blocklist. `src/lib/leadPhotos.ts` carries
the blocklist version of this idea for the Supabase path — reject `..`, reject
`://` — which was correct for a display helper over service-written values and
is the wrong shape for a boundary, because a blocklist must anticipate its
attacker. Percent-encoded traversal, homoglyph separators, embedded NULs and
trailing spaces are refused here without any of them having been thought of;
the nineteen-row deny table documents the property rather than creating it.

`assertKeyBelongsToTenant` parses and compares the tenant *segment* rather than
comparing a prefix, because one tenant id can be a prefix of another —
`'t/acme-evil/…'` passes the spelling someone reaches for first. Its refusal
also names neither the requested tenant's neighbour nor the key's owner, so a
denial is not a way to enumerate which tenants exist.

### 6. Configuration is `OBJECT_STORAGE_*`, never `R2_*`

Both R2 and the retained S3 fallback take the same four inputs. Naming the
variables after the selected vendor would mean a provider swap edits every
deployment environment as well as one adapter file — exactly the coupling
`ObjectStorageProvider` exists to prevent. The vendor's name appears in
`r2Provider.ts` and nowhere else.

The neutral half also declares its own default region rather than importing
R2's constant. A neutral module importing from an adapter inverts the dependency
the port is for; this was written the wrong way round first and corrected before
commit.

### 7. The fake plays the store, not just the provider

A fake that only returned URL strings could assert that a URL was produced and
nothing about what it permits — and what it permits is the entire subject of
S19. `FakeObjectStorageProvider.deliver()` keeps the terms of every URL it
issues and enforces them when one is presented: method, expiry, exact key, and
every signed header. That makes all six acceptance properties testable as
*behaviour* in the default `npm test`.

It is emphatically not a re-implementation of R2 and computes no signature. The
division is the one `identity/fakeProvider.ts` already draws: this suite proves
the product honours the contract; the candidate's own behaviour is proved
elsewhere, or recorded as unproven.

### 8. `statObject` answers `null`; `deleteObject` answers nothing

"Absent" is an ordinary answer on this path — a lead whose photo sync has not
run is not an error — so a missing object is `null` and an unreachable provider
throws. The two must stay distinguishable: a reconciliation pass that read an
outage as "absent" would conclude the bucket had been emptied. Mutation V3
covers exactly that collapse.

`deleteObject` returns `void`, which is a deliberate refusal to lie. S3 and R2
both answer `204` whether or not the object existed, so a provider cannot report
which happened without a preceding `statObject`, and the pair would not be
atomic anyway.

### 9. What is deliberately absent

No `listObjects`, no manifest, no checksum reconciliation — the spec gives those
to `S20`, and an unused surface now would probably be the wrong shape for its
first real caller. No agent-artifact bucket: G0 places it in a separately scoped
bucket with its own credential and the spec gives it to `S23`; its keys are not
tenant-prefixed and must not borrow this grammar by accident. `runtime.ts`
exists with no caller so that S20 starts from a wired entry point rather than
re-deciding how configuration reaches an adapter.

### The findings: the first pass had four silent mutations, and two were real defects

`N-UI-TESTS.md` closed with the lesson that a suite can be green and empty, and
that only the mutation pass says which. That happened again here, four times,
and two of the four were defects in this slice's own code rather than gaps in
its tests.

**S6 — two computations of `SignedHeaders` that could disagree.** `presignUrl`
computed the header list twice: once via a private `signedHeadersOf` for the
canonical request's query parameter, and once via the list returned by
`buildCanonicalRequest` for the URL it handed back. Unsorting one left the other
sorted, so the URL would advertise one header order while the signature covered
another — a request that fails only at the store, and no test noticed. The query
parameter object was built twice for the same reason and had the same exposure.

Fixed by collapsing both to one source: a single `sortedHeaderNames` feeds the
canonical request and the query parameter, and the query object is built once
and used for both. **The defect is now unrepresentable rather than tested for** —
two computations that must agree are a defect waiting for the day they stop
agreeing; one computation cannot disagree with itself.

**K4/K5 — an unreachable guard that was masking a real one.** `parseTenantObjectKey`
ended with a round-trip check: rebuild the key from its parsed parts and demand
an exact match. Deleting it reddened nothing, because every component is already
validated by the rules the builder applies and `join` is deterministic — a
doubled separator or trailing slash is refused as an empty *segment* long
before. Worse, deleting the object-class check reddened nothing *either*,
because the round-trip called the builder, which re-checked the class.

The guard is removed rather than kept and documented. A guard that cannot fire
is a guard nobody can maintain: the next person to loosen the segment grammar
would have no way to discover that the safety net they were relying on had never
been load-bearing. With it gone, K5 reddens and the class check is the thing
enforcing the class.

**S2 — a sort that was a no-op on every tested input.** Removing `.sort()` from
the canonical query builder changed nothing, because every parameter `presignUrl`
adds happens to be inserted in alphabetical order already. A caller passing a
`response-content-disposition` override would have been the first to find out.
Fixed by adding a test with deliberately out-of-order parameters.

**A harness note rather than a finding:** the first K6 anchor matched twice —
the builder and the parser carry similar length checks — and the harness
reported `anchor-error` instead of silently mutating both. A mutation script
that does not verify its anchor is unique produces confident, meaningless
numbers.

## Known limits

1. **Nothing here has spoken to R2, so "R2 accepts these URLs" is unproven.**
   The signature bytes are graded against AWS's published vector and the
   adapter's response handling against an injected `fetch`, but the end-to-end
   claim needs a bucket. This is the single largest limit of the slice and it is
   an owner gate, not an oversight.
2. **G0's review trigger 5 asks S19/S20 to prove five things.** This slice
   closes **URL expiry** and the half of **private-bucket isolation** that lives
   in code. **Lifecycle/versioning configuration, checksum reconciliation and
   copy time** are all bucket-level or data-level and remain entirely S20's,
   because each requires a real bucket to exist.
3. **There is no caller.** `runtime.ts` is wired and unused; S20 owns the lead
   photo API and UI that will call it. Until then the layer is dead code that
   type-checks and tests.
4. **`tenantId` has no source yet.** It is a parameter with a validated grammar,
   but nothing in the canonical schema carries a tenant id — multi-tenancy is
   `S21`+. Every caller today would have to supply a constant, and choosing that
   constant is a decision this slice does not take.
5. **Signing `content-length` requires the exact byte count up front.** A
   browser must read the file's size before requesting a URL, and a streaming or
   chunked upload cannot use this mechanism at all. That is the cost of design
   call 3 and it is the right trade for avatars; it would be the wrong one for
   large-file uploads, which would need the POST form policy instead.
6. **The fake is not R2.** It proves the product honours the contract, not that
   the provider does. Anything depending on R2's own behaviour — its exact
   status codes, its header canonicalization quirks, its clock skew tolerance —
   is unproven here by construction.
7. **The object-class allowlist has one entry.** `lead-photos` is the only class,
   which makes the allowlist's *shape* the tested property rather than its
   contents. A second class must be added together with its policy in
   `OBJECT_CLASS_POLICIES`, or it inherits nothing and fails closed.
8. **Everything the migration's own limits say still holds.** This slice added a
   new provider boundary and moved nothing else. `NEON_READS_DEFAULT` is still
   not flippable for the three reasons `N-BROWSER-RUN.md` § "Exact starting
   point" item 2 lists, and `N-UI-TESTS.md` item 4 still describes the next
   database decision as a whole-cutover one rather than a slice.
