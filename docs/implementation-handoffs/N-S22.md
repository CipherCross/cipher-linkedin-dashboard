# N-S22 — the agent's half: a second transport, a key that survives a retry, and a parity check that refuses

S22's row in the spec is `agent.py dual Supabase/ingest endpoint и rollout flags`,
graded on `py_compile`, extraction parity and a gateway dry-run/replay, with the
old transport preserved. All four are implemented. None of them is proved against
a live gateway, because there is no live gateway to prove them against — the
endpoint S21 built answers 503 in every environment until an owner sets two
variables and runs one cluster-scope artifact. That line is stated once here and
not blurred anywhere below.

This slice is the mirror image of S21. S21 built a write surface nothing called;
S22 builds the caller and still nothing connects them. What S22 changes is that
the gap is now one configuration step wide instead of one implementation wide.

## The owner gate, stated plainly

Six things stand between this branch and a real notebook writing a real batch.
S22 did none of them, and none of them is a code change:

1. `000_machine_ingest_role_bootstrap.sql` run on the **cluster** — `app_machine`
   is `NOLOGIN` until it is, so `NEON_MACHINE_DATABASE_URL` cannot be formed.
2. `NEON_MACHINE_DATABASE_URL` set on Vercel.
3. `APP_TENANT_ID` set on Vercel, equal to `OBJECT_STORAGE_TENANT_ID` if that is
   set. Absent either variable the endpoint answers 503.
4. A Vercel deploy carrying S21's endpoint, which is on `main` but not deployed.
5. A credential minted through `admin.agentCredentialIssue`. There is no UI —
   N-S21 known limit 2 — so this is an API call by hand, and the plaintext token
   exists in exactly one HTTP response.
6. `deploy.sh` to publish agent 1.13.0, then per notebook: `ingest_url` and
   `ingest_mode: shadow` from the Health page, and `ingest_token` pasted into that
   notebook's local `config.yaml`. The token is the one part that cannot be done
   remotely, by design.

Until all six, this branch is a transport with nowhere to go. That is the same
shape N-S20 had with the R2 bucket, and it is said the same way rather than
implied.

## The design calls

### 1. Three modes, and deliberately no fourth

`off` builds nothing and sends nothing. `shadow` delivers and treats every
failure as noise. `dual` delivers and hands a failure to the run warnings, so the
run reads `partial` on the Health page.

There is no mode that stops writing to Supabase. It would have been three lines,
and it would have been an untested way to take the fleet down: making the new
store authoritative is a decision about the whole dashboard — the SPA still reads
Supabase, `NEON_READS_DEFAULT` is still not flippable — not a flag on one
notebook. A mode that existed here would eventually be set by somebody who
believed the flag was the cutover.

The split between `shadow` and `dual` is the escalation lever and is worth the
second mode. `shadow` says "this is being proved, do not page me". `dual` says
"this is expected to work, tell me when it stops". Same delivery, different
consequence, and the difference is exactly the thing a rollout needs to change.

### 2. The idempotency key is a digest of the batch's own content

`sync.<UTC date>.<32 hex of sha256(payload without the key)>`.

The key is a function of **what is being sent** and of nothing else, and that one
choice is the whole retry property:

* A retry — the same extraction delivered again after a failure, by this process
  or by the next cron run — hashes the same bytes and presents the same key. If
  the first attempt committed, the gateway answers it as a replay and writes
  nothing; if it rolled back it left no trace at all (S21 design call 9), so the
  retry is an ordinary first attempt.
* A genuinely new sync has moved milestones, new leads or new messages in it, so
  it hashes differently and gets its own key.

Two alternatives were rejected, and both fail on the same axis. A **random key
per run** makes every retry a fresh batch, which is precisely what the gateway's
ledger exists to prevent. A **time-bucketed key** ("this hour") makes two
different payloads share a key, which the gateway correctly refuses with a 409
that only a human can clear.

Content-addressing has a property neither has: the 409 branch is **unreachable
from an honest agent**, short of a digest collision (known limit 6). Same key
implies same content implies same endpoint digest, so "this key is recorded
against different data" is not something this code can produce. That branch still
exists on the endpoint, for a buggy or hostile caller.

The reverse direction is harmless and worth stating so nobody chases it: two
payloads the endpoint *normalizes* to the same thing — a truncated overlong
string, two spellings of one instant — have different agent keys and the same
endpoint digest, which is two batch rows recording the same content, not a
conflict.

The date component is not part of the identity — it makes the key legible in a
log, and it gives an otherwise-unchanged notebook one fresh batch a day rather
than an unbroken run of replays. Its cost is one line in the limits below.

**The two digests need not agree.** The endpoint computes its own digest and
compares it against its own stored one, never against this one. So there is no
cross-language canonicalization contract to maintain — the agent's digest only
has to be a stable function of its payload, which sorted keys and fixed
separators give.

### 3. Extraction parity is structural first and checked second

The obvious shape — one extraction feeding both transports, then compared — is
what this does, and the structural half matters more than the check.

`cmd_sync` reads LH2 once. The Supabase upserts and the ingest payload are handed
the **same in-memory lists**, including the same *deduped* messages and events:
`dedupe_messages` and `dedupe_events` were hoisted into locals so both transports
send the same objects rather than two independent dedupes of the same inputs. Two
dedupes would be two places for the tie-breaking rule to live, and the parity
check would then be comparing a list against itself computed twice.

What remains for the check to prove is that the **projection** into the contract,
and the **chunking** of it, are lossless. `verify_ingest_parity` re-derives, from
the chunks, the row sets the Supabase push just sent, and compares counts, key
sets and per-row values: milestones and identity on leads, three counters on
steps, bodies on messages, `occurred_at` on events, name and status on campaigns.
It also checks the caps and the key uniqueness, because a chunk the endpoint
would refuse is a parity failure of the same kind.

The tests check this **by mutation**, not only by agreement: a dropped lead, a
dropped message, a dropped campaign, a changed milestone, a changed counter and a
dropped start year each produce a problem. A checker that only ever reports "ok"
is indistinguishable from one that reports nothing, and that is the lesson the UI
test harness recorded.

Applying that standard to the checker itself removed two of its assertions.
"Every chunk carries the same campaigns" and "…the same instance id" were written
and then deleted: `_ingest_chunk` builds each chunk with `dict(payload)`, so the
campaign list is one shared object and the instance id one shared string, and
both assertions compared a thing with itself. No mutation could have made either
fail. A check that cannot fail reads as coverage without being any, and the
comment in its place says so rather than leaving the next reader to rediscover it.

### 4. A parity problem refuses the delivery

Not a warning. A number known to disagree with the authoritative store must not
be written to a second one — wrong in two places is worse than missing in one,
because the second copy is what somebody will eventually reconcile against.

### 5. The credential is local-only by subtraction, not by comment

`ingest_url` and `ingest_mode` are in `REMOTE_CONFIG_KEYS`, because the rollout is
"turn one notebook to shadow, watch it, then the rest" and that must not need an
SSH session. `ingest_token` is not, and is treated the way `notify_secret` is.

The mechanism is a **subtraction**, not a comment:
`LOCAL_ONLY_CONFIG_KEYS` is removed from the allowlist inside
`apply_remote_config`. The failure it prevents is a future session adding the
token to `REMOTE_CONFIG_KEYS` "so it can be rotated from the Health page" — with
the subtraction in place, that edit changes nothing, and a test asserts exactly
that by adding the key to the allowlist and watching the local value survive.

The dashboard's half of the same rule was **missing**, and S22 closed it. The
config writer in `frontend/api/pipeline.ts` already stripped `notify_secret` from
an incoming blob; it did not strip `ingest_token`. A stored token would have been
inert — the agent refuses to read it back — but it would have been a machine
credential at rest in a row every admin can read and the AI SQL guard can select,
put there by somebody who believed it was being delivered. A cross-language test
now reads that denylist out of the TypeScript and fails if either key leaves it.

The marginal capability this leaves is worth naming rather than hiding: whoever
can write `instances.config` is an admin, and an admin can already issue and
revoke credentials directly. So an admin redirecting `ingest_url` at a host of
their choosing gains nothing they did not already have — but the payload, and the
bearer token in its header, would go there. That is the same exposure
`notify_url` + `notify_secret` has had since S-reply-notify, and it is a property
of remote-overridable URLs generally, not of this key.

### 6. Every chunk carries the full campaign list

A notebook with four thousand leads and three times as many messages does not fit
in one request, and the endpoint's own header comment says as much. Chunks are
bounded by row count first and serialized size second, because two thousand leads
are small and two thousand two-kilobyte message bodies are not. The byte split is
a halving recursion, so a single oversized row cannot loop it — it stops at one
row, which is always sendable.

`campaigns` is never sliced. `campaign_steps` join their campaign and leads
reference one, so a chunk that arrived without its campaigns would be silently
short rows rather than loudly wrong — and "silently short" is exactly the failure
mode this whole chain has been designed against. A campaign list is a handful of
rows; carrying it five times costs nothing.

Each chunk is keyed by **its own** content, so an unchanged chunk inside a changed
run is a free replay, and a failed chunk is retried alone.

An **empty** extraction still produces one batch. A quiet notebook must not look
like a dead one, and the instance row and the sync-run row are written by a batch.

### 7. The dry run does not touch the gateway, and says so

It prints the batches a real sync would deliver — their real keys, their row
counts, their sizes — the credential id, the endpoint, and the parity verdict. It
sends nothing.

That is not a shortcut. **The gateway has no non-writing POST.** Any request that
could answer "is this key a replay?" would *be* the first attempt if the answer
were no. So the honest form is to show the keys and say plainly that the replay
question is the gateway's to answer, which the output does in as many words. The
keys shown are the real ones, so the line a real run prints lines up with the
preview key for key:

```
ingest 1/5: accepted  2001 rows  key sync.20260807.6258bef5…  written 2001
ingest 1/5: replay    2001 rows  key sync.20260807.6258bef5…  batch 0f3c…
```

**A replay is distinguishable from a first attempt in two independent ways**, and
the agent cross-checks them: `replayed` is true, *and* `batch_id` names the batch
already on record. A first attempt returns `replayed: false` and a NULL batch id,
because its own row is written last and has no id to report yet. When those two
disagree the agent says so — it is the only local signal that would catch a
gateway answering something other than what this agent believes it is talking to.

### 8. After the Supabase push, before the run is recorded

**After**, so the authoritative write is never delayed or endangered by the new
one — a gateway that hangs costs the retry budget and nothing else.

**Before the run row is patched**, so a `dual` failure reaches the Health page in
*this* run's own error field rather than the next one's.

`push_ingest` swallows every exception and returns `(ok, note)`, so the outer
`except` in `cmd_sync` is unreachable from it and a green Supabase run stays
green. That is asserted by a test that makes the transport raise.

**The swallow starts at the projection, not at the POST**, and the first draft
got this wrong. `push_ingest` never raised, but `build_ingest_payload` and
`plan_ingest` sat outside it in `cmd_sync` — ordinary code with ordinary ways to
fail, the realistic one being a mapping that produced a row shape nobody
expected. An exception there would have reached the outer handler and turned a
*completed* Supabase push into `sync failed`, which is the exact opposite of the
property being claimed. `run_ingest_transport` and `preview_ingest_transport` now
hold the whole thing behind one `except` each. The lesson generalises past this
file: "this component cannot fail the caller" is a claim about every line of it,
and putting the guard at the part that obviously fails leaves the parts that
quietly do.

Proving it needed care, too. The obvious test — hand the transport a malformed
lead — fails for the wrong reason: a row malformed enough to break the projection
breaks `derive_events` first, and that is the *old* path, which is correctly
allowed to fail a sync. The test makes the projection itself raise, and also
asserts the Supabase upserts all completed.

### 9. Start years go inline here and stay bucketed there

The Supabase path pushes the two start-year columns as separate bucketed upserts,
because PostgREST rejects a batch with a mixed key set and a NULL year would
clobber a stored one. Neither constraint exists on the gateway: it takes one row
shape and `COALESCE`s both year columns, so a NULL leaves the stored value alone.

Same values, one statement. This is the one field the two transports genuinely
carry *differently*, so it is the one most able to drift, and the parity check
compares the inline years against exactly what `build_year_updates` would have
sent — including for leads that carry neither.

### 10. Retry because keyed; never a 4xx

Connection errors, timeouts, 429 and 5xx are retried twice with the same backoff
the Supabase writes use. The addition specific to this endpoint is *why* it is
safe: a timeout after the gateway committed is answered on the retry as a replay,
so the ambiguity a non-idempotent write has here simply does not exist.

Any other 4xx is never retried. A malformed batch, a revoked credential and a key
already used for different data are answers, not blips, and retrying them only
delays the log line that explains the run.

### 11. The token is screened locally before a request is made

A typo'd token otherwise costs a round trip and comes back as an opaque 401,
which reads like a *revoked* credential rather than a mistyped one. And parsing
is what lets the dry run name the credential at all: the id is the half that is
safe to print — it answers "which notebook is this?" without carrying anything
that authenticates — which is S21 design call 1 used from the other side.

The secret half is never printed, never logged, and leaves the process only in an
`Authorization` header. A test asserts it appears in no request body and in no
dry-run line.

### 12. The contract is pinned across the language boundary

The two halves of this contract are written in different languages and deployed
independently. The transport tests read `frontend/api/_lib/agent/ingest.ts` and
compare, against what the agent produces: the three caps, the idempotency-key
regex, and the **field names of all five row interfaces**. They read
`credentials.ts` for the token prefix and secret pattern, and `pipeline.ts` for
the config denylist.

That is the only thing that stops the two halves drifting, and it is cheap. The
`events` row is the one the agent sends short — `raw` exists on the contract and
`derive_events` has nothing to put in it — so the test asserts that difference
explicitly rather than loosening the comparison.

The tokens in the token tests are **generated**, not literals. S21 lost time to a
format bug that a hand-typed literal hid: base64url's alphabet contains `_` and
`-`, and roughly three real tokens in four carry one.

## Known limits

1. **No live end-to-end, and it is an owner gate.** Every property above is
   proved against a stubbed gateway. No real notebook has authenticated, no real
   batch has been written, and the endpoint answers 503 in every environment. The
   six actions that would change that are listed under "The owner gate" and none
   is a code change.
2. **The fixtures are synthetic.** Parity is proved over generated rows in the
   exact shapes `extract_local` returns, not over a real LH2 database. The cheap
   next check is `agent.py sync --dry-run` on one real notebook with 1.13.0
   installed — it contacts nothing and prints the parity verdict — and that is an
   owner action on a machine this project does not administer.
3. **One `sync_runs` row per chunk on the gateway side.** `recordSyncRun` is
   unconditional inside `ingestBatch`, so a five-chunk sync logs five rows there
   where Supabase logs one. Each row accurately describes its own batch, and
   `agent_ingest_batch` is the authoritative per-batch record, but a Health page
   fed from the new store would need to group them.
4. **An unchanged notebook re-syncing the same day is a replay,** so the gateway
   records no sync-run row for it and its `last_sync_at` there goes stale even
   though the agent is alive. The date component bounds this to a day. A real
   heartbeat is a separate operation and is not in this slice.
5. **A retry that crosses midnight mints a new key** and therefore a second batch
   row with the same digest. Harmless — every write behind it is an upsert — but
   it is the one case where "the same extraction" and "the same key" come apart.
6. **The key carries 128 bits of the digest,** not all 256. A truncation
   collision would present as a 409 rather than as corruption, at odds no
   deployment will meet.
7. **`photo_path` and `photo_synced_at` are always NULL from this transport.**
   The photo mirror writes them to its own store after the push; the gateway
   `COALESCE`s both, so sending NULL is a no-op rather than an erasure, and the
   new store simply has no photo paths until something else writes them.
8. **The two stores disagree about `events.occurred_at` on conflict.** Supabase
   takes the newest (migration 035); the gateway takes `LEAST`. Parity covers
   what is *sent*, not what each store does with it, and this divergence is the
   endpoint's design rather than something S22 introduced or can fix from here.
9. **`ingest_mode` is remote-overridable, so an admin can turn the transport on
   for a notebook and can point `ingest_url` anywhere.** The payload and the
   bearer token in its header would go there. An admin can already read every
   lead and issue credentials directly, so the marginal capability is nil — but
   the exposure is real, is identical to `notify_url`'s, and is stated rather
   than assumed away.
10. **The 66 offline tests do not run in CI,** because there is no CI for
    `sync-agent/`. They need the agent's own virtualenv (`agent.py` imports
    `requests` and `yaml` at module scope), which is gitignored. `deploy.sh` now
    runs them before publishing — that is the last gate before the whole fleet
    self-updates, and `py_compile` alone only proves the build parses — but it
    **skips them with a warning** when the virtualenv is absent, so a fresh
    checkout can still deploy. Anything stronger than a warning would make the
    deploy path depend on an untracked directory.
11. **Everything the migration's own limits say still holds.**
    `NEON_READS_DEFAULT` is not flippable, `NEON_WRITES_DEFAULT` gates the S14
    writes, and the next database decision is still a whole-cutover one.
