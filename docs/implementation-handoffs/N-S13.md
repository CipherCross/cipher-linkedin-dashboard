## An incident I caused, and how it was found

Worth recording first because it is the most transferable thing in this document.

Midway through, `tests/dataStore.neon.test.ts` — an **S11** test, untouched by
this session — started failing, in isolation as well as in the full run:

```
Neon driver — the actor context cannot leak between transactions
  > confirms the same transaction scoping through the pooled endpoint
AssertionError: expected '00000000-0000-0000-0000-000000000001' to be ''
```

That test opens a raw `pg.Client` against the **pooled** endpoint, sets
`app.actor_id` transaction-locally, commits, and asserts the setting is gone. It
had passed at session start.

**The cause was my own diagnostic script.** To size the fixture I had probed the
live project and published an actor so RLS would let me count rows — with
`set_config('app.actor_id', …, false)`. The third argument is `is_local`, and
`false` makes the setting **session**-scoped rather than transaction-scoped. Neon's
pooler multiplexes client connections onto reused server backends, so that
setting outlived my script and leaked into whichever client later landed on those
backends. The value the test reported was exactly the one my probe had set.

**Repaired and verified.** Twelve concurrent pooled connections were opened to
force the pooler to hand out distinct backends: **6 of 12 were polluted**, all were
reset with `set_config('app.actor_id', '', false)`, and re-measurement showed
**0 of 12**. `dataStore.neon.test.ts` then returned to 33/33 and the full Neon suite
to green.

Three things follow, and the last is the one that matters:

1. **A throwaway script against a shared pooled endpoint is not read-only** even
   when it only runs `SELECT`s. `set_config(..., false)` is a write to session
   state that survives the process.
2. **Always pass `true`.** The driver already does this everywhere, which is why
   the product code never had this bug — only my scratch script did.
3. **The S11 test that caught this is more valuable than it looks.** It reads like
   a tautology about PostgreSQL semantics; it is actually a live probe of the
   pooler's isolation, and it caught cross-connection contamination that no
   application test would have. It should not be "simplified" away.

## The design calls

### 1. Keyset pagination — the operation owns the predicate, the driver owns the cursor

N-S12 pre-decided keyset for the inbound-messages read and required it be written
**before** the read rather than retrofitted, and that extending `neon.ts` be
scoped as a driver change rather than smuggled into a slice. Both held.

**Decision: an operation declares `keyset: { columns: [...] }`. The driver decodes
the previous page's key, hands it to `build` as `context.after`, and applies
`LIMIT` with no `OFFSET`. The operation writes its own seek predicate and its own
`ORDER BY`.**

**The rejected alternative was the symmetrical one.** The driver already wraps
every query as `SELECT * FROM (…) AS datastore_page LIMIT $n OFFSET $m`, so the
obvious move is to have it also append
`WHERE (a, b) < ($1, $2) ORDER BY a DESC, b DESC`. Rejected on two grounds:

- **It depends on the planner.** A qual applied outside a subquery only reaches an
  index if the subquery is flattened and the qual pushed down. When that does not
  happen, every page sorts the whole relation and keyset buys nothing while
  looking like it works — a failure mode with no symptom.
- **It duplicates the operation's knowledge.** Emitting a correct comparison needs
  the sort direction, the NULL ordering and the column types. That is the
  operation's own knowledge, and a second copy in the driver is how the two drift.

**What the driver keeps is the security-relevant half**: the cursor stays opaque
and scope-bound. The digest still pins operation, params, range, tenant and actor,
so a forged key can only re-request rows the same actor could have requested
directly, and RLS still decides the row set. The payload does carry the last row's
key values in decodable form — and those values were in the response body the
caller just received, so nothing is disclosed that the caller did not have.

**Two defects found while writing it, both now asserted:**

- **The cursor codec split on the last `.` and had to split on the first.** A
  sha256 digest in base64url contains no `.`, so for an integer payload the two are
  identical — which is why the existing code was correct. A keyset payload is JSON,
  and `2025-03-01T09:00:00.000Z` carries a `.` of its own. `lastIndexOf` would have
  rejected every page after the first, for messages only.
- **Cursor arity has to be checked against the declared key width.** A two-element
  key handed to a one-column operation would be spliced into the parameter list and
  shift every later placeholder, producing a syntactically valid query about
  something unrelated. It is refused as a pagination error before the database.

**Offset stays the default and every existing operation is untouched.** Which
reads seek and which count is asserted in the guard suite so it stays a decision.

### 2. Keyset's benefit is real but **not yet realized**, and the numbers say so

This is the call most at risk of being written up dishonestly, so here are the
measurements before the argument. Server-side `EXPLAIN ANALYZE`, p50 of 7 runs,
over the fixture's 2,103 inbound messages:

| page | execution |
|---|---|
| `OFFSET 0` | **8.23 ms** |
| `OFFSET 2000` | **7.57 ms** |
| keyset seek to row 2000 | **6.93 ms** |

**Keyset is not measurably faster here.** The spread is inside the noise and the
*first* offset page is the slowest of the three. Client-side timings through the
handler agree and are dominated by the ~40 ms RTT (99/96/48 ms across a
three-page keyset walk).

**The plan explains why, and it is the actual finding.** Both formulations produce
`Seq Scan on messages` feeding a `top-N heapsort`. The sort key
`(sent_at DESC, id DESC)` has **no unpartial index behind it** in the baseline:
`messages_thread_latest_nonempty_idx` carries those columns but is partial and
prefixed by `(instance_id, profile_url)`, and `messages_intent_backlog_idx` is
partial on the intent backlog. The ROW comparison lands as a `Filter`, not as an
`Index Cond`. So neither formulation avoids scanning today and their costs
converge.

**Keyset was still written, for two reasons independent of today's numbers:**
`OFFSET n` is O(n) in rows discarded and therefore quadratic over a full walk once
the relation is large; and a seek predicate is the only one of the two an index
*can* satisfy. Adding `messages (direction, sent_at DESC, id DESC)` turns this into
an index scan and makes the difference real — **that is a ledger step, so it is not
this session's** (R5: the ledger is the only apply path). It is Known limit 1.

### 3. The `leads` column ladder dies, and does not become a parameter

`DataContext` walks a four-rung retry ladder: request the widest column list, and
on PostgREST's SQLSTATE 42703 drop to a narrower rung.

**Decision: one fixed projection. No ladder, and no ladder-shaped parameter.**
Three reasons, in the order that decided it:

1. **There is no drift window to survive.** The ladder exists because migrations
   041/042/048 were applied to Supabase out of band, so a deployed frontend could
   be ahead of the database. The Neon schema is applied through the migration
   ledger with pinned digests, and the baseline already contains **every column of
   the widest rung**, including the demographics-v2 set. A missing column here is
   not a migration in flight; it is a broken deployment.
2. **Silent degradation is worse than failure on this particular read.** A narrower
   rung returns leads with no `pipeline_stage`, and `stageOf` reads an absent stage
   as an un-staged lead. The dashboard would not break — it would report a
   *different funnel*, confidently. That trade was worth making against a dead page
   during a known migration window. It is not worth making to paper over a
   deployment error.
3. **A caller-chosen column list is SQL crossing the contract boundary.** A
   parameter naming columns is a projection expressed by the caller, which is what
   the registry exists to prevent. It would have kept the letter of "handlers submit
   names, never SQL" while giving it up in substance.

A consequence worth stating: `LeadRow`'s demographics fields are
non-optional-but-nullable, where `Lead`'s are optional. On this path `null` means
"not inferred" rather than "not asked for", which is strictly more information.

### 4. `messages` is two operations, not one with a `direction` parameter

**Decision: `messages.inboundHistory` and `messages.outboundRecent`.**

The asymmetry between them is a product invariant, not a filter value. `CLAUDE.md`
states it: inbound is fetched in full, all-time, because sentiment and the durable
P3 milestone — the denominator for post-P3 booking conversion — are rendered beside
all-time lead totals, so a window silently undercounts them on a busy account.

A single `messages.byDirection(direction, since)` would have made that invariant a
caller's responsibility, and the first caller to pass a `since` for inbound would
break the P3 numbers without breaking a test. Two named operations put the decision
in the vocabulary: `inboundHistory` **ignores `range` entirely**, and a test asserts
that supplying one does not change its rows.

### 5. The delta watermark is a parameter, and `range` is not overloaded

`DataContext` refreshes on a 5-minute interval by fetching only rows whose
`updated_at` moved past a cursor.

**Decision: an explicit `updatedSince` parameter (`?updated_since=`), instant-granular.
`leads.directory` ignores `range` altogether; `messages.outboundRecent` uses `range`
for its `sent_at` window and `updatedSince` for the watermark at the same time.**

For every other operation `range` means "the window the rows belong to" —
`daily_activity.day`, `messages.sent_at`. `updated_at` is not that: it is a
replication watermark, and a lead invited in January reappears in a delta because
somebody re-staged it today. Overloading one field to mean sometimes one and
sometimes the other is how a caller filters the wrong column. It is instant-granular
rather than day-granular because the watermark's job is to be finer than a day —
the Supabase path sets it to load-start minus a two-minute overlap, and rounding to
a day would either re-fetch the day so far every tick or skip commits.

### 6. The roster stays off this path — N-S12's pre-decision is retired

N-S12 recorded that "the `team_members` roster is available through the B4
function, so assignee and owner name joins work". **That premise is retired.**

`leads.assigned_to` is a `bigint` FK into a Supabase `team_members.id`, and the same
integers on Neon denote different people — source 1 is the real admin, target 1 is
the immutable S06 fixture "Active One" (N-B2 has the full map). A Neon roster joined
against Supabase-shaped `assigned_to` in `usePipelineActions.memberName` mislabels
every Pipeline owner chip and CSV column **and fails nothing**.

So the column is **read and never resolved**: `leads.directory` selects it, and
nothing on this path reads `team_members` or `team_roster`. Asserted structurally —
one `FROM`, no `JOIN` of any kind — rather than by comment.

**The guard suite's `assigned_to` assertion was deliberately narrowed, and this is
the widening the brief asked to be declared.** Part 1 asserted "no operation's SQL
contains the string `assigned_to`", which was true only because no operation read
`leads` yet. `leads.directory` must carry the column — the Pipeline page's owner
state *is* that value, and dropping it would be data loss dressed as caution. The
invariant is now the one always meant: the column may be selected, and must never be
joined. Every other operation still may not mention it at all.

The allowlist itself grew from six names to nine, spelled out literally so a tenth
has to edit that line, plus a new assertion that every allowlisted name has an
inspected definition — otherwise a read could dodge every guard by not appearing in
the list.

### 7. Two invariants this session establishes for whoever moves the roster

1. **`leads` and `team_members` are one unit.** Whatever provider answers one must
   answer the other. Mixing providers is what breaks, and `config.readPath` cannot
   be flipped for leads until the roster moves too.
2. **`public.team_roster()` returns no `auth_user_id`.** `Team.tsx:236-239` decides
   "Login enabled" vs "Assignment only" on that column alone, so the roster needs a
   new column stating whether a login exists before any browser reads it from Neon.
   That widening belongs to the session that moves the roster — **not** to ledger
   steps `001`–`005`, which are frozen.

### `frontend/src/lib/leads.ts` against Neon — N-B2's open item, closed

`tests/leadsRecompute.neon.test.ts`, 9 tests. N-B2 left this explicitly to S13: the
two SQL views agreeing across providers says nothing about the *client recompute*,
which is what every page renders.

Rows are fetched through the real read path and put into the real functions:

- **`stageOf`** — all four stages populated, every count matching an expectation
  computed independently of any SQL.
- **`rangeTotals`** — the all-time funnel matches the fixture's own; over four
  bounded windows it matches PostgreSQL computing the same window with
  `BETWEEN … ::date`, including both constrained rate numerators.
- **`rangedCampaigns`** — every count and both rates reproduce `campaign_metrics`
  at the view's own one-decimal precision.
- **`riskOf`** — both risk cohorts flagged at their exact expected sizes.

**The finding this harness produced.** `tsInRange` takes a lead's day with
`ts.slice(0, 10)` — it does not parse. So the entire ranged funnel depends on
instants arriving as UTC with a `Z`, which is a property of the *driver's type
parsers* rather than of anything in `leads.ts`. PostgREST emits `+00:00`, the Neon
driver emits `Z`, and both slice to the same day — but a driver change, a pooler
change or a `timestamp`-typed column would shift every ranged metric by up to a day
while every count-based test stayed green. The suite demonstrates the hazard with a
counter-example (the same instant respelled at `-14:00` leaves a single-day range)
and then asserts the guarantee over the rows it actually fetched.

**A pre-existing divergence found and deliberately not fixed.**
`campaign_metrics.last_activity_at` is `max(last_action_at)`; `rangedCampaigns`
instead takes the newest of `invited_at`/`connected_at`/`replied_at`, while its own
comment claims the two match. They do not, whenever `last_action_at` is not itself
one of those milestones — the normal case in production. This exists identically on
the Supabase path. S13 found it, did not introduce it, and does not fix it: changing
a displayed metric is a product decision, not part of a read migration. It is
asserted as a *divergence* so it cannot be mistaken for parity. Known limit 4.

## Known limits

1. **The keyset index does not exist.** `messages (direction, sent_at DESC, id DESC)`
   would turn the seek into an index scan; without it both offset and keyset do a
   `Seq Scan` plus `top-N heapsort` and their costs are indistinguishable at fixture
   scale. It is a ledger step and therefore a later session's. **Until it lands,
   keyset is the right shape with none of its benefit.**
2. **Eleven of twenty `DataContext` reads are not migrated**, plus all three
   component-local reads. Enumerated below.
3. **`conversation_reply_intent` is unpaginated on the Supabase side today** and
   therefore silently truncated at PostgREST's 1,000-row cap
   (`DataContext.tsx:636`). That is a **live bug on the existing dashboard**, not
   something this session introduced, and it is not inherited silently: part 3 owns
   that read and must paginate it. Worth telling the owner independently of the
   migration, because it affects numbers being shown today.
4. **`rangedCampaigns` and `campaign_metrics` disagree on `last_activity_at`** —
   pre-existing, present on both providers, asserted as a divergence rather than
   fixed. See above.
5. **The fixture is permanent.** 2,300 leads, 3,503 messages, 3 campaigns and 1
   instance under `s13-dashboard` now live on the shared Neon project, joining
   S11's and S12's. All synthetic, no tenant data, idempotent under re-run — but the
   project's `leads` and `messages` counts are no longer near-zero, so a future
   session must scope by `instance_id` rather than assume an empty relation.
6. **The Neon suite mutates the shared project**, unchanged from S11: two concurrent
   runs would interfere, and `fileParallelism: false` protects a single runner rather
   than two developers. The pooled-session incident above is a sharper instance of
   the same hazard.
7. **No browser evidence.** Nothing in `frontend/src/` changed, so there was nothing
   to render; S12's harness was not re-run. The first browser evidence for these
   reads belongs to S18, which rewires `DataContext`.
8. **Parity is against seeded fixtures, not tenant data.** B2's copy is deleted and
   re-copying is a fresh owner decision. What is proven is that these operations and
   the client recompute agree with SQL over a controlled dataset — not that live
   dashboard figures match.
9. **`leads.directory` is unscoped by instance.** `DataContext` reads the whole team
   at once, so this is correct, but it means the read returns whatever else is on
   the project; the live suite filters to its own `instance_id` and asserts global
   consistency separately.
10. **The delta path is untested against a real concurrent write.** `updatedSince`
    is proven to select the stamped cohort; the 2-minute overlap that makes it
    correct under concurrency is inherited from the Supabase path unchanged and
    unexercised.
