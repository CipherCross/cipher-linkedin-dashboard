## Completed scope

- Added the versioned platform operations contract `p2.v1`.
- Defined deterministic naming, immutable tenant slugs, closed logical ownership
  tags, strict adoption rules, and stable cron-slot allocation.
- Defined versioned allowlist catalogs for regions, provider tiers, pricing,
  backup profiles, release compatibility, capabilities, and subprocessors.
  Unknown, expired, unpriced, deprecated, or unapproved entries block apply.
- Defined production prerequisites for provider organizations, region/data
  residency, capacity/tier selection, custom SMTP/Auth delivery, backup coverage,
  source revision, and external machine-scoped ingest.
- Added strict Draft 2020-12 JSON Schemas for:
  - onboarding plan envelope/spec;
  - release plan envelope/spec;
  - apply/resume request.
- Fixed the RFC 8785 canonical-plan/SHA-256 digest contract, plan expiry and
  invalidation rules, registry optimistic version check, operation locking, and
  idempotency conflict behavior.
- Fixed onboarding effect order, canary/fan-out release order, required smoke
  tests, and plan/tenant/operation/step state machines.
- Defined the logical SQLite registry/audit model that P3-A must implement,
  including resource references, fencing locks, release targets, capability
  budgets, recovery profiles, Keychain references, and hash-linked audit.
- Defined itemized integer-minor-unit monthly cost estimates, explicit paid-tier
  selection, capability budgets, usage ceilings, and overage actions.
- Defined the default recovery objective: RPO at most 24 hours, RTO at most one
  eight-hour business day, daily provider backup, encrypted export at least every
  seven days, and disposable restore rehearsal at least every 92 days.
- Defined the full forbidden/destructive surface, including provider deletion,
  down/repair migrations, raw provider/SQL/shell/HTTP/DNS/env/secret operations,
  automatic cleanup, stale-plan apply, early admin invite, Preview secrets,
  pre-canary stable rollout, and service-role credentials on external machines.
- Added the future operator workflow and break-glass boundary to `AGENTS.md`.

## Remaining blockers and risks

- P2 has no acceptance blocker.
- There is deliberately no approved live provider catalog yet. Until later
  implementation loads an approved, unexpired catalog snapshot, an onboarding
  plan must remain blocked rather than guess a tier, region, capability, or price.
- JSON Schema enforces structure and closed vocabularies. Cross-field relations
  documented in the contract — such as cost high/low ordering, consecutive
  migrations, provider snapshot drift, catalog resolution, and capability
  secret/budget rules — must be implemented as semantic validation in P3-A.
- External company onboarding remains intentionally blocked until P5 provides an
  approved machine-scoped ingest protocol without client-side service-role or
  shared notification secrets.
- The standard recovery target is a contract, not a completed backup setup.
  Provider backup/export automation and a measured restore rehearsal remain P8-A.
