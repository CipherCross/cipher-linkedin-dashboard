### Finding: the control-plane bootstrap could not run on a managed provider

`000_control_plane_role_bootstrap.sql` failed on Neon at
`ALTER SCHEMA public OWNER TO app_owner`:

```
ERROR:  must be able to SET ROLE "app_owner"
```

**Mechanism.** Since PostgreSQL 16, a non-superuser holding `CREATEROLE` that
creates a role is auto-granted membership in it with `admin_option = true` but
**`set_option = false`**. Transferring an object to a role requires the executor
to be able to `SET ROLE` into it. Measured on the live project:

| member | role | admin_option | inherit_option | set_option |
|---|---|---|---|---|
| `neondb_owner` | `app_owner` | t | f | **f** |
| `app_migration` | `app_owner` | f | f | t |

`pg_has_role('neondb_owner','app_owner','SET')` returned **false**.

**Why S08 never saw it.** The clean-room harnesses bootstrap as the superuser
`postgres`, which is exempt from the membership check. The container's superuser
masked the defect. The file's own header claims it is intended to run as "the
provider's database owner role on a managed platform" — precisely the case that
failed.

**Scope.** This is not Neon-specific. It affects any provider that hands the
operator a non-superuser `CREATEROLE` principal, which is the normal
arrangement. It was also **not** caused by the version difference: the failure
was first seen on 18.4 and then reproduced byte-identically on 17.10, with the
same statement, same message and the same `set_option = f`. That reproduction
was run deliberately, as a stated prediction, before the fix was written.

### Fix

A conditional grant immediately before the ownership transfer:

```sql
DO $$
BEGIN
    IF NOT (SELECT rolsuper FROM pg_roles WHERE rolname = CURRENT_USER) THEN
        EXECUTE format(
            'GRANT app_owner TO %I WITH SET TRUE, INHERIT FALSE',
            CURRENT_USER
        );
    END IF;
END
$$;
```

Design notes:

- **Superuser → no-op.** A naive unconditional grant would add a membership row
  for `postgres` in the clean-room, and role memberships are part of the S08
  inventory snapshot — fixing the provider path would have broken the existing
  evidence. The guard keeps the container role graph byte-identical.
- **No privilege is conferred.** The principal created these roles and holds
  `ADMIN OPTION` on them, so it could grant itself `SET` at any time.
  `neondb_owner` additionally holds `BYPASSRLS`, `CREATEROLE` and `CREATEDB`
  over this database already.
- **`INHERIT FALSE`** preserves the contract's rule that a privilege is only
  ever used after an explicit `SET ROLE`.
- The grant is **permanent**, by owner decision. A self-closing window was
  considered and rejected: every subsequent control-plane ownership operation
  would hit the same wall again.

## Every way real Neon differed from PostgreSQL 17.10 in a container

Stated even where it did not matter, as required.

1. **The privileged principal is `neondb_owner`: a non-superuser** with
   `CREATEROLE`, `CREATEDB` and `BYPASSRLS`. The container's is superuser
   `postgres`. **This mattered** — it is the entire finding above.
2. **`REVOKE ALL ON SCHEMA public FROM PUBLIC` in `000` silently does nothing**,
   emitting `WARNING: no privileges could be revoked for "public"`. After
   `ALTER SCHEMA ... OWNER TO app_owner` the remaining PUBLIC grant is recorded
   as made by `app_owner`, and `neondb_owner` holds that membership with
   `INHERIT FALSE`, so it revokes nothing. **This did not matter in the end**:
   step 002 repeats the same `REVOKE` under `SET ROLE app_owner` and it
   succeeds. Verified after apply — final ACL carries no PUBLIC entry,
   `has_schema_privilege('public','public','USAGE')` is false, `CREATE` is
   false, and 0 tables are granted to PUBLIC. It is worth flagging because it is
   the same class of hazard as R1: a failed REVOKE is a warning, not an error.
3. **Schema `public` is owned by `pg_database_owner`**, not `postgres`. Did not
   matter; the bootstrap transfers ownership.
4. **The only superuser is `cloud_admin`**, unavailable to the operator. Did not
   matter for apply; it does mean the ledger harness's case 10 ("a superuser
   apply principal is rejected") cannot be exercised on Neon at all.
5. **The initial project defaulted to PostgreSQL 18.4.** Removed by recreating
   at 17.10. Had it been kept, `pg_dump` 17.10 could not have dumped the server
   at all, since pg_dump refuses a newer major version.
6. `pgcrypto` is available at 1.4 and installs as a trusted extension by the
   non-superuser owner, exactly as the baseline assumes.

## Is risk R2 closed?

**Partly. Honestly, not fully, and it cannot be fully closed by these harnesses
as written.**

Closed:

- the portable baseline applies on real Neon, through the ledger, as a
  non-superuser, and produces an inventory identical to the container's on every
  recorded metric;
- roles created by SQL authenticate through Neon's proxy;
- the trusted-extension assumption holds;
- actor context, RLS, runtime boundaries and the AI guard all behave identically
  on the real provider;
- ledger idempotent-skip and verify hold on a real provider.

**Not closed:** the dump/restore half. Neither S08 harness can be pointed at a
managed provider, for three independent reasons:

- both `docker run` their own clusters; there is no host or endpoint override
  (only `POSTGRES_IMAGE` and `S08_EVIDENCE_JSON`);
- both drive the cluster as superuser `postgres` under
  `POSTGRES_HOST_AUTH_METHOD=trust`; Neon offers neither;
- `portable_dump_restore_cleanroom.sh` requires **three independent clusters** by
  design — roles are cluster objects, so reusing them would hide a dependency the
  bootstrap must create. Neon branches and extra databases do not substitute:
  both inherit the project's roles, defeating the exact property the replica
  cluster exists to prove. A5 authorises one project.

So the G1 phrasing "re-run both harnesses against a disposable project" was not
mechanically achievable. What was achievable — the apply path and every
behavioural property — was done. Giving real-provider dump/restore evidence
needs an external-endpoint mode in the harnesses, which is its own piece of work
and its own owner decision. **S27's timed rehearsals depend on this.**

## Design inputs measured for the driver (not yet acted on)

The pooled endpoint is Neon's PgBouncer in transaction mode. Measured through
it, as `app_runtime`:

| moment | `app.actor_id` | `statement_timeout` |
|---|---|---|
| inside the transaction | `0000…0001` | `10s` |
| same connection after `COMMIT` | empty | `0` |
| a fresh session | empty | `0` |

This is the empirical basis for the pooling decision S11's phase 1 must make:
`SET LOCAL` is correctly transaction-scoped through PgBouncer, so the actor
context **cannot** leak across pooled connections — it does not outlive the
transaction that set it. The same measurement shows `SET LOCAL
statement_timeout` surviving into the transaction, which is the mechanism R3
requires.

The four open design calls (driver choice, pooled vs direct endpoint, driver
location, credential path for tests) are **deliberately not decided here**.
Deciding them before the baseline was verified would have been deciding against
a blog post rather than against measured behaviour — and the baseline turned out
to need a fix, which is exactly why the sequencing mattered.

## How the actor context reaches the database

Not chosen by me — read out of `002_identity_roles_actor_rls.sql`, whose header
states it: the server-owned API must begin each database transaction with
`SET LOCAL app.actor_id = '<canonical user UUID>'`. Every policy reads it back
through `current_setting('app.actor_id', true)`, guarded by a strict UUID regex
and a `CASE` that yields `NULL::uuid` for anything malformed, then requires an
active `users` row and an active `team_members` row. Missing, malformed, unknown
and inactive actors therefore fail closed inside the policy expression, without
relying on provider claims. The driver's job is to set it; RLS decides.

## Why the driver was not built

Phase 0 was specified as a gate that comes first, and it did not pass cleanly —
it produced a defect that prevented the baseline from applying to any managed
provider at all. The brief's own instruction for that case is a finding and a
stopped session rather than a driver built on an unverified baseline.

The owner elected to repair the defect properly rather than work around it on
the live project, which was the right call but converted the session into
baseline work: fix, re-pin, re-run both clean-room harnesses to prove no
regression, then apply and verify on the real provider. That is the whole
session.

Building the driver on top of a baseline artifact that changed **today** and has
not yet been reviewed would also have compounded two things that deserve to be
judged separately.
