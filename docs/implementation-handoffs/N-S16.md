## The design calls

### 1. The candidate itself — accept, with conditions

**Decision: recommend accepting it.** The full comparison is finding **F12** in
the G3 artifact; the short version of why the realistic alternatives lost:

- **Hand-rolled sessions on the canonical tables** is the serious alternative
  and the closest call. It removes the second user store entirely. It loses
  because the delta it buys is one column and one round trip — both of which the
  resolver function in F7 removes anyway — while the delta it costs is
  authorship of scrypt parameters, token entropy, timing-safe comparison,
  single-use reset tokens, cookie signing and origin validation. The candidate
  already passes every check this spike ran; a hand-rolled one would have to
  pass them again, written by us. It also still needs its own ledger session for
  a sessions table, so it does not even avoid the schema change.
- **Auth.js / `@auth/core`** is oriented at OAuth providers and JWT sessions,
  and ships no invite, ban or revocation primitives — we would build the whole
  lifecycle on top and still carry the dependency.
- **Lucia** was deprecated as a library in March 2025 and is now a learning
  resource for implementing sessions yourself. Choosing it *is* choosing the
  hand-rolled option.
- **Self-hosted Ory Kratos / Keycloak / Zitadel** are services to deploy and
  operate — a new runtime component for four users, and a new deployment the
  current constraints forbid.
- **A managed provider, or staying on Supabase Auth**, contradicts the point of
  the migration. G0 already excluded managed Auth, and staying on Supabase Auth
  would keep a live Supabase dependency after N8 is meant to have removed the
  last one.

Two things about the candidate carried real weight beyond feature coverage. It
is a **library, not a service**, so it adds no deployment and no provider. And
the **porting surface is two function members** — `handler(request)` and
`api.getSession({headers})`, the whole of `CandidateAuth` in `src/handler.ts` —
so if it ever has to be replaced, that is a bounded change rather than a
rewrite. That is worth as much as any feature, because it is what stops this
decision from being irreversible.

### 2. Cookie session, not a token — and where the session lives

**Decision: an opaque session token in an `HttpOnly` cookie, with the session
row in the database. Not a JWT, and nothing in browser storage.**

- Revocation has to be immediate, and the single best result of this spike
  (below) depends on server-side state being consulted per request. A
  self-contained JWT would stay valid until it expired.
- An `HttpOnly` cookie is the only option that keeps the credential away from
  script. Anything the SPA can read, an XSS payload can read.
- The price is CSRF surface, because the browser attaches the cookie by itself.
  That price is paid explicitly — `SameSite=Lax` plus origin validation — and it
  is **measured**, not assumed.
- The serverless price is a database round trip per request.
  `session.cookieCache` is deliberately **left disabled**: enabling it validates
  the session from a signed cookie instead, which reintroduces exactly the
  revocation delay a JWT has. If S17 wants it for latency, that is a deliberate
  trade and needs its own decision.

### 3. Where the identity store lives

**Decision: the candidate keeps its own four tables, in the same database as the
canonical ones, in its own schema, owned by its own role, with no grants either
way.**

There is **no second source of truth for `users.id`**, and the schema enforces
it: the candidate's `user.id` is `text`, because it is a *provider subject*. It
belongs in `user_identities.provider_subject` and cannot be casually joined to a
`uuid`. The one genuine duplication is the email address, which exists on both
`identity_spike.user` and `public.team_members`.

Co-location in one database is what answers reconciliation: **invite and disable
are one SQL transaction across both stores**, so there is no compensating write
and no reconciliation job. Measured — a transaction that writes `public.users`,
`public.team_members`, `public.user_identities` and the candidate's `user` and
`account` rows, then fails on the candidate's half, leaves neither store with a
half-person.

Isolation is measured in both directions: the `identity_store` role cannot read
any business table or any canonical identity table (42501, six relations), and
`app_runtime` cannot read the candidate's `user`, `session` or `account` tables
(42501, three relations) — so a SQL-injection or a policy mistake in the product
cannot become a credential dump. Only the admin path reaches both, and only
under an explicit `SET ROLE`, because `app_migration` is `NOINHERIT`.

### 4. What S18 will need

Recorded so the `AuthContext` rewrite is mechanical rather than a redesign. Full
list in the artifact (F14); the load-bearing parts:

- **The browser holds nothing.** There is no token for `AuthContext` to store,
  read or refresh. Its state comes from one authenticated call.
- **`GET /api/s16-whoami` is the shape of that call**: `{subject, actor:
  {actorId, role}}` on 200.
- **Three outcomes, not two.** 401 is "not signed in"; **403 is "signed in, but
  not an active member"** and is genuinely reachable, because a deactivated
  member keeps a valid session. The UI needs a distinct "your access has been
  removed" path rather than bouncing them to sign-in.
- `role` comes from that response, never from the session, and is the only thing
  route gates may key on.
- Sign-in returns **200 with a Set-Cookie, not a 302**, even when given a
  `callbackURL` — so the SPA navigates itself.
- Every state-changing request must be same-origin; a cross-origin call from a
  preview domain to the production API is refused 403.

## Required coverage — what each test proves, and what it does not

### Session cookies

**Proves.** Measured off the wire: one session cookie, `HttpOnly`,
`SameSite=Lax`, `Path=/`, `Max-Age=604800`, value signed `<token>.<hmac>`.
Nothing is script-visible, so `document.cookie` yields nothing. A real 302 — the
password-reset link — carries the already-held `HttpOnly` session to the target
path and the target authenticates. An off-origin `redirectTo` is refused 403
`INVALID_REDIRECT_URL`. With `useSecureCookies` on over plain HTTP, the header is
sent and a browser drops the cookie, so the next request is anonymous — the
local-development trap, stated before S17 hits it.

**Does not prove.** Browser-engine behaviour. The spike's jar implements the RFC
6265 rules; it is not a browser, so Chrome's two-minute `SameSite=Lax` POST
grace period, third-party cookie policy, CHIPS partitioning and
`__Host-`/`__Secure-` prefix *enforcement* are untested. The harness is plain
HTTP on localhost, so TLS itself is not exercised and `Secure` is measured
through the jar's storage rule.

### CSRF

**Proves.** Seven refusals observed over HTTP with the status and error code the
candidate actually returned, plus a same-origin control that succeeds:

| request | result |
|---|---|
| `update-user`, valid session, own origin | **200** (control) |
| `update-user`, valid session, hostile origin | **403** `INVALID_ORIGIN` |
| `update-user`, valid session, no `Origin` header | **403** `MISSING_OR_NULL_ORIGIN` |
| `change-password`, hostile origin | **403** `INVALID_ORIGIN` |
| `sign-out`, hostile origin | **403** `INVALID_ORIGIN` |
| cross-site *navigation* sign-in | **403** `MISSING_OR_NULL_ORIGIN` |
| off-origin `callbackURL` | **403** `INVALID_CALLBACK_URL` |

Replay is covered separately: a token spliced onto another session's signature
is refused 401, a tampered value is refused 401, and a cookie captured before
sign-out is worthless after it — while A's intact cookie still resolves to A, so
the splice failed on the signature rather than because the session died.

**Does not prove.** That a browser produces these header combinations — the
requests are constructed. And the candidate protects **only its own routes**:
`/api/pipeline`, `/api/import` and S13's dispatching endpoint get nothing from
it.

**Two findings inside this one.** There is **no synchroniser token** — the
question "is a state-changing request without the token refused" has to be
re-posed as "without a trusted *origin*", because that is the defence the
candidate implements. And **the candidate switches that defence off when it
detects a test environment**: `skipOriginCheck` resolves to
`disableOriginCheck ?? (isTest() ? true : false)` with `isTest()` being
`NODE_ENV === 'test' || TEST`, and skipping the origin check also skips the CSRF
check. Vitest sets `NODE_ENV=test`. A CSRF suite that does not set
`advanced.disableOriginCheck: false` runs against a build with **no CSRF
defence** and reports green. The spike asserts both directions — with the check
off, the identical hostile-origin request returns **200** — so the pair cannot
rot.

### Invite / reset / disable

**Proves.** Public sign-up refused (400 `EMAIL_PASSWORD_SIGN_UP_DISABLED`).
Admin `create-user` refused for an anonymous caller (401) and for an ordinary
member (403). Reset issues a token to a sink we control, returns an identical
body for an unknown address and mints no token for it (not an enumeration
oracle), is single-use, and invalidates the old password.

And the requirement as written — a disabled person's **existing session** stops
working, not merely their next sign-in — in **two** independent ways:

| kill switch | existing session | can they sign in again? |
|---|---|---|
| canonical: `team_members.active = false` | **403 on the very next request** | yes — authenticated, but not a member |
| candidate: `admin/ban-user` | **401**, session destroyed | no |

The canonical one needs no session bookkeeping at all, because the actor is
re-resolved from the tenant database on every request. **This is the single
strongest structural result of the spike**: authorization does not depend on the
identity provider's own state being correct, which is what makes the provider
replaceable. Corroborated by a role conflict — an account whose candidate-side
role says `admin` while `team_members.role` says `member` resolves as
**member**.

**Does not prove.** Email delivery. No SMTP provider was configured and no mail
was sent; the token is captured in process. The spec already treats SMTP as an
external gate.

**One finding.** A **password reset does not revoke existing sessions by
default** — `revokeSessionsOnPasswordReset` is only consulted when set. A reset
is the flow used *after* a suspected compromise, so the default is the wrong way
round here. Measured at 200 (default) and 401 (with the option), both asserted.

### Mapping

**Proves — on the live Neon project, read-only.** A session the candidate issued
resolves to a canonical `public.users.id` through `public.user_identities` under
the baseline's own RLS, with the role read from `team_members`. It runs through
the **product's own driver and its own `identity.resolveSelf` operation** — the
same code path `frontend/api/activity-daily.ts` uses. The spike supplies the
subject; the product supplies the mapping. Active member → `…0001`/member;
active admin → `…0002`/admin; inactive user → 403; unmapped subject → 403;
proposal naming a different real user → 403.

**Nothing was written to Neon.** The candidate was told to mint accounts whose
ids are exactly the baseline's fixture subjects, so the existing rows sufficed. A
test asserts that subjects this suite invented resolve to nothing — which they
could not do if the suite had written them.

**Does not prove.** The production provider label: the live leg matches on
`provider = 'fixture'` because those are the rows that exist, while production
would use `provider = 'better-auth'` (which the clean-room leg uses). The
predicate is identical either way.

### Rotation and expiry

**Proves.** At expiry the browser drops the cookie at `Max-Age` and the raw
value replayed afterwards is refused 401. On refresh the expiry slides forward
and **the token does not change** — `session.token` and the cookie value are
byte-identical before and after, so there is no rolling token. Each sign-in
issues a distinct session and leaves earlier ones live; sign-out ends one,
`revoke-sessions` ends all. A value planted under the session cookie's name
before sign-in is replaced by it, so there is no fixation surface.

**Does not prove.** Behaviour across a clock change or a long-running
deployment; the windows tested are seconds.

**One housekeeping finding.** An expired session that is *presented* is deleted;
one that is simply abandoned stays in the table. `session` grows with every
abandoned login. Not a security hole — an expired row is never honoured — but
not self-limiting either.

### Vercel smoke — NOT DONE

The coverage list asks for it; this session's invariants forbid creating
anything on a provider, and a deployment is a provider resource. **The owner was
asked on 2026-08-03 and chose no deployment**, with the gap recorded.

The two alternatives were put and rejected: deploying to the existing Vercel
project needs a **13th** function file in `frontend/api` — over the Hobby cap B3
has only just cleared — and would put spike auth routes on the production
domain; a throwaway project is a new provider resource plus a Neon-reachable
deployment.

**Measured instead**: the handler is a pure `(Request) => Promise<Response>`,
called with a Web Request and no HTTP server at all (401 anonymous, 200 for the
right subject); it holds no per-instance state, so a handler built from scratch
accepts a session an earlier one issued; multiple `Set-Cookie` headers are
emitted separately rather than folded into one — the classic serverless-adapter
bug, which fails silently; the module imports without a database credential; and
`frontend/api` still holds exactly **12** function files.

**Therefore unproven**: cold-start cost, the platform's header handling, request
size and duration limits, region-to-Neon latency for the session read, whether
the cookie handling survives Vercel's edge layer, and TLS itself. **S17 closes
it, as an explicit exit criterion.**

## Two blocking findings for S17, both needing the ledger

### The runtime role cannot write the identity tables at all

`app_runtime` holds INSERT/UPDATE/DELETE on the business tables and on **none**
of `public.users`, `public.user_identities`, `public.team_members`. This is
table grants, not RLS, so no actor context unlocks it. Four attempted writes,
every one refused with SQLSTATE **42501**.

So **S17's invite, disable and role-change endpoints have no write path**. Two
shapes are available — `SECURITY DEFINER` admin functions owned by `app_owner`,
or a distinct privileged login role used only by admin endpoints — and choosing
between them is the owner's. The spike used `app_migration` + an explicit
`SET ROLE app_owner` as a stand-in to prove the path is *needed*; that is not a
proposal for production.

### Reading the mapping requires already knowing the answer

`user_identities_active_actor_select` requires `user_id = app.actor_id`. Two
ways out, both measured:

- **Propose-then-confirm, no schema change.** The account row carries a
  `canonicalUserId` set at invite time; the handler publishes it and RLS
  confirms the pairing. Works today, on live Neon. A stale or hostile proposal
  fails closed. Costs a duplicated field and a round trip. Unlike S12's bridge,
  the proposal is durable per account, so adding a person no longer needs an
  environment edit and a redeploy.
- **A `SECURITY DEFINER` resolver** —
  `spikes/s16-identity/sql/candidate_identity_resolver.sql`, applied to the
  ephemeral container **only**. One round trip, no proposal to keep in sync, and
  demonstrably **immune to a stale proposal**: the account that fails closed
  under propose-then-confirm resolves *correctly* here. Still fails closed for
  an inactive member and an unknown subject, and returns nothing for a wildcard,
  so it is not an enumeration primitive. It does let a caller holding a subject
  learn the canonical id — strictly more exposure than testing a pair — which is
  exactly why it is not the spike's call.

**Recommended:** the resolver, landed in the same ledger session as the write
path above, the candidate's own schema, and the already-approved **B4** roster
function. They are the same tables, the same ledger and one coherent identity
surface for a reviewer to judge.

## Known limits

1. **The Vercel smoke was not performed.** Owner decision, 2026-08-03. S17
   closes it. See the section above for exactly what is unproven.
2. **The cookie jar is not a browser.** It implements the RFC 6265 storage and
   sending rules the claims depend on, and nothing beyond them.
3. **No TLS.** The harness is plain HTTP on localhost, so `Secure` is measured
   through the jar's storage rule rather than over a real connection.
4. **No email was sent.** Reset tokens are captured in process. SMTP is an
   external gate the spec already recognises.
5. **The clean room needs Docker** and the `postgres:17-alpine` image already
   present; it refuses an implicit network pull, exactly as the S08 harnesses do.
   On a host without Docker the clean-room suite cannot run at all — it fails
   loudly rather than skipping.
6. **The live leg matches `provider = 'fixture'`**, because those are the rows
   that exist on Neon. Production would use `provider = 'better-auth'`.
7. **Only the candidate was measured.** The alternatives in F12 are assessed on
   fit, not benchmarked. A serious head-to-head with a hand-rolled
   implementation would have meant writing one, which is S17's work if the owner
   changes the candidate.
8. **The spike's own admin path is a stand-in.** `app_migration` +
   `SET ROLE app_owner` proves the write path is missing; it is not a proposal
   for how S17 should obtain one.
9. **The clean-room container publishes a trust-auth PostgreSQL on
   `127.0.0.1`** for the length of a run. Localhost-only and ephemeral, but it
   is a listening service on the developer's machine while the suite runs.

**S17 may build the production `IdentityProvider` on self-hosted Better Auth.**
It may **not** ship admin endpoints before the identity ledger session lands,
and it may not start S18.

**Nothing was made stricter and nothing was relaxed.** All six conditions were
taken exactly as recommended. This is the first gate in the series where the
owner's decision matches the preparing session's recommendation without
amendment — G1 and G2 both differed on at least one item.

### The question behind the decision

The recommendation named one thing that would have reversed it: unwillingness to
carry a second user store at all, even a subordinate one in its own schema with
no grants in either direction. **The owner answered yes, that is acceptable.**
That closes F12's hand-rolled alternative — the only option the spike rated a
close call, and one that lost on authorship of the security-critical parts
rather than on features.

### C3 amends G2's sequencing — B4 is no longer its own session

G2 recorded the **B4** roster function as its own session, sequenced before
S13. It is now **folded into the identity ledger session** alongside the
identity write path, the `SECURITY DEFINER` resolver and the candidate's own
schema.

Nothing about its nature changes: it is still a ledger-applied schema change,
still reviewed as one, and still lands before S13. It simply shares a session
with three other changes to the same tables, so one reviewer sees one coherent
identity write surface instead of reviewing it twice.

**The B2 bounded tenant-data copy is not affected** and remains its own separate
session.

Resulting order: **`S17` → `[B2 data slice]` → `S13` → `S18`**, with the
identity ledger session immediately ahead of S17's admin endpoints.
