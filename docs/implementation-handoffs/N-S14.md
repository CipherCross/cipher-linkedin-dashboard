# N-S14 — the non-AI writes behind the data API

Twenty-one write actions now have a Neon branch behind one fail-closed flag, and
three of them stop being able to come apart. The headline is not the port,
though — it is that **the brief's framing needed four corrections, each measured
rather than reasoned**, and the largest one inverts what the session was for.

Follow-ups were named "the clearest win available in this session" on the
grounds that a state row and its event row are separate PostgREST calls. **They
are not.** All six follow-up actions already call one `SECURITY DEFINER`
function that takes an advisory lock, checks a revision optimistically, replays a
repeated `mutation_id` and writes both rows in one transaction. The real
atomicity wins were elsewhere: `set_stage`, `set_gender` and the conversation
import, each of which today reports its audit row failing as a **field inside a
200**.

A second measured surprise, from the mutation pass: swapping
`COALESCE(replied_at, $2)` for `COALESCE($2, replied_at)` left the whole suite
green. Nothing covered "a paste may fill a NULL milestone and may never change a
filled one", and `leads_keep_milestones` does not help — it blocks non-NULL →
NULL only. The argument order was the entire defence and it was untested. It is
tested now.

## The four corrections to the brief

### 1. Follow-ups were already atomic, locked and idempotent

`/api/pipeline`'s six follow-up actions all call `public.apply_follow_up_action`,
one `SECURITY DEFINER` function in baseline step `003`
(`003_functions_triggers_ai_guard.sql:97`). It takes `pg_advisory_xact_lock` on
the thread key, checks `p_expected_revision`, replays a repeated `p_mutation_id`
after comparing a `request_fingerprint`, and writes `conversation_follow_up_state`
and `follow_up_events` in one transaction. So all four of the spec's
stopping-condition words were already satisfied in SQL that travels with the
baseline, and what this session owed was **proof it still holds on Neon under
`app_runtime`** — delivered, four tests, below.

### 2. The real atomicity wins are elsewhere, and there are three of them

| action | the pair | how failure is reported today |
|---|---|---|
| `set_stage` | `leads.pipeline_stage` + `pipeline_events` | `event_error`, HTTP **200** |
| `assign` | `leads.assigned_to` + `pipeline_events` | `event_error`, HTTP **200** |
| `set_gender` | `leads` demographics + `lead_gender_reviews` | `review_error`, HTTP **200** |
| `conversation_import` | `messages` + `leads` milestones | `milestone_error`, HTTP **200** |

`assign` is roster-blocked, so three were available. `pipeline_events` is not a
log the dashboard displays — it is what "ever reached stage X" is
*reconstructed* from — so a missing row permanently lowers a funnel number with
nothing recording that it is missing.

### 3. `/api/review-digest` writes no database at all

Zero `db()`, `.from(` or `.rpc(` calls: it validates a payload and posts to
Slack. Out of scope because there is nothing to move.

### 4. `/api/import`'s Airtable actions write Airtable, not Postgres

`companyImport.ts` (555 lines) and `contactImport.ts` (611 lines) have zero
`db()` calls between them. Of `/api/import`'s ten actions only three touch the
database, all in `conversationImport.ts`. `_lib/savedSearch.ts` and `_lib/icp.ts`
are validators only; their apparent `db()` reference is a comment.

## The atomicity evidence

### The injected mid-transaction failure

Three tests swap **one** command in the *real* `buildApplicationRegistry()` for
one that issues `DO $$ BEGIN RAISE EXCEPTION … END $$`, then assert a **500** —
not a 200 with an error field — and read the paired row back to show it absent.
Injecting the failure is the honest way to test a rollback; the alternative is
contriving a value that violates a constraint, which tests the constraint.

| injected failure | asserted afterwards |
|---|---|
| `pipeline.appendStageEvent` | `pipeline_stage` still `first_contact`, `pipeline_stage_changed_at` still NULL, 0 `pipeline_events` |
| `pipeline.appendGenderReview` | `gender` still `male`, `demo_model` still `name-v1`, 0 `lead_gender_reviews` |
| `conversations.backfillMilestones` | 1 message (the fixture's), all three milestones still NULL |

The fake-store suite adds the shape assertion the live one cannot make cheaply:
the 500's body carries **no** `ok` key, **no** `event_error` key, and no driver
text.

### The measured cost of the design that buys it

Design call 1 chose two operations in one transaction over a single CTE
statement, trading a round trip for one allowlist entry per operation. Measured,
not asserted — `tests/pairedWriteLatency.neon.test.ts`, three runs of 15 against
the live pooled endpoint:

| | p50 | p90 |
|---|---|---|
| two operations in one transaction | **197–201 ms** | 252–285 ms |
| one CTE statement doing both writes | **156–159 ms** | 241–247 ms |

**≈41 ms, a factor of 1.26.** Both arms open a transaction, so `BEGIN` and the
`set_config` preamble are inside both and cancel out; the difference is one
client-server round trip. 41 ms is a human clicking a board once. The measurement
is a test that keeps running rather than a number in a document, precisely so the
trade can be re-taken if this ever becomes a fan-out.

### The lock the pairing still needed

`pipeline.leadPipelineFields` now reads **`FOR UPDATE`**. Reading it inside the
writing transaction was not enough: under READ COMMITTED two concurrent stage
moves both read the same previous stage, and although the second blocks on the
`UPDATE`'s row lock, by then it has already decided what its audit row says. The
lock moves to where the decision is taken, so the two `pipeline_events` rows
**chain** instead of forking.

The test overlaps the two moves deterministically — the first store's actor-name
read is swapped for one that sleeps *after* the pre-read has taken its lock — and
asserts a chain rather than a fixed order, because which call wins the lock is
legitimately undecided. Warming the second pool first was necessary: without it
the race is decided by whose TLS handshake finishes, and the test passed alone
and failed in a full run.

`leadDemographics` deliberately did **not** get the same treatment. `set_gender`
reads by lead id and updates by `(instance_id, profile_url)`, so locking the row
it read would leave a writer that read a *sibling* row of the same person
unblocked — a lock that looks like a fix and is not one. Known limit 2.

## Design calls, with the rejected alternative

1. **A pair of writes is two operations in one transaction, not one.** Rejected:
   a CTE chain doing both — one round trip, equally atomic, but two operations'
   SQL behind one allowlist entry. Cost now measured at 41 ms.
2. **Dedup stays in JavaScript.** Rejected: `lower(btrim(regexp_replace(…)))` in
   SQL. It would be a third definition in a different language, Postgres and JS
   disagree on `\s` and on non-ASCII `lower()`, and the failure mode is a doubled
   thread. `normalizeForDedup` is passed across as a function.
3. **The import takes `pg_advisory_xact_lock` on the thread key**, reusing
   `apply_follow_up_action`'s exact expression. A **genuine improvement over the
   Supabase path**, not a port: today two concurrent pastes both read the same
   "already there" set, and because a manual row's `sent_at` is the real message
   time while a synced row's is the LH2 action-run time, two pastes with
   different parsed instants are not identical under `messages_identity_key` and
   both survive. Two live tests.
4. **The milestone backfill is `COALESCE(column, $n)` per column** — argument
   order load-bearing, see the mutation pass. It agrees with
   `leads_keep_milestones` by construction: `COALESCE` cannot produce NULL from a
   non-NULL input.
5. **The audit row's actor name is read from Neon, keyed on
   `team_members.user_id`** (the canonical uuid), never on the colliding bigint.
   Rejected: reusing the Supabase principal's name, which would source a Neon
   write's audit trail from Supabase; and carrying the name in `ActorContext`,
   which would widen the one function that runs with no actor published.
6. **`setGender`'s SQLSTATE-42703 rolling-deploy fallback is dropped**, because
   the portable baseline has all four lifecycle columns in step `001` by
   construction — a branch that can never fire is a branch nothing tests.
7. **Authorization is `resolveRequestActor({ acceptLegacyBearer: true })`**, so
   the role comes from **Neon's** `team_members` rather than a Supabase read.
8. **Write semantics live in their own modules**, not appended to `pipeline.ts` /
   `conversations.ts`, whose headers are essays about read semantics.
9. **`NeonWriteDeps` is an injected argument, not an env var** (S17's stated
   reason). Every endpoint call site omits it.
10. **A partial-column UPDATE is `CASE WHEN $2::jsonb ? 'col' THEN … ELSE col
    END`.** Key *presence* is what distinguishes "leave it alone" from "clear
    it". Three alternatives lost: `COALESCE(new, col)` cannot clear a column
    (right for milestones precisely because that statement must never clear
    anything, wrong here because this one must); one statement per key subset is
    combinatorial; `jsonb_populate_record` resolves an absent key to NULL and so
    would blank every field a patch did not mention.
11. **Nineteen fixed statements replace two generic helpers.**
    `saveEntity(supa, table, bodyKey, …)` was generic over a **table-name
    string** — an allowlist entry whose relation is decided at run time
    authorizes every relation. The genericity moved to TypeScript, over a closed
    union of five entities. Adding a table now means adding operations *and* an
    entry, which is the review step the string parameter skipped.
12. **The driver classifies 23505 and 23503 into `DataStoreConstraintError`.**
    The second widening of the S03 contract, for the same reason as the first: a
    caller must distinguish an outcome from a failure without reading driver
    text. Rejected: `ON CONFLICT DO NOTHING` with a zero row count meaning
    "conflict", which cannot express an UPDATE's rename conflict and collides
    with the zero row count that already means "unknown id". **23514 is
    deliberately not classified** — every cap in `_lib/icp.ts` mirrors a `CHECK`,
    so a payload that reaches the database and fails one is a defect, and a
    defect must surface as a 500 rather than as a tidy 400 someone could leave in
    place. A test holds that line.
13. **The admin rule is re-checked against Neon's own `team_members`.**
    `/api/playbook`'s relations carry only an *active member* policy — admin is an
    application rule, not a database one — so a Neon write trusting the Supabase
    role would be authorized entirely by the provider it is leaving.

## Known limits

1. **No browser was run and no page was loaded.** The endpoint branches are
   covered by `tsc` and by the suites calling the same functions the endpoints
   call — not by the endpoints themselves. A test that drives
   `POST /api/pipeline` or `POST /api/playbook` end to end with the flag on does
   not exist.
2. **`set_gender` still has the concurrency exposure `set_stage` no longer has.**
   Two overrides of the same person, arriving through different lead rows, can
   both snapshot the same prediction into `lead_gender_reviews`. `FOR UPDATE` is
   the wrong instrument (see the atomicity section); the right one is an advisory
   lock on `(instance_id, profile_url)`, the same key the import uses. Small,
   wants its own concurrency test, deliberately not taken blind.
3. **`safeErrorLabel` now has four copies** — `api/activity-daily.ts`,
   `api/identity.ts`, `api/_lib/neonWrites.ts`, `api/_lib/neonLibraryWrites.ts`.
   A `_lib` module importing from a function file would invert the dependency and
   consolidating them touches files this session does not own. Recorded, not
   resolved.
4. **`neonSetHypothesisCampaigns` decides a 404 by reading driver text.** The
   baseline function raises `unknown hypothesis id` as a plain exception, which
   the driver wraps message-first; the Supabase path reads the same substring.
   It is restricted to a string *this application authored*, in a message that
   names no relation and no host. Removing it means the function has to signal
   the case structurally — a baseline change, therefore a ledger step, therefore
   not this session.
5. **The `s14-lib` fixture is scoped by a name prefix, not by a tenant column.**
   `icps`, `hypotheses` and `saved_searches` carry no `instance_id`, so cleanup
   deletes rows whose name starts with `s14-lib`. A human row on the shared
   project named that way would be deleted by a test run. The prefix is
   deliberately ugly for that reason.
6. **Both write fixtures commit.** `afterAll` drops and `beforeEach` resets, so a
   hard kill can leave rows; the next run cleans them. The playbook singleton is
   the one row with no scope to delete by, so its test restores the previous
   content explicitly.
7. **Carried forward untouched:** N-S13-consolidation's Known limit 3 (the RLS
   plan leaves ~2.6× on the table), `fetchAllPipelineEvents` still returning its
   accumulator on a mid-walk error, the `rangedCampaigns` / `campaign_metrics`
   `last_activity_at` disagreement, `public.team_roster()` having no
   `auth_user_id`, C5 and the three Vercel identity env vars from S17, and the
   eleven read operations with no caller.
