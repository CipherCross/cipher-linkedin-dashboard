## The four open design calls, decided

### 1. Environment variable names — declare the new contract *and* keep writing the old ones

Chosen: **(a) + (c)**, matching the stated preference.

`ops/src/providers/hosting-tenant.ts` defines
`CANONICAL_TENANT_ENVIRONMENT` (contract `hosting.environment.v1`). The binding
surface belongs to the hosting port: binding environment values is one of the
seven capabilities, and a provider-neutral port cannot own names that spell a
specific data vendor. `buildTenantEnvironmentBindings()` emits every canonical
name **and** its legacy name, with the same value class and the same source, so
a deployment produced through this contract still satisfies every consumer that
has not been ported yet. The transition column disappears when `frontend/` and
`sync-agent/` stop reading it — S13–S15 and S21–S23, not here.

| Old name (still written) | New canonical name | Value class | Source kind |
|---|---|---|---|
| `VITE_SUPABASE_URL` | `PUBLIC_DATA_API_URL` | `public_build` | `derived_from_plan` → `resources.data_api_url` |
| `VITE_SUPABASE_ANON_KEY` | `PUBLIC_DATA_API_KEY` | `public_build` | `secret_label` → `data.public_key` |
| `SUPABASE_URL` | `DATA_API_URL` | `server_public` | `derived_from_plan` → `resources.data_api_url` |
| `SUPABASE_ANON_KEY` | `DATA_API_KEY` | `server_public` | `secret_label` → `data.public_key` |
| `SUPABASE_SERVICE_ROLE_KEY` | `DATA_API_ADMIN_KEY` | `server_secret` | `secret_label` → `data.admin_key` |
| `CRON_SECRET` | `SCHEDULE_INVOKE_SECRET` | `server_secret` | `generated_secret` → `tenant.schedule_invoke_secret` |
| `NOTIFY_SECRET` | `INGEST_INVOKE_SECRET` | `server_secret` | `generated_secret` → `tenant.ingest_invoke_secret` |

| `DASHBOARD_URL` | `APP_BASE_URL` | `server_public` | `derived_from_plan` → `domain.hostname` |

That is exactly the nine keys of the retired `PRODUCTION_ENV_KEYS`, so nothing
that runs today loses a value. The mapping is **data**

and source as its replacement.

`DATABASE_URL` is deliberately **absent**. S11 owns the Neon driver and is
blocked on G1; declaring a binding whose source nothing can resolve would make
the plan promise a value the apply step could not produce. S11 adds it to the
same contract.

No secret value enters a plan or a result. The generator IDs map onto the key
store's existing tenant secret names (`cron.secret`, `notify.secret`,
`mcp.secret`), so the reviewed secret catalog did not grow and no stored value
was orphaned.

### 3. The test seam — a narrow, adapter-private vendor transport

Chosen: **a narrow adapter-private client interface injected into
`createP4CSdkPorts`, defaulting to the real SDK**, as preferred.

`HostingVendorClient` (in `ops/src/providers/hosting-vercel.ts`) has fourteen
members, each a *named hosting operation* with a typed, provider-neutral
payload: `describeCapabilities`, `findTarget`, `createTarget`,
`putEnvironmentValues`, `createRelease`, `readReleaseSchedules`, `findDomain`,
`attachDomain`, `activateRelease`, `activeReleaseId`, `runRuntimeChecks`.

Why this does not widen the boundary:

- there is no `request(url, body)`, no header map, no method parameter and no
  passthrough — nothing arbitrary can be sent through it, which is the property
  `operations-contract-v1.md` requires;
- it carries no SDK type, so `@vercel/sdk` stays inside `p4c-sdk.ts`;
- the seam is *narrower* than what it replaced: the previous
  `P4CVercelSdkPort` reached the SDK directly from a port implementation.

`createP4CSdkPorts` takes an optional `{ hostingClient, hostingResolver }`. Both
default to the reviewed SDK-backed implementations. The test supplies an
in-memory client that deliberately hands back vendor-shaped IDs
(`prj_…`, `dpl_…`) so anything that leaked one is visible in a canonical result.

## How each capability is realised, and what the adapter had to do that the fake did not

`VercelHostingAdapter` in `ops/src/providers/hosting-vercel.ts`.

| # | Capability | What the adapter does | Beyond the fake |
|---|---|---|---|
| 1 | `tenant_deployment` | `findTarget` by deterministic name; adopt on ownership match, otherwise `createTarget` | Rejects a provider that created the target with automatic promotion or non-isolated previews enabled — the fake cannot disobey its own request |
| 2 | `environment_binding` | Resolves every declared source, writes the values to the provider, drops them | Marks `server_secret` values for encrypted provider storage and registers each with the `Redactor` before any provider call can echo it |
| 3 | `pinned_build` | `createRelease` at the pinned revision | Verifies the provider built the revision it was asked for and reached a verified state; reports the provider's **observed** artifact digest rather than a digest of its own inputs |
| 4 | `domain_assignment` | `findDomain`, else `attachDomain` | Refuses a hostname already attached to a different target |
| 5 | `schedule_registration` | Same digest/duplicate checks as the fake, then reads the release's own routing manifest back | **Reads `frontend/vercel.json` off the pinned revision and refuses to claim a registration the artifact does not carry.** On a file-routing provider the schedule set is baked into the build, so this is the only honest way to register it |
| 6 | `release_rollout` | `activateRelease`, with an in-adapter rollout ledger | Nothing extra; the constraints are re-implemented rather than shared (see below) |
| 7 | `deployment_verification` | Cross-checks the provider's active release against the expected one and runs the four runtime checks | `runtime.reachable` is a real observation (`activeReleaseId` equals the expected release), not a local flag |

`inspect` maps `describeCapabilities()` onto the canonical capability questions.

**Handles are canonically derived, never vendor-issued.** `htgt_…` is
`sha256(deterministicName)[:20]`, `hrel_…` hashes the canonical release key
(target, revision, recipe, manifest digest, public value names), `hroll_…` hashes
target/kind/sequence. This is not cosmetic: it is what lets an interrupted apply
reconcile by deterministic name and ownership marker, and it is why the adapter
and the fake produce byte-equal canonical results for the same plan. The provider
resource IDs live in a private map and never leave the module.

**The rollback constraints are re-implemented, not shared.** `hosting-fake.ts` is
S09's and was not modified, and its guards are private. The adapter implements
the same four rules independently, and the parity suite asserts both reject each
case identically — two independent implementations agreeing is stronger evidence
than one shared helper.

## Parity evidence, capability by capability

`ops/test/hosting-parity.test.ts`, 19 tests. A single `driveCapabilities()`
sequence is run through both providers and the results compared.

| Capability | Assertion |
|---|---|
| pinned build | `assert.deepEqual(withoutArtifactDigest(adapter.release), withoutArtifactDigest(fake.release))`, plus `revisionId === REVISION_A`, `revisionPinned === true`, `buildRecipeId`, and `publicValueNames` deep-equal to the canonical + legacy public set |
| environment binding | `assert.deepEqual(adapter.binding, fake.binding)` — full equality including `bindingDigest`; binding names deep-equal the canonical binding list |
| domain assignment | `assert.deepEqual(adapter.domain, fake.domain)`, plus `certificateMode === "provider_managed"` and `ownershipMarkerDigest === OWNERSHIP.digest` |
| schedules | `assert.deepEqual(adapter.schedules, fake.schedules)`, and separately against the parsed manifest (below) |
| deployment target | `assert.deepEqual(adapter.target, fake.target)` |
| promote / rollback | `assert.deepEqual` on both, plus `rolloutKind` `promote`/`rollback`, `reasonCode` `null`/`verification_failed`, monotonic `rolloutSequence`, and `previousReleaseHandle` |
| verification | `assert.deepEqual(withoutArtifactDigest(...))` on the whole report, plus explicit `runtime` / `schedules` / `domain` / `build` field assertions |

**One field is compared by shape rather than value, deliberately:**
`artifactDigest`. It is the one field a provider genuinely *observes* rather than
derives from canonical inputs — the fake hashes its own release key, the adapter
reports what the provider built. Both are asserted to match
`/^sha256:[0-9a-f]{64}$/`. Forcing them equal would have meant either the adapter
faking a digest or the test rigging the vendor to return the fake's — neither
would be evidence. This is the only exception, and it is stated rather than
hidden.

## How the four schedules were proven equal across all three places

Three representations, never restated by hand:

1. `CANONICAL_TENANT_SCHEDULES` — the canonical set (S09);
2. `frontend/vercel.json` — **parsed** at test time by
   `parseReleaseScheduleManifest()`, which splits `"/api/briefing?kind=weekly"`
   into route `/api/briefing` plus parameter `{kind: "weekly"}` rather than
   treating the query as part of the route name;
3. what the adapter actually registers.

`the four schedules match the canonical set and the live routing manifest`
asserts the parsed manifest deep-equals the canonical set on the
(route, parameters, expression) triple, that both have exactly four entries, and
that comparison is order-independent.

**The assertion is proven able to fail.** `a divergence in any one of the four
schedules fails the assertion` mutates each of the four entries in two ways —
changing the cron expression, and adding a query parameter — and asserts
`notDeepEqual` for all eight mutations, plus a ninth case that drops a schedule
entirely. And `the adapter refuses to register schedules the pinned release does
not declare` feeds the adapter a drifted manifest and asserts
`registerSchedules` rejects.

`frontend/vercel.json` was **read only**. It was not edited, regenerated or
staged; `git diff --name-only main` lists no file under `frontend/`.

### No SDK type crosses the canonical boundary

Three independent mechanisms:

- **Structural walk** over every canonical result, the verification report and
  the registry rows: vendor-shaped keys (`vercel`, `teamId`, `projectId`,
  `targetId`, `deploymentId`, `releaseId`, `buildId`, `crons`) and vendor-shaped
  values (`vercel`, `team_…`, `prj_…`, `dpl_…`) both rejected, plus a prototype
  check that no grep can do — every object must have `Object.prototype` or
  `Array.prototype`, which an SDK type instance would not.
- **The in-memory vendor deliberately emits `prj_…` and `dpl_…` IDs.** The sweep
  therefore has something real to catch. It catches nothing.
- **Strict zod parsing.** `HOSTING_RESULT_SCHEMAS` are `strictObject`s, so an
  adapter returning an extra field fails closed at the boundary rather than
  reaching the registry. A test asserts their key sets equal
  `HOSTING_RESULT_SHAPES` in both directions, so the schema and the contract
  cannot drift apart; another feeds a deliberately leaky port a `projectId` and
  asserts rejection.

### Secret handling

## Known limits

1. **The adapter has never met the real provider.** The Vercel SDK calls in
   `VercelHostingVendorClient` are type-checked and structurally close to what
   `P4CVercelSdkPort` already did, but nothing in this session exercised them.
   `activeReleaseId` reads `project.targets.production.id` through an untyped
   accessor and is the least-proven call. First live contact is S25/S26 behind
   G1 and G4.
2. **The rollout ledger is per-process.** The adapter seeds rollout state in
   memory and derives `rolloutSequence` from it. Across a process restart the
   sequence restarts, so a resumed rollback would need the durable history the
   registry does not yet record. Rollback is `planned_only` in the canonical plan
   and the executor never calls it, so nothing depends on this today; durable
   rollout history belongs with S24's registry migration.
3. **Schedule registration rides on ordinal 9.** Adding a fourteenth ordinal
   would have changed the pinned onboarding plan digest, which is S24's event to
   declare. Registering schedules as part of building the release they belong to
   is defensible on S09's own reasoning, but it does mean ordinal 9 performs two
   effects. Both are idempotent and the resume matrix covers each separately.
4. **`artifactDigest` parity is by shape, not by value** — see above. It is the
   only field not compared by value.
5. **The runtime-profile and build-recipe IDs are still placeholders.**
   `web-node22-1x` and `spa-plus-http-handlers-v1` are constants in
   `hosting-tenant.ts`; the real values must come from the approved catalogs,
   which S24 defines.
6. **`DATABASE_URL` is not in the environment contract yet** — S11 adds it.
7. **The `no protected path changed` test depends on `git` and on `main`.** It
   skips when `git` is unavailable rather than failing, so it is corroborating
   evidence, not a hard gate. The command-line check is the primary one.
8. **S08's session-scope static assertion still fails for any ops-touching
   session.** A later session that owns `postgres/tests/` should narrow that
   check to the paths a given session does not own, rather than every session
   inheriting S08's ownership list.
9. **A real Vercel team ID remains in `p4c-runtime.ts`** — pre-existing, see
   above.
