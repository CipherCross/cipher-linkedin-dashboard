## The five design calls

### 1. Which slice — the daily-activity series, and why that one

**Decision: the per-day, per-event-type activity series over
`public.daily_activity` for one instance and one UTC date range, served by
`GET /api/activity-daily` and rendered by the existing `ActivityChart` on a new
`#/neon-activity` route.**

Four reasons, in order of how much they mattered:

1. **It has a genuine old/new counterpart.** `DataContext` already fetches
   `daily_activity` through PostgREST. The parity question is therefore "does the
   same view, read through two providers, produce the same numbers" — not "do two
   independently written aggregates agree", which would have been a much weaker
   claim.
2. **It is the only slice with the volume to test pagination honestly.**
   `events` is the sole relation on Neon carrying real row counts. Every other
   candidate would have needed a stub.
3. **Its UTC requirement is substantive.** `daily_activity` buckets days with
   `date_trunc('day', occurred_at)::date`, which resolves in the session's
   `TimeZone`. The day boundaries genuinely move if the session is not UTC, so
   the UTC coverage requirement tests something real.
4. **Its blast radius is zero.** `DashboardData.activity` is fetched today but
   read by no page — every page recomputes activity from `leadsToActivity(leads)`
   instead. And `ActivityChart` takes only `DailyActivity[]`. So the slice reuses
   real production UI without touching a single existing consumer.

Deliberately **not** the Dashboard/Overview page: it needs leads, campaigns,
messages, intents and follow-ups at once, which is S13's job and would have made
G2 a decision about a whole page rather than about one read.

### 2. How a browser user becomes a canonical Neon actor — propose, then confirm

**Decision: `frontend/api/_lib/neonActor.ts`, marked TEMPORARY in a banner
comment at the top of the file.** Three steps:

1. **`requireUser(req)`** verifies the Supabase Auth JWT and yields a
   trustworthy `sub`. Note it uses only the Supabase URL and **anon key** — the
   Neon path never touches `service_role` and never reads Supabase's
   `team_members`. That is a deliberate improvement, not an accident of the
   local environment: authority for the Neon path should come from Neon.
2. **A server-only map proposes** a canonical `users.id` for that `sub`, read
   from `NEON_ACTOR_BRIDGE` (JSON, `{"<sub>": "<canonical-uuid>"}`). It confers
   no privilege by itself.
3. **The database confirms it.** `identity.resolveSelf` runs with the proposed
   id published as `app.actor_id`. RLS returns a row only if that id is the
   canonical user for the presented `sub`, *and* the user is active, *and* they
   are an active team member. The **role comes back from `team_members`**, so
   privilege originates in the database rather than in the browser or the map.

**Why it is shaped this way rather than as a lookup.** `user_identities` is
readable by `app_runtime` only through `user_identities_active_actor_select`,
which requires `user_id = app.actor_id` — reading the mapping requires already
knowing the answer. The data plane holds no role that can read it unscoped:
`app_runtime` is `NOBYPASSRLS` by construction, and adding a `SECURITY DEFINER`
resolver would be a schema change, which is a finding for the owner and not
something S12 may apply (R5: the ledger is the only apply path).

**What exactly is temporary: step 2, the environment-held map. Nothing else.**
Steps 1 and 3 are the intended shape. A wrong, stale or hostile proposal cannot
escalate, because the policy compares `user_identities.user_id` against the
published actor and the presented subject in the same predicate — proven by a
test that maps a subject to a *different* real user and gets a 403.

**What S17 replaces.** S17 makes the canonical `users` / `user_identities` tables
the identity authority instead of Supabase Auth. Once the subject is issued
against Neon — or a ledger-applied `SECURITY DEFINER` resolver can read
`user_identities` unscoped — the proposal step disappears and this whole module
is deleted; the handler will resolve the actor from the token alone. Until then
this file is the only place a Supabase subject and a Neon actor id are allowed to
meet.

Two smaller temporary pieces, both named in code:

- `TENANT_ID = 'primary'`. The baseline has no `tenant_id` column and no policy
  scopes by one — the tenant boundary is the database itself. The contract needs
  a non-empty tenant id because it participates in cursor scoping. It is
  deliberately **not** derived from any provider resource identifier. S16
  replaces it.
- `NEON_ACTOR_BRIDGE_PROVIDER`, which lets the tests drive the deny matrix
  against the baseline's own `provider = 'fixture'` identity rows instead of
  minting Auth users on a live provider. Unset in any real deployment.

### 3. How parity is proven without tenant data on Neon

**Decision: compare the new SQL against the existing view's logic over one
shared fixture on Neon. I did not copy tenant data, and I did not seed
synthetic rows into the production Supabase project.**

Why not the other two options:

- **Copying a bounded slice of tenant data** would change the Neon project's
  status from "holds no tenant data, and none has ever been copied". That is an
  owner decision and explicitly not mine to take. It is recorded as G2 blocker
  **B2** with the decision left open.
- **Seeding one synthetic dataset into both sides** would mean writing fake
  `events` rows into the live Supabase project. `DataContext` fetches
  `daily_activity` for all instances, so the fake rows would appear in the real
  team's dashboard. Rejected as invasive.

**The method, in two legs.**

1. **Structural.** The `daily_activity` definition is semantically identical in
   `supabase/migrations/001_init.sql:92-99` and
   `postgres/tenant-baseline/v1/001_portable_business_baseline.sql:886-892` —
   same `date_trunc('day', occurred_at)::date`, same `count(*)`, same `GROUP BY`,
   both `security_invoker = true`. Parity of numbers therefore reduces to parity
   of the *range predicate* and the *session timezone*, which is what leg 2
   tests.
2. **Executable.** The new path's formulation (UTC instants converted to a
   half-open day range) was diffed **row for row** against the formulation the
   Supabase path actually uses — PostgREST's `.gte`/`.lte` compared directly
   against the `date` column — over the same fixture on the same database, across
   five windows including both single-day endpoints.

**The numbers.** 2,700 view rows over 4,800 `events` rows; 5 windows;
**0 row-level mismatches, 0 total mismatches**. Cross-checked: the sum of `cnt`
over the view equals `count(*)` over the underlying events, 4,800 = 4,800.

**What parity does *not* cover.** Stated plainly, because a parity claim that
quietly compares two different datasets is worse than none:

- **Production tenant numbers.** Neon holds no tenant data, so nothing here
  claims the live dashboard's figures match. This is the largest gap in the
  evidence and it is G2 blocker B2.
- **Any relation other than `daily_activity`.** The other reads `DataContext`
  performs are unproven.
- **The client recompute.** Every page today renders activity from
  `leadsToActivity(data.leads)`, not from the view, so the view is currently
  unconsumed and its agreement with the recompute was not measured.
- **Timezone parity with Supabase.** The Neon path pins `timezone = 'UTC'` per
  transaction; the Supabase path relies on that project's session default. Both
  are UTC today, but only one of them guarantees it.

### 4. Where the real operation registry lives

**Decision: `frontend/api/_lib/data/operations/`, one module per domain, composed
by `buildApplicationRegistry()` in its `index.ts`. The store lives at module
scope in `frontend/api/_lib/data/store.ts`.**

- The contract and diagnostics registries under `frontend/tests/support/` stay
  where they are. They exercise the adapter, not the product; they are fixtures.
- **The store is hoisted to module scope**, which was the single most
  load-bearing thing S11's handoff asked for: 158.9 ms warm versus 578.8 ms with
  the store constructed per call. It is constructed **lazily**, on first use, not
  at import — so importing a handler needs no credential and the API surface
  stays importable by a type-check or a test that never touches a database.
  Asserted: `dataStoreExists()` is false before the first request, true after,
  and `getDataStore() === getDataStore()`.
- The pool ceiling is **2**. Many warm function instances each hold their own
  pool and share one Neon connection budget, so a large per-instance `max` is
  how a serverless deployment exhausts a database.
- `statementTimeoutMs` is **8 s**, deliberately under the handler's
  `maxDuration = 10`, so a hung query is aborted by the database with SQLSTATE
  57014 — which the driver turns into a `DataStoreTransactionError` — rather than
  by the platform killing the function with no diagnosis.
- **S12 registers no command.** The slice is read-only, so there is no write path
  to reach even by mistake; `registerCommand` is simply never called. Asserted.

### 5. Pagination for this slice — offset, examined and retained

**Decision: keep the driver's offset cursor for this slice. Not inherited —
measured.**

- **Measured:** a page at **offset 1000 cost 522 ms against 525 ms for the first
  page.** Offset is not the dominant term here, because the slice reads an
  *aggregate*: the `GROUP BY` over every matching event in the range has to run
  for any page, so keyset would remove the `OFFSET` skip without removing the
  cost that actually dominates.
- **Structurally correct:** the sort key `(day, instance_id, event_type)` is a
  total order over the aggregate, so offset paging cannot duplicate or skip.
  Asserted over 2,700 rows at two different page sizes, which returned identical
  rows.
- **When keyset becomes required:** S13's inbound-messages read. That one is over
  a base table rather than an aggregate, is far larger than 2,700 rows, and has a
  natural indexed key `(sent_at, id)`, so O(offset) would be paid for nothing.
  The driver's cursor is offset-based generically, so adding keyset means
  extending `neon.ts` — a driver change that should be scoped as such rather than
  smuggled into a slice.

`frontend/api/` held exactly **12** function files, and

**This remains a constraint on S13** (G2 blocker B3): there is no slot budget for

endpoint** keyed by allowlisted operation name.

## The driver defect the first real slice exposed

`date` (OID **1082**) was not normalized. `pg` parses a bare `date` into a `Date`
at **local** midnight, so the calendar day `2026-01-01` read on this host arrived
as `2025-12-31T23:00:00.000Z` — a different day, shifted by an amount that
follows the host's DST rather than by a constant.

**Fix:** `neon.ts` now normalizes OID 1082 to the `YYYY-MM-DD` text PostgreSQL
sent. A calendar day is not an instant. The change is additive and per-pool,
alongside the existing 1184/1114 handling; S11's 33 contract tests stay green.

The slice's own SQL casts `day` to text and so would never have caught this,
which is exactly why the regression is asserted separately, through a store and
registry of its own. **Mutation-verified:** reverting the fix turns exactly that
test red.

This is the only change to S11's driver. No redesign: the transaction wrapper,
cursor mechanism, actor publication, SQLSTATE translation and principal
verification are untouched.

### A second finding, from code review: the driver's error messages name the database

Raised in review and then **measured**, because it would otherwise have been a
plausible-sounding guess. `toContractError` wraps a failure as
`` `${what}: ${originalMessage}` ``, and for a connection-level failure the
original message is raw driver text. Against a deliberately unresolvable host:

```
name/code : DataStoreTransactionError/TRANSACTION_INVALID
message   : Acquiring a database connection: getaddrinfo ENOTFOUND <host>
```

So `error.message` embeds the database hostname **even for a contract error**,
and this session's invariants forbid a provider hostname in any log line. The
first draft of this handler logged the whole error object; a second draft logged
`error.message`. **Both were unsafe.** The handler now logs only
`safeErrorLabel(error)` — the contract error's `name` and `code`, which are
adapter-owned constants — at both of its log sites.

Defended by four tests in `frontend/tests/activityDailyLogging.test.ts`, which
assert the hazard (the message *does* contain the host) alongside the guarantee
(the label does not), with no database and no network. **Mutation-verified:**
returning `error.message` from `safeErrorLabel` turns two of them red.

**This generalises, and S13/S15 will hit it on every handler.** The safe rule is
that a `DataStoreContractError`'s `code` and `name` are loggable and its
`message` is not. A tidier long-term fix would be for the driver to keep the
provider text on `cause` and out of `message`, but that is a driver change and
S12 declined to make one beyond the date fix.

## Required coverage

### Pagination past 1000 rows, through the real handler

The fixture seeds 900 consecutive UTC days × 3 event types → **2,700**
`daily_activity` rows over **4,800** `events` rows, sized so a full walk needs
**three** pages and the cursor has to chain **twice** (one page over the cap
would not prove chaining). Counts per day vary 1–3 rather than being constant, so
a bug that dropped or duplicated rows changes the totals instead of cancelling
out.

| assertion | result |
|---|---|
| page sizes at `limit=1000` | `[1000, 1000, 700]` |
| pages at `limit=250` | 11, returning **identical rows** |
| distinct `(day, event_type)` keys | 2,700 — no duplicates, no gaps |
| ordering | ascending, verified against a sorted copy |
| `limit=1001` | refused, 400 |
| cursor replayed against a different range | refused, 400 |

### UTC

- **Day assignment.** Every one of 2,700 buckets carries exactly the count the
  fixture wrote — which holds only if the deliberately seeded boundary instants
  `00:00:00.000Z`, `23:59:59.000Z` and `23:00:00.000Z` all land on the same UTC
  calendar day.
- **Agreement with `leads.ts`.** `dayRangeToUtcRange` is asserted against
  `presetRanges` and `weekStart` **directly**, not against a restatement of them.
  `leads.ts` uses an inclusive `[from, to]` day pair; the contract uses a
  half-open instant range; the exclusive end is exactly one day past the
  inclusive one, verified for every preset the client can produce. A UTC ISO week
  read through the handler returned exactly 7 days and 21 rows, with `weekStart`
  confirmed to be a Monday.
- **Timezone sensitivity demonstrated.** The same rows read on an `Asia/Tokyo`
  session bucket into different days than on a UTC session.

**One finding stated precisely, because it is easy to overclaim.** The baseline
pins no timezone. This Neon project's default session timezone is currently
**`GMT`**, so days come out UTC-correct even *without* the driver's preamble
today. The preamble's value is that the result stops depending on that default: a
server-side, pooler-side or provider change would otherwise silently shift every
day boundary in the dashboard, with no test to catch it. The test is named for
what it proves — that the view is timezone-sensitive — rather than for the
stronger claim.

### The auth deny matrix

| case | outcome | enforced by | JWT verification |
|---|---|---|---|
| no bearer token | **401** | handler | **real, unstubbed** |
| invalid / expired token | **401** | identity-provider verification | **real, unstubbed** |
| verified user, no canonical mapping | **403** | actor bridge, before any connection | stubbed subject |
| **inactive user** | **403** | **RLS** | stubbed subject |
| **proposal not matching the subject** | **403** | **RLS** | stubbed subject |
| active member / active admin | 200 | RLS permits | stubbed subject |
| malformed request (missing instance, `2026-3-1`, `2026-02-30`, inverted range) | 400 | handler, before the database | — |

**Two denials are enforced by RLS, not by the handler.** The inactive-user case
is the required one: `user_identities_active_actor_select` requires an active
`users` row and an active `team_members` row, so the confirming read returns zero
rows and the handler denies. Corroborated directly out of band — the same actor,
published the same way, sees **0** identity rows and **0** events, while an active
actor sees **1** and **4,800**.

The 403 rows stub only the JWT verification, because minting an Auth user for an
inactive-account test would have created a resource on a live provider. What they
exercise — the bridge and the RLS policies — is real, and the two 401 rows run
the real verification unstubbed.

## Measured latency, and where the store lives

Dev host → Neon Free, AWS `eu-central-1`, ~40 ms RTT. **These are not production
latency** — a Vercel function co-located with the project pays single-digit
milliseconds per round trip. What transfers is the ratio.

| path | p50 |
|---|---|
| full warm request through the handler (1,000 rows) | **525 ms** (min 518) |
| identity confirmation alone — the bridge | **196 ms** |
| activity page of 1,000 rows alone | **334 ms** |
| page at offset 1000 | **522 ms** (vs 525 for the first page) |

**The bridge is 37% of the request**, because it is a whole extra transaction —
its own `BEGIN READ ONLY`, preamble, query and `COMMIT`. That is the most
important number in this table for S13: if S13 resolves the actor independently
per read, 13 reads pay it 13 times. **Resolve the actor once per request and pass
the `ActorContext` down** (G2 blocker B5).

The store lives at module scope in `frontend/api/_lib/data/store.ts`, lazily
constructed, `max: 2`, 8 s statement timeout.

## Browser evidence

this host, and `vercel dev` requires logging in and linking a Vercel project —
which creates or re-parents a provider resource, and S12 must create nothing on
any provider.

**What was used instead**, and why it supports the same claim: a local harness

actor and reads the real Neon database. The harness is deliberately **not
committed** — it is dev scaffolding, not product — and is reproduced verbatim at
the end of this section so S13 can re-run it.

### The harness, verbatim

Run from `frontend/`:

```bash
set -a && . ~/.config/neon-s11-datastore.env && . ./.env && set +a
export NEON_ACTOR_BRIDGE='{"<your-auth-sub>":"<canonical-neon-user-uuid>"}'
export NEON_ACTOR_BRIDGE_PROVIDER=supabase   # or 'fixture' against baseline rows
npx tsx ./s12DevServer.mts                   # file contents below
```

The signed-in subject is displayed on the page whenever the bridge rejects it, so
an operator can read it off and configure the map — it is the viewer's own
identifier, shown to themselves, and it disappears with the bridge in S17. A
`user_identities` row for `(provider, provider_subject)` must exist on Neon for
the chosen provider; the baseline ships three under `provider = 'fixture'`
(`subject-one` → active member, `subject-two` → active admin, `subject-three` →
inactive), and inserting a `provider = 'supabase'` row requires the owner
credential because `app_runtime` holds no write grant on that table.

```ts
// s12DevServer.mts — local stand-in for `vercel dev`
import { createServer as createHttpServer } from 'node:http'
import { createServer as createViteServer } from 'vite'

const PORT = Number(process.env.PORT ?? 5199)
const vite = await createViteServer({
  server: { middlewareMode: true }, appType: 'spa', root: process.cwd(),
})
const handler = (await vite.ssrLoadModule('/api/activity-daily.ts')) as {
  GET: (req: Request) => Promise<Response>
}

createHttpServer((req, res) => {
  const url = req.url ?? '/'
  if (!url.startsWith('/api/')) return void vite.middlewares(req, res)
  void (async () => {
    const headers = new Headers()
    for (const [k, v] of Object.entries(req.headers)) {
      if (typeof v === 'string') headers.set(k, v)
      else if (Array.isArray(v)) headers.set(k, v.join(', '))
    }
    const response = await handler.GET(
      new Request(`http://localhost:${PORT}${url}`, {
        method: req.method ?? 'GET',
        headers,
      }),
    )
    const body = await response.text()
    const out: Record<string, string> = {}
    response.headers.forEach((value, key) => { out[key] = value })
    res.writeHead(response.status, out)
    res.end(body)
    console.log(`${req.method} ${url} -> ${response.status}`)
  })()
}).listen(PORT, () => console.log(`http://localhost:${PORT}/#/neon-activity`))
```

## The G2 recommendation

**Conditional go for building S13. Not yet a go for a production cutover of
dashboard reads.**

The data path is proven and the per-slice cost is low — a named operation plus a
`mapRow`, roughly 20 lines of SQL for two operations. The expensive parts of S12
were not the slice: they were the actor bridge, the registry placement and the
serverless-function budget, all of which are one-time and now done. The S03
contract needed no change and the driver needed one small, generic fix.

**It is not an unconditional go, because two of the six findings are not
engineering details:**

- **B2 — parity has no dataset.** Correctness of a migrated dashboard cannot
  currently be demonstrated *at all*, because there is no tenant data on Neon to
  compare against. S12's parity is a structural argument plus a synthetic
  fixture: honest, but not evidence about production numbers. Resolving it needs
  an owner decision — a bounded tenant-data copy, a production dual-read
  comparison, or acceptance that parity is checked at cutover.
- **B1 — the actor bridge cannot serve a team.** It maps only explicitly
  configured subjects, so every member would be hand-entered into an environment
  variable and adding a person breaks their reads until it is edited and
  redeployed. Fine for one slice; unworkable for the team. Needs S16–S18, or an
  explicit owner acceptance that it stays development-only while S13 is built
  behind a flag.

The other four: **B3** endpoint-per-slice does not fit the function budget
(resolved for now, constrains S13's shape); **B4** `team_members` is self-only
under RLS, so assignee/owner name joins return NULL for everyone but the caller
and serving a roster needs a baseline change — an owner decision; **B5** resolve
the actor once per request; **B6** `events` is upsert-deduped by
`events_identity_key`, so `daily_activity.cnt` counts distinct tuples rather than
occurrences — true on both providers, preserved rather than corrected because
correcting it would break parity.

Full evidence and the recommended sequencing are in
`docs/platform-ops/g2-datacontext-migration-go-no-go.json`.

## Known limits

1. **Parity covers no tenant data.** G2 blocker B2. The largest gap.
2. **The actor bridge is an environment-held map.** G2 blocker B1. Temporary,
   marked as such in a banner comment, and the thing most likely to leak into
   permanence if S13 builds on it without noticing.
3. **`team_members` is self-only under RLS**, so assignee and owner names are
   unreadable by the runtime role. G2 blocker B4; needs an owner decision because
   the fix is a baseline change.
4. **The function budget is full at 12.** S13 needs one dispatching endpoint.
5. **Offset pagination is retained** for this slice on measured grounds, but
   keyset is required before S13's inbound-messages read.
6. **Day-granular bounds only.** Because the series is aggregated per day, a
   mid-day boundary would be ambiguous, so the handler accepts only `YYYY-MM-DD`
   and expands to UTC midnight. Documented at `dayRangeToUtcRange`.
7. **`vercel dev` was not used** — the CLI is not installed and linking a project
   would create a provider resource. The browser evidence used a local harness
   that mounts the real handler module; see "Browser evidence".
8. **The slice's page is scaffolding.** `#/neon-activity` exists to make G2
   decidable on real evidence. It is not linked from the nav and should be
   removed when S13 migrates the real pages.
9. **The Neon suite mutates the shared project**, unchanged from S11: two
   concurrent runs would interfere, and `fileParallelism: false` protects a
   single runner rather than two developers.
10. **R2's dump/restore half is still open**, unchanged from S11 phase 0 and
    sequenced to S25 by owner decision. Nothing in S12 moved it.
