### What the diagnostic bought

`providerJson` read each failed response body only to discard it, so a
deterministic Vercel refusal reached the operator as a bare `400`. The bridge now

```

```

That named the defect in one attempt, after three attempts of guessing.

### Step 9's two real defects

- `POST /v13/deployments` carried **no project build settings**. Step 6 creates
  the project through the API, which leaves it without any, and Vercel then
  refuses the deployment outright. The settings now travel with the deployment as
  the approved `spa-plus-http-handlers-v1` recipe's own definition.
  **`rootDirectory` is `frontend`**, not the `null` the P4-C path used for this
  same application: that is where the app and `frontend/vercel.json` live, and
  that file declares exactly the four crons this step then waits for — its paths
  and expressions match `CANONICAL_TENANT_SCHEDULES` one for one. A null root
  would build the wrong tree and never register a schedule, so the step would
  have failed at the cron wait even once the build started.
- Every readiness wait gave up after **20 attempts at one second**. A real Vite
  build takes minutes, so a fresh build could essentially never be recorded — and
  each timeout reported `outcome_unknown`, quarantining the operation for a build
  that was merely still running. Running out of polling budget is not an unknown
  outcome: the deployment exists, its id is known, and it carries the build
  identity digest, so `#existingDeployment` adopts it once it is READY. All three
  waits (deployment readiness, cron activation, and step 10's promotion) now
  report `provider_readiness_blocked` — deterministic and retryable — and share
  one bounded budget. The budget stays bounded deliberately: a Workers request
  cannot be held open for minutes, so convergence comes from the adopt path
  across retries.

Both confirmed live: `missing_project_settings` is gone and the deployment is
accepted, and the step now fails as `provider_readiness_blocked` instead of
quarantining the operation.

### Where it stands — needs a look at the Vercel dashboard

Step 9 is `failed` at **attempt 9** with `provider_readiness_blocked`. Six
sequential attempts (~5 minutes of polling in total) never saw the deployment
reach READY with its crons registered.

Retries are **not** piling up builds while a build is in progress:
`#existingDeployment` adopts a candidate carrying the exact digest and waits on it
rather than starting another. But it `continue`s past `ERROR`/`CANCELED`/`BLOCKED`
candidates, so **if the build is failing, each retry starts a fresh one** — and
from the operator's side that is indistinguishable from a slow build, because both
surface as the same `provider_readiness_blocked`. Do not keep retrying blind.

Three possibilities, and the dashboard separates them instantly:

1. the build is genuinely still queued or slow — retry and it converges;
2. **the build is failing** (`npm run build` is `tsc -b && vite build` at SHA
   `b2c287af`, with `rootDirectory: frontend`) — then the fix is in the app or the
   build settings, and every retry has been starting another doomed build;
3. the build succeeds but the **crons never register** — then
   `#waitForProjectCrons` is what blocks, and the cron record or the Hobby plan's
   cron support is the issue.

The Worker's own `provider_readiness_blocked` messages already distinguish (1)/(3)
— "Vercel deployment is still building" vs "Vercel crons are not activated yet" —
but the bridge forwards only codes, not messages, so they do not reach the
operator. Forwarding a bounded reason token for readiness would settle this class
without a dashboard, and is the obvious next diagnostic if the dashboard is
inconclusive.

### The exact cause

`applyPinnedPortablePostgres` asked whether the migration ledger already
existed with:

```sql
SELECT to_regclass('app_ledger.applied_migration') IS NOT NULL AS present
```

run as `app_migration` and outside any `SET ROLE`. Resolving a
schema-qualified name requires USAGE on the schema. `000_migration_ledger.sql`
ends by revoking everything on `app_ledger` from `PUBLIC`, leaving it owned by
`app_owner` with ACL `{app_owner=UC/app_owner}` and no USAGE for anyone else,
and `app_migration` is `NOINHERIT`.

So the probe answered NULL — correctly, `present = false` — on the **first**
apply, when the schema did not exist yet, and raised
`42501 permission denied for schema app_ledger` on **every apply afterwards**.
`databaseFailure` maps any 5-character SQLSTATE to `provider_error`, the bridge
answers `provider_error` with HTTP 409, and the client read that 409 as
`outcome_unknown`.

could never adopt a baseline it had itself applied. It matches the observed
history exactly — `op_e893a0d8…` passed step 3 against a fresh project and

### The fixes

Two commits, both local:

- `cca8cf8` — **the bridge 409 misclassification.** The bridge derives its HTTP
  status *from* a deterministic `OpsError` code, so `provider_error` and
  `provider_readiness_blocked` both leave as 409, one of the statuses

  the body's `code` is now authoritative, restricted to a closed set of codes
