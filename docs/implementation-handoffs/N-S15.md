## What was built

### The second principal

- `frontend/api/_lib/data/aiStore.ts` — a second lazy module-scope
  `NeonDataStore` beside `store.ts`, resolving `NEON_AI_DATABASE_URL` through
  `neonConfig.ts`'s `VITE_`-refusing reader, with its own registry and a 12 s
  transaction timeout (a margin over the guard's own 10 s cap, so the guard's
  refusal wins the timeout race). `buildAiStoreConfig(env)` is exported as a
  value so the two properties whose silent loss would run the AI path as
  `app_runtime` — the credential env name and the `SET LOCAL ROLE` — are
  unit-asserted.
- **Unconditional `SET LOCAL ROLE app_system`**, implemented as the driver's
  new `localRole` preamble (`neon.ts`): correct when connected as `app_system`
  directly (production) and as a member with `SET TRUE` (test fixture),
  transaction-scoped, issued before the timeout/timezone/actor preamble.
- **`SYSTEM_ACTOR`** — `kind: 'system'`, the nil uuid. It matches the strict
  uuid regex the policies apply and then fails the active-user `EXISTS`
  behind it, so every actor-scoped policy denies it. Step 005's `users`
  inserts are the only user creator and use `gen_random_uuid()`, so the nil
  uuid is unassignable. It is published for the contract and the audit trail,
  not as a key to anything.
- `frontend/api/_lib/data/operations/ai.ts` — the AI registry. One generic
  operation, `ai.executeSql` (arbitrary SQL as a **bound parameter**; the
  allowlist argument is the grant graph, see the file's header), plus one
  entry per fixed query the application authors — ten in total, the latest
  being `instancesList`, which absorbed `anomalies.ts`'s last direct table
  read.

### One flag moves the whole layer

`NEON_AI_PATH_DEFAULT` (`aiPath.ts`), shaped exactly like
`deploymentWritePath`: only the string `neon` enables it. Reads and writes
move together — a briefing cannot investigate Neon while recording its job
state in Supabase. The flag governs per invocation, once, invisibly to the
browser.

### The endpoint split, by actor

| endpoint | auth | human actor | on Neon when flagged |
|---|---|---|---|
| `coach.ts` POST | `guardMember` | yes | **moved** — `CoachData` seam, member suffices |
| `classify.ts` POST (batch, `demographics`, `reclassify`) | `guardAdmin` | yes | **moved** — admin re-checked against Neon's `team_members` |
| `briefing.ts` POST | `guardAdmin` | yes | **moved** — the whole job machine, via the `BriefingData` seam |
| `chat.ts` `save_search` tool | `guardMember` | yes | **moved** — `buildTools({ req })` → S14's `neonSaveEntity` |
| `classify.ts` GET, `briefing.ts` GET | `CRON_SECRET` | no | **blocked** — stay on Supabase, declared |
| `notify-replies.ts` | `CRON_SECRET`/`NOTIFY_SECRET` | never | **blocked** — declared in its header |
| `mcp.ts` `save_search` | `MCP_SECRET` | never | **blocked** — answers with an explanatory refusal when flagged |

The two seams follow the `coach.ts` pattern: everything above data access —
prompts, model calls, marker math, ref-validation, response bodies — is
shared; only the `CoachData` / `BriefingData` implementations differ. The
briefing machine's optimistic predicates (`WHERE version = $n`) moved into
the operations' SQL (`briefingWrites.ts`), so a claim that forgot its version
check is an operation nobody registered, not a runtime accident. The
demographics phase reproduces migration 048's fair batch as one statement and
drops the legacy ladder — the baseline carries the v2 columns by
construction.

Guard reads (`executeSql` / `executeNamedSql` in `core.ts`) route through the
AI store when flagged; `SCHEMA_DOC` was corrected against the portable
baseline (header, the `instances`/`team_members` column allowlists,
`photo_path`, five new tables) with the funnel-cohort reasoning preserved
verbatim.
