# N-S21 — the machine ingest path: a credential per notebook, a batch that is idempotent, and a write surface the database scopes

S21's row in the spec is `Tenant/machine-scoped /api/agent/ingest,
credential/revoke/replay`, graded on three properties: **a repeated payload is
idempotent**, **a wrong-tenant or revoked credential is denied**, and **a partial
write rolls back**. All three are implemented, and all three are proved against
the live Neon project rather than only against a fake.

This is the first slice of the chain whose central artifact is a *credential*.
Everything before it authenticated either a human session or the deployment
itself. The sync agent authenticates as neither: it runs on notebooks nobody in
this project administers, and today it holds `service_role` — one shared key, in
a config file on every notebook, that bypasses every row policy, cannot be scoped
to one machine, cannot be rotated without touching all of them, and cannot be
revoked at all without revoking everyone. Every property below is a property that
key cannot have.

## The applies, stated precisely

Two steps were applied to the live tenant database this slice, both through the
runner as `app_migration`, both under the owner's explicit authorisation:

* **`009_machine_ingest_path.sql`** — the credential relation, the batch ledger,
  the machine actor gate, the write surface, and the three admin functions.
* **`010_machine_schema_usage.sql`** — one `GRANT USAGE ON SCHEMA public TO
  app_machine`, which 009 omitted.

Step 010 is worth understanding rather than skimming, because it is the shape of
mistake this instrument exists to make survivable. Step 009 granted `app_machine`
DML on nine relations, two sequences and two functions, and wrote eleven
policies — and gave it no USAGE on the schema they all live in. PostgreSQL checks schema USAGE *before* any
privilege on an object inside it, so every one of those grants was unreachable:
the first statement of the first ingest failed with `42501 permission denied for
schema public`.

The omission was invisible to review because the other principals never needed it
said out loud — `app_runtime` and `app_readonly` receive the grant in step 002 and
`app_system` in step 003, each as one line among many. `app_machine` was reserved
by the seven-role bootstrap with no grants at all, so it was the first role in the
chain to arrive at the schema boundary with nothing behind it.

**It was found by the live suite, the first time a transaction actually entered
`app_machine`.** No offline test could have found it: a fake has no schemas, so
the whole class of "the privilege is there and unreachable" is invisible to one.
This is the concrete answer to the standing question of what the live suite buys.

The correction is a **new step**, not an edit to 009, because 009 was already
applied: its SHA-256 sits in `app_ledger.applied_migration` and in the manifest,
`down_migrations.supported` is false by contract, and changing its bytes would put
every database that received it permanently at odds with the ledger. A correction
to an applied step is a new step — that is the whole shape of the instrument.

## Two defects the *second* live run found, and only the second

The slice's own live suite was reported green at 19/19 when it was written. That
number was the ingest file alone, run once. Running the **whole** `test:neon`
suite a second time produced three failures, and both causes are worth recording
because neither is the kind of thing a test count reveals.

### A test that asserted its own step was unapplied

`aiSystemWrites.neon.test.ts` § 7 was written by S15 to prove
`pipeline_auto_advance()` was **unreachable by every principal** — that was the
fact justifying step 008 as a written-but-unapplied artifact. S21 applied 008,
which granted `app_system` EXECUTE, so the assertion that made the section true
became the assertion that made it false.

Nothing caught it at apply time because the apply commit ran the *ingest* suite,
not the suite whose subject the step was. The lesson is narrow and reusable:
**applying a ledger step invalidates every test that asserted the step was not
applied**, and those tests are by construction in a different file from the one
the slice is about.

It is inverted rather than deleted — what is worth pinning now is that the grant
landed on **one** role. `app_ai_runner` still does not hold it, and `app_machine`
was added to the same assertion, because S21 is the slice that gave that role any
grant at all and a side-effecting definer function is exactly what it must never
reach.

The **direct call is no longer attempted.** It was a positive control while it
was guaranteed to be refused; now that `app_system` holds EXECUTE, issuing it
would run a real auto-advance over the tenant's pipeline — moving live leads and
writing live `pipeline_events`. S15's own comment warned about precisely this
(*"the test stops before running a real auto-advance"*), and the warning came
true. `has_function_privilege` is the whole of what step 008 changed, so
measuring it is measuring the step.

### An assertion that passes on an empty table and never again

Two counts in `agentIngest.neon.test.ts` were scoped by `idempotency_key` alone:

```sql
SELECT count(*) FROM public.agent_ingest_batch WHERE idempotency_key = $1  -- expected 1, got 3
```

The file carries a per-run suffix for instance ids and profile urls precisely so
runs cannot collide — but the idempotency keys are **fixed literals**. The unique
key is `(credential_id, idempotency_key)` and every run mints a fresh credential,
so every run adds a row under the same key, legitimately. And no role holds
`DELETE` on `agent_ingest_batch` by design, so the residue only grows.

The first run passed on an empty table. The second could not. The fix is one
predicate — `credential_id = $1::uuid AND idempotency_key = $2` — which is also
what the assertion always meant. The file's own header comment claimed every
assertion was scoped "to this run's credential *or* its idempotency key"; the
`or` was the bug, and the comment now says why.

**The generalisation for this project:** on a shared live project, an assertion
about a table nothing deletes from must be scoped to something this run created.
A run-scoped *instance id* is not enough when the row's identity is a different
column. Re-running a live suite twice is the cheapest way to find these, and it
is not something a green first run can tell you.

## The design calls

### 1. The token carries the credential id, and the database stores only a hash

The token is `lha.<credential uuid>.<32 random bytes, base64url>`. The database
stores a SHA-256 of the secret half and never the secret.

Carrying the id in the token rather than looking a credential up *by its secret*
buys two things that matter operationally. A request can be **logged by credential
id** — which is what an operator needs to answer "which notebook did this?" —
without the log line containing anything that authenticates. And the lookup is by
primary key with the hash as a second condition, so **the stored hash is never an
index a caller can probe**: presenting a secret alone is not a query this system
can answer.

The separator is a dot and not an underscore, and that is not cosmetic. Base64url's
alphabet is `[A-Za-z0-9_-]`. An underscore separator was written first and a test
issuing *real* secrets caught it within a minute — roughly three tokens in four
carry an underscore or a hyphen of their own, so the parse split into four parts
and refused a token this process had just minted. A dot cannot occur in either
half. The lesson generalises: a token-format test that uses a hand-written literal
instead of the real generator proves nothing about the format.

### 2. SHA-256, not a password KDF

The secret is 256 bits from `randomBytes`. There is no dictionary to run against
it and no human memory that shortened it, so an attacker holding the hash faces
2^256 candidates whether the function is fast or slow. What a slow KDF buys —
resistance to guessing a *low-entropy* input — is not a property this input lacks.
What does matter is that the comparison is constant-time (`timingSafeEqual`) and
that the secret is never stored, and both are true.

The database's own comparison is ordinary SQL equality. Step 009 section E states
why that is acceptable: what a timing side channel leaks there is the *hash*,
which the caller must already hold to be asking.

### 3. The published actor is the credential, not the notebook

`machineStore.ts` puts `agent_credential.id` in `app.actor_id`. Publishing the
*instance id* instead was possible and would have been wrong in a way worth
stating: revocation would then be a fact the **handler** checked once, at the
start of a request. With the credential published, step 009's policies re-derive
"exists, not revoked, not expired" on **every statement**, so a credential revoked
while a batch is in flight stops being able to write before that batch commits.

The live suite pins exactly that — `refuses a revoked credential mid-transaction,
not only at resolution`.

### 4. The gate also scopes, and step 007 needed no equivalent

`app_system`'s policies compare `app.actor_id` against the nil uuid, because there
is exactly one system principal. There are as many machines as there are
notebooks, so the machine gate is a **lookup**, and every business policy
additionally requires the row's instance to be the credential's instance. A
credential issued for `notebook-1` cannot write `notebook-2`'s leads even through
a handler bug.

Step 007 needs no equivalent because the system principal legitimately spans every
instance. This is the one place the machine path is strictly narrower than the
system path rather than parallel to it.

### 5. A third store, because a connection is one principal

`machineStore.ts` joins `store.ts` (`app_runtime`, active-human policies) and
`aiStore.ts` (`app_system`, nil-uuid gate). Three stores rather than a flag on one,
because these are three different sets of policies and a connection is one
principal. `SET LOCAL ROLE app_machine` is unconditional — a role may always `SET
ROLE` to itself, so the identical statement is correct for a direct `app_machine`
login and for the member login the live suite uses. Transaction-scoped, never the
session variant: see `neon-pooled-session-guc-leak`.

### 6. `resolveMachineActor` joins `resolveActor`, and the category did not widen

This is the second read that runs with **no actor published**. The rule is
unchanged rather than relaxed: an operation may be actorless only if *running it
is what establishes the actor*. Both resolvers now share one private transaction
in the driver — `BEGIN READ ONLY`, an explicitly published empty `app.actor_id`,
one allowlisted operation, one row or nothing — extracted when the second arrived
rather than copied, because two copies is two places for one of those properties
to be dropped.

The three input screens (uuid, 64 hex characters, non-blank tenant) run **before**
a connection is acquired. They are shape, not authorization: a malformed
credential id would reach `::uuid` and raise `22P02`, and a hash that is not 64
hex characters cannot be the SHA-256 of anything this code produced.

### 7. `POST /api/import?op=agent.ingest`, because there is no free slot

`frontend/api/` holds exactly 12 top-level files and the Vercel Hobby cap is 12.
S17 already had to fold `reclassify.ts` into `classify.ts` to make room for
`identity.ts`. A subdirectory would keep the count assertion in
`spikes/s16-identity/tests/serverlessShape.test.ts` green — its `readdirSync` is
non-recursive — while breaching the real cap, so that was not an option either.

Of the eleven existing files this one belongs on `import.ts`, and the reason is
what that file already is: **the shared ingest dispatcher**, whose other actions
are a pasted conversation and a CSV of contacts. An agent's batch is the same kind
of thing. The alternatives each lose a property: `activity-daily.ts` states
read-only end to end as an invariant, and `pipeline.ts` keys its audit rows on a
human actor's display name, which a machine has none of.

The `?op=` dispatch happens **before the body is read and before `guardAdmin`
runs**, so the human actions are untouched — same order, same guard, same error
text — and this operation's own authentication is the only one it ever meets.

### 8. Issue, revoke and list live on `/api/identity`; the split is by who authenticates

The three admin operations are `admin.agentCredentials`,
`admin.agentCredentialIssue` and `admin.agentCredentialRevoke`. They sit on
`identity.ts` because that file already owns every principal-shaped decision and
is the one dependency-injected endpoint. The ingest sits elsewhere because it
authenticates with a machine token and never meets a human session.

The plaintext token exists in exactly one HTTP response and nowhere else. Only its
SHA-256 reaches the database. There is no read-back operation, by construction.

### 9. The batch row is written last, and without `ON CONFLICT`

**Last**, so it can never describe writes that did not commit. **Without `ON
CONFLICT`**, so a concurrent duplicate raises a unique violation and rolls *this*
batch back, instead of committing its writes while claiming nothing happened.

The consequence is the property that makes the agent's retry safe: a failed batch
leaves **no trace at all**, so the retry is an ordinary first attempt against a
database that never saw the first one. The live suite pins both halves — `rolls
the whole batch back when a later statement fails` and `lets the same key succeed
after a rolled-back attempt`.

Replay detection is a lookup on `(credential, idempotency_key)` at the *start* of
the transaction. Found with the same payload digest is a replay and is answered
from the stored counts with **no write at all**; found with a different digest is
two different batches sharing a key, and is a 409.

### 10. Dependency injection, because the alternative is untested branches

`N-S20.md` known limit 3 recorded the cost of the other shape: request validation
inside a handler that resolves an actor first is reachable only through a
database, so it is checked by `tsc` and the live suite and by nothing that runs on
every commit.

Here the handler is built by `createAgentIngestHandler({store, tenantId})`, so
every branch — the 405, both 401s, the 503, the 413, the 400s, the 403, the 409s
and the 500 — is exercised offline against `FakeDataStore`. That limit is closed
for this endpoint. It remains open for the photo endpoint.

### 11. `APP_TENANT_ID` and `OBJECT_STORAGE_TENANT_ID` must **agree**, not one win

G0's shape gives every tenant its own database, so "which tenant is this?" is
already answered by the connection string. The redundant `tenant_id` is the check
rather than an oversight: a credential minted for another tenant, or a dump
restored into the wrong deployment, is refused by `agent_credential_resolve`
instead of being accepted because the row happened to be present in the database
it was asked about.

Two names exist because `OBJECT_STORAGE_TENANT_ID` came first (S20 needed a key
prefix before the schema had a tenant column) and `APP_TENANT_ID` is the name that
outlives the storage layer. Both are read, and when both are set they must be
**equal**. A precedence rule would have been shorter and would have hidden the one
configuration that is genuinely broken: objects filed under one tenant while
credentials are checked against another. That deployment signs URLs for keys
nobody writes and accepts credentials nobody issued, and neither failure looks
like a misconfiguration from outside.

### 12. `WWW-Authenticate` on every 401, because the caller is a program

A notebook that gets an opaque 401 retries forever. One that is told the scheme
has something to log. Small, and the sort of thing that is never added later.

### 13. A misconfigured deployment answers 503, not 401

If `NEON_MACHINE_DATABASE_URL` or the tenant id is absent the endpoint returns
503, not 401. The caller may hold a perfectly good credential, and telling it
"unauthorized" would send an operator looking at the wrong thing entirely.

### 14. The instance mismatch is a 403 here even though the database refuses it too

Step 009's policies scope every relation to the credential's instance, so a batch
naming another notebook writes zero rows regardless. The handler still checks,
because **the policy version of that failure is a batch that writes nothing and
looks exactly like a working sync of an empty notebook.** A 403 is a diagnosis.

Both are pinned: `refuses a write scoped to another notebook, by policy` and
`writes nothing for a credential whose leads name another notebook`.

### 15. No `DELETE`, anywhere, for anyone

A credential is revoked, never removed, because a removed credential takes its
batch history with it. `app_machine` receives no `DELETE` on any relation, and no
role receives raw DML on the credential table — the three admin functions are
granted to `app_runtime` alone and gate themselves on `public.is_app_admin()`,
exactly as step 004's write path does. A credential also cannot revoke or extend
itself; the live suite pins that too.

## Invariants confirmed

* **`SET LOCAL`, never the session variant.** The pooled endpoint reuses backends
  across clients; `neon-pooled-session-guc-leak` is what the session variant costs.
* **Actorless reads did not widen as a category.** Two members, one rule, one
  shared transaction.
* **The AI SQL guard is untouched and still `SELECT`-only.** The credential table
  is readable through it exactly as every other table is, and carries no secret
  material to read.
* **The ledger stayed append-only under pressure.** The first real temptation to
  edit an applied step arrived this slice and was declined.
* **The human import actions on `/api/import` are byte-identical.** Same order,
  same guard, same error text.

## Known limits

1. **`agent.py` is untouched.** Nothing calls this endpoint. The agent still
   writes to Supabase with `service_role`, so every property above is available
   and unused until S22 gives the agent the dual transport. That is the shape of
   a cutover slice and is wrong as a steady state.
2. **There is no UI for credentials.** Issue, revoke and list are API operations
   on `/api/identity` with no page behind them, so today minting a token means
   calling the endpoint by hand. The spec row does not ask for a page; it is
   named here so nobody assumes one exists.
3. **`009` and `010` are not yet in `PROTECTED_PATHS` or `IMMUTABLE_BASELINE`,**
   and this session could not put them there: the list is checked against the diff
   since the merge base, so a session's own new file would flag itself. **The next
   session must promote both**, with the step-count assertion at ten. This is the
   same one-session lag that 004 through 008 each had.
4. **No credential has ever been used by anything but a test.** Every live
   assertion runs against a credential the suite mints for itself in `beforeAll`.
   A real notebook has not authenticated, and the production login is not proved
   either: `app_machine` is `NOLOGIN` until
   `000_machine_ingest_role_bootstrap.sql` runs on the cluster, so the suite
   connects as a *member* of the role and relies on the driver's unconditional
   `SET LOCAL ROLE app_machine`. That makes the policies identical from the
   database's side and says nothing about the login.
5. **Expiry is enforced but never exercised in production time.** The live test
   for an expired credential sets the expiry in the past rather than waiting, so
   what is proved is the predicate, not the passage of time.
6. **The 500 path is offline-only.** A failure that is neither a constraint
   violation nor an `IngestRequestError` is turned into a 500 and logged by name;
   the live suite has no way to induce one, so that branch is proved against the
   fake alone.
7. **`MAX_INGEST_BYTES` is checked from `content-length`,** which a caller
   controls. A body that lies about its length is caught by the JSON parse and the
   per-field limits rather than by that check, so the header check is a courtesy
   to honest callers, not a defence.
8. **The live suite leaves credentials and batch rows behind, permanently.**
   No role holds `DELETE` on `agent_credential` or `agent_ingest_batch` — that is
   step 009's deliberate design, not an omission — so every `test:neon` run adds
   a fixture credential and a handful of batch rows to the live project that
   nothing will ever remove. The rows are inert and name notebooks that do not
   exist. Opening a delete path for a test would trade a real invariant for
   tidiness, so it stays; a future clean-up is an owner action against the
   database, not a code change.
9. **Everything the migration's own limits say still holds.** `NEON_READS_DEFAULT`
   is not flippable, `NEON_WRITES_DEFAULT` gates the S14 writes, and the next
   database decision is still a whole-cutover one.
