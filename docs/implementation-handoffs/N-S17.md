## The design calls, their alternatives, and why the losers lost

### 1. One dispatching endpoint over an operation vocabulary

**Chosen:** `/api/identity?op=<name>`, one function, an allowlist of ten
operations, four of which are forwarded to the candidate's own routes.

**Rejected: a prefix-forwarding catch-all.** Forwarding anything under the base
path would expose every route the candidate and its plugins register — including
routes a future dependency upgrade adds. The allowlist is the surface, and the
admin plugin's `create-user`, `ban-user`, `list-users` and impersonation routes
are deliberately not on it. Asserted by test.

**Why the op name is in the query string and not the body.** The candidate's
routes need their body delivered untouched. A dispatcher that parsed the body to
learn where to send it would have to reconstruct it — which is how a credential
ends up copied through a component that had no reason to hold it. The op is in
the URL; the body is forwarded verbatim, and a test asserts both that the body
arrives unmodified and that `op` does not reach the candidate.

**Rejected: calling `auth.api.*` server methods directly.** It would have given
full control of the HTTP shape, at the cost of bypassing the candidate's own
origin/CSRF middleware — the very middleware F3 measured seven refusals from.
Forwarding a rewritten `Request` keeps that middleware in the path, so
state-changing operations are origin-checked **twice**: by us, then by it.

### 2. The actor resolver needed a driver capability, and it is deliberately awkward

`identity_resolve_actor` must be callable *before* an actor exists — the ledger
handoff calls it "the ONE function in this artifact that is deliberately reachable
with no actor context". But `DataStore.query` requires a valid `ActorContext` and
publishes it as `app.actor_id`.

**Chosen:** a separate, single-member allowlist. `registerActorlessQuery` /
`lookupActorlessQuery`, a `resolveActor` member on the `DataStore` contract, and
its own `BEGIN READ ONLY` that publishes `app.actor_id` as the empty string.

**Rejected: a synthetic system actor.** Inventing
`{kind:'system', actorId:'<some uuid>'}` would have needed no driver change and
would have put a value identifying nobody into `app.actor_id`. Every RLS policy
in the baseline compares that setting against a `user_id`; a fabricated id is one
`GRANT` away from meaning something. The empty string matches nothing, by
construction.

Two properties stop this becoming a general escape hatch, and both are asserted:
the actorless allowlist has **exactly one** member, and the resolver is reachable
as neither a query nor a command — so no code holding an actor can route to it by
name, and no code lacking one can reach anything else.

`''` is published rather than left unset, because an unset `app.actor_id` and one
left over from a previous transaction on a pooled connection are
indistinguishable to a policy.

### 3. The cross-store invite: ledger step 005, and one refinement to it

**Owner decision: the ledger step**, with the consequence accepted that the live
project sits at 4/5 until the apply is authorised.

The brief described this route as "granting the identity tables' DML to
`app_owner` plus one `SECURITY DEFINER` function". The step grants **INSERT
only, on two tables** — not DML on four — because an invite inserts, and nothing
on this path updates or deletes store rows.

**A shape that does not work, measured rather than reasoned about.** The first
version used `SET LOCAL ROLE identity_store` inside the function and added **no
grant at all**, relying only on the `app_owner`→`identity_store` membership step
004 already created. That is strictly less privilege and it is wrong: inside a
`SECURITY DEFINER` function the role switch is authorized against the **session**
user, which on this path is `app_runtime`, and `app_runtime` is not a member of
`identity_store`. `SECURITY DEFINER` changes `current_user`, not `session_user`.
So the function holds the two INSERT privileges directly.

What step 005 does **not** do: no new role, no new credential, no control-plane
action, no `UPDATE` or `DELETE` on any identity table, no grant to `app_runtime`,
`app_readonly`, `app_machine`, `app_system` or `app_ai_runner`, and no hashing —
the hash arrives already computed, because inventing password handling in SQL is
exactly the authorship this project declined when it accepted a reviewed library.

**The endpoint offers only the atomic invite.** Step 004's
`identity_admin_invite_member` writes the canonical half alone, which produces a
member who is on the roster and cannot sign in — the half-person F8 argues
against. Until step 005 is applied, `admin.invite` returns an explicit **503
`LEDGER_STEP_PENDING`** rather than half-creating people.

### 4. `B1`: the bridge is gone, and the S12 page still works

The brief says to delete `neonActor.ts`. Doing only that would have broken
`src/pages/NeonActivity.tsx`, which calls `/api/activity-daily` with a Supabase
bearer token — and S18, which rewires the browser, is out of scope. That would
have violated "the existing dashboard keeps working".

**The way through:** the bridge's *shape* — verify a subject, then let the
database decide who that is — was always right; only the environment-held
proposal map in the middle was temporary. `identity_resolve_actor` resolves **any**
provider, so the Supabase JWT now yields a subject that the database resolves
under `provider = 'supabase'`. No map, no proposal, no redeploy per team member.

So `resolveRequestActor` accepts two authenticators and has one resolver: the
identity session cookie (production), and the Supabase bearer (**transitional**,
deleted by S18). The bearer is no longer a mapping authority — it yields a subject
and nothing more.

`activity-daily.ts` passes **no** identity provider, so it reads no cookie and
needs no identity credential. That is what stops the bridge removal from becoming
a deployment prerequisite.

`NEON_ACTOR_BRIDGE` and `NEON_ACTOR_BRIDGE_PROVIDER` are both gone. The test seam
that needed the latter is now an injected argument
(`createActivityDailyHandler({ legacyProviderName })`), because an environment
variable that exists only for tests is indistinguishable at a glance from one a
deployment is supposed to set.

### Why `expiresIn` is 12 hours

F9 measured that the session token does **not** rotate while a session slides
forward, so the window is how long a captured cookie stays useful once it stops
being refreshed. Twelve hours means a cookie stolen from a closed laptop is dead
by morning, while an SDR working a normal day signs in once. What it does not
bound: a cookie an attacker *actively uses* slides forward like any other. That is
F9's accepted limit and the answer to it is revocation — immediate, and available
in two places — not a shorter `expiresIn`.

### Why pruning is not a Vercel cron

C1 forbids any S17 endpoint changing state on a GET, and Vercel's cron scheduler
issues **only** GET. Rather than carve an exception into the one rule whose whole
purpose is that there are no exceptions, the sweep is triggered from inside the
request path, at most once per six hours per instance, and additionally exposed as
a deliberate POST. The trade, stated plainly: a fleet of cold starts sweeps more
often than one warm instance would, and an instance that never serves a request
never sweeps. Neither is a correctness problem — an expired row is never honoured.

## What every endpoint exposes, and what it does not

| Operation | Method | Who | Reaches |
|---|---|---|---|
| `session.signIn` | POST | anyone | candidate `/sign-in/email` |
| `session.signOut` | POST | anyone | candidate `/sign-out` |
| `password.requestReset` | POST | anyone | candidate `/forget-password` |
| `password.completeReset` | POST | anyone | candidate `/reset-password` |
| `session.current` | GET | any signed-in caller | the resolver, then nothing |
| `team.roster` | GET | any active member | `public.team_roster()` |
| `admin.invite` | POST | admin | `identity_admin_invite_member_atomic` (step 005) |
| `admin.setActive` | POST | admin | `identity_admin_set_member_active` + session revocation |
| `admin.setRole` | POST | admin | `identity_admin_set_member_role` |
| `maintenance.pruneSessions` | POST | admin or `CRON_SECRET` | expired rows only |

**Not exposed:** any candidate admin-plugin route; member deletion (disable is the
sanctioned end state and `public.users` rows are never removed); any other
person's session or subject; any password material in any response. `admin.invite`
generates a random initial passphrase that is never returned and never logged —
nobody, including the admin who ran the invite, ever knows it; the invited person
reaches their account through the reset flow.

`session.current` returns exactly `{subject, provider, actor:{actorId, role}}` —
asserted by key set, and asserted not to contain the caller's email. Its three
outcomes are distinct, which S18 must render: **401** not signed in, **403**
signed in but not an active member, **200**. The 403 is a real reachable state
(F5), and collapsing it into 401 would bounce a deactivated member to a sign-in
that succeeds and changes nothing.

`identity_admin_set_member_role` is used rather than the baseline's older
`admin_update_team_member`, which is also `SECURITY DEFINER` and also granted to
`app_runtime` but performs **no authorization of its own**.

## The denials that actually bite

The requirement was that an ordinary member be refused every admin endpoint, and
that it be proved by a test rather than by a grant. Both stores prove it
independently.

**In the endpoint suite.** The fake commands standing in for the SQL functions
deliberately do **not** re-check the actor's role. So the assertion
`expect(h.executed).toEqual([])` is what fails if the endpoint ever stops
refusing — the denial is proved by the database receiving nothing, not by a
status code alone. Covered for a member (403), an unauthenticated caller (401),
and a deactivated caller whose session is still valid (403).

**In the database.** `portable_identity_atomic_invite_assertions.sql` runs as
**`app_runtime`**, the real request principal, and the non-admin denial is its
first case. Its `when others` branch re-raises rather than passing, so a `22023`
would fail the test: the gate must fire *before* argument validation, and the
ordering is what that proves.

Three bugs in my own test file, each of which taught something and each recorded
in the file rather than quietly fixed:

1. `app_runtime` **cannot look up the fixture actors** — reading
   `user_identities` requires already being the actor. The ids are now constants,
   and the preconditions are confirmed through `is_app_admin()` disagreeing
   between the two actors, so a missing fixture cannot make the denial test pass
   for the wrong reason.
2. `app_runtime` **cannot see the person it just created** — every policy
   restricts it to its own row. Verification goes through `public.team_roster()`,
   which is how the product reads the roster. An admin can create a member and
   still cannot read anyone's raw canonical rows.
3. `has_table_privilege('app_owner','identity."user"','INSERT')` **fails for
   `app_runtime`** with `permission denied for schema identity`, because resolving
   the table *name* needs `USAGE`. That is a stronger statement of the isolation
   than the ACL check would have been, and it is now asserted from the principal
   it matters for; the ACL itself is checked from `app_owner` in the clean room.

## A defect the tests found in my own code

`pruneSessionsIfDue` tracked "last swept" as `0`, so the first sweep was due only
once `now` exceeded the interval — meaning a fresh instance would silently skip
its first sweep. Real wall-clock time hides this completely, since `Date.now()` is
always far past any interval; it took a test with an injected clock to surface it.
Now `null` means "never", and the reason is written next to the declaration.

## Known limits

1. **`C5`, the Vercel smoke test, is NOT DONE, and I could not do it.** It is a
   named S17 exit criterion; my invariants forbid any Vercel deploy. The
   obligation therefore moves again rather than disappearing. What is now ready
   for it: the endpoint is a pure `(Request) => Promise<Response>` with no
   per-instance state, the function count is back to 12 so a deploy fits the
   Hobby cap, and the three environment variables it needs are documented below.
   **Deploying also needs the identity variables set in Vercel**, which is an
   owner action.
2. **Password *reset* cannot complete end to end.** There is no SMTP provider —
   the spec treats mail as an external gate — so the default sink discards the
   link and logs only that a reset was requested, with no token and no address.
   The candidate's reset routes are wired and forwarded; delivery is not. What
   *does* work is `password.change`, added after the owner pointed out the
   consequence: without it, an initial passphrase handed over out of band would
   have been permanent, because the only other route to a new password needs the
   email that does not exist.
3. **The live adapter leg is read-only, so sign-in is not proved against Neon.**
   Minting an account on the live project would leave rows in a production store
   outside the ledger, and G3 recorded that the spike wrote nothing there. What is
   proved live: the adapter connects as `identity_store`, the candidate's
   unqualified names resolve, pruning and revocation statements are valid against
   the real DDL, hashing is salted and the passphrase does not survive, and the
   store is **still empty afterwards** — asserted, not promised. The end-to-end
   claim rests on S16's clean room and step 005's.
4. ~~**Step 005 is not applied.**~~ **Resolved 2026-08-04** — applied and
   verified; see "The apply, as performed". The live project is at `5/5` and
   `admin.invite` no longer returns 503. Worth keeping in view: the ledger row is
   permanent, so reversal would be a break-glass action leaving deliberate,
   visible drift.
5. **The transitional Supabase bearer path is still accepted**, by
   `/api/identity` and `/api/activity-daily`. It is no longer a mapping
   authority, but it is a second authenticator and S18 must delete it.
6. **`app_owner` can now INSERT into two identity tables.** Argued above and
   narrower than the brief's own proposal, but it is a real widening of what the
   backup principal can do, and it is asserted to be INSERT-only on exactly those
   two tables.
7. **The in-request pruning schedule is per instance**, so a fleet of cold starts
   sweeps more often than one warm instance, and an idle instance never sweeps.
8. **`session.cookieCache` stays disabled**, so every request pays a session read
   plus an actor resolution. S12 measured the actor confirmation at 196 ms of a
   525 ms request from a dev host; the candidate's session lookup is now ahead of
   it. Both are resolved once per request. Enabling the cache is a deliberate
   trade against F5 and needs its own decision.
9. **`team_members.email` still has no unique constraint** — carried forward from
   step 004's limit #4. Step 005's invite refuses a duplicate case-insensitively,
   but the older `admin_update_team_member` path could still create one.

## Environment variables S17 introduces

All server-only. None may ever be `VITE_`-prefixed; the config reader refuses a
`VITE_` name and refuses to resolve in a browser context.

| Name | What |
|---|---|
| `IDENTITY_STORE_DATABASE_URL` | the `identity_store` login, **direct/unpooled** endpoint |
| `IDENTITY_SESSION_SECRET` | cookie-signing secret, ≥32 chars, **not** a database credential and refused if equal to one |
| `IDENTITY_BASE_URL` | this deployment's own origin; decides the trusted origin **and** whether the cookie is `Secure` |

`useSecureCookies` is derived from `IDENTITY_BASE_URL`'s scheme, deliberately not
from `NODE_ENV`: F2 measured both halves of that trap, including that a `Secure`
cookie over plain HTTP is dropped by the browser and the next request is
anonymous.
