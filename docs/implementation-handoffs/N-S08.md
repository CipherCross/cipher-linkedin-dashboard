## Two design calls, decided with the owner before implementation

Both were flagged as genuinely open and were put to the owner rather than
chosen unilaterally.

**Ledger storage — hybrid.** A repo-side manifest declares the expected state; a
table inside the tenant database records the actual state. The table lives in its
own `app_ledger` schema rather than in `public`. Putting it in `public` would
have made it a 26th table and forced every S05/S06/S07 count — 25 business
tables, 27 RLS tables, 52 policies — to be re-baselined, so "business table"
would no longer mean business table. A repo-side file alone was rejected because
it cannot detect drift on a live database: nothing would record which steps a
given database actually received, so a skipped step, a wrong order or a repeated
apply would be unverifiable against a real target.

**Re-apply semantics — idempotent skip, hard-reject on mismatch.** A step already
recorded with a matching digest is skipped and the run exits 0. This is not
merely a convenience: the baseline SQL is plain `CREATE TABLE` with no
`IF NOT EXISTS`, so re-executing it would error, and the runner must skip rather
than re-run. It also keeps an interrupted provisioning run safely retryable,
which the resume-safe idempotency contract S24–S26 will build on. Every other
disagreement is a hard non-zero failure.

## Ledger contract

Declared in `postgres/tenant-baseline/v1/ledger.manifest.json`:

| Property | Value |
|---|---|
| Order | `001 → 002 → 003`, contiguous from 1 |
| Digests | SHA-256 pinned for all seven artifacts, including the bootstraps and the restore-window pair |
| Apply principal | `session_user = app_migration`, `current_user = app_owner`, superuser forbidden |
| Store | `app_ledger.applied_migration` + `app_ledger.role_bootstrap`, append-only |
| Role bootstrap | recorded as a dependency, with the seven required roles |
| Re-apply | idempotent skip |
| Down migrations | none, and none accepted |

`app_migration` is `NOINHERIT` and the ledger is granted to nobody but its owner,
so even reading it requires an explicit `SET ROLE app_owner`. Each step applies
in one transaction together with its ledger row, so a half-applied step can never
look applied. `UPDATE`, `DELETE` and `TRUNCATE` are refused by trigger: a ledger
that can be edited is not evidence.

The runner reaches PostgreSQL only through `$LEDGER_PSQL`, so no host, port,
connection string or credential exists anywhere in the repository.

### The restore window — a real finding, not a formality

A plain `pg_restore` of this baseline is **not** safe, and the failure is quiet.
Both halves were reproduced in the clean-room:

1. `ALTER FUNCTION public.ai_execute_sql(query text) OWNER TO app_ai_runner`
   fails outright with `permission denied for schema public`. PostgreSQL requires
   the incoming owner to hold `CREATE` on the schema, and `003` grants that,
   takes ownership and revokes it again inside one artifact — so a restored
   database legitimately has no such grant to inherit.
2. Worse, once the first problem is solved with a `CREATE` grant alone, the
   guard's `REVOKE ALL ... FROM PUBLIC` and `GRANT EXECUTE ... TO app_system`
   are executed by `app_owner`, which is a `NOINHERIT` member of the function's
   owner. PostgreSQL does not raise on a `GRANT` the caller cannot make — it
   emits a **warning** and does nothing. The guard therefore comes back at its
   default ACL: **executable by `PUBLIC`, with no `app_system` grant**, while
   `pg_restore --exit-on-error` reports success. Measured before the fix:
   `acl==X/app_ai_runner,app_ai_runner=X/app_ai_runner`.

The procedure is now two committed, digest-pinned files.
`restore_window_open.sql` grants `CREATE` on `public` to `app_ai_runner` and
makes `app_owner`'s membership in it temporarily inheriting.
`restore_window_close.sql` reverses both and then refuses to succeed unless the
window is shut, the guard is owned by `app_ai_runner`, `PUBLIC` cannot execute it
and `app_system` can. The harness additionally fails on **any** `pg_restore`
warning, and the reconciliation re-checks the same properties independently.

## Known limits

1. **The restore window is the sharp edge.** Its residual risk is operator
   procedure: someone who runs `pg_restore` outside the documented sequence still
   produces a database whose AI guard is executable by `PUBLIC`, and
   `--exit-on-error` will not tell them. S25 must encode this in the Neon adapter
   rather than leave it to a runbook. The harness's "any warning is a failure"
   rule should be carried into that adapter verbatim.
2. **Evidence is from PostgreSQL 17.10 in a container, not from Neon.** Neon
   hands out a different privileged bootstrap principal and may differ on
   trusted-extension installation and on granting `CREATE` on the database to a
   non-superuser. Nothing in the baseline, the ledger or the restore procedure
   uses a superuser or a provider role, but the first real apply must re-run both
   harnesses against a disposable project. That is the substance of G1.
3. **`pgcrypto` is installed by `app_owner`, not by a superuser.** It is a
   trusted extension, so this works with `CREATE` on the database, and it makes
   the extension owned by `app_owner` rather than by the bootstrap principal. The
   inventory records the owner, so a provider that installs it differently will
   surface as a diff rather than silently.
4. **Dump size says nothing about the cutover window.** ~236 kB is an empty schema
   plus fixtures, and a custom-format dump embeds run metadata so the exact byte
   count wobbles between identical runs. S27 owns the timed rehearsals against
   real volume.
5. **The ledger is authoritative only for databases the runner touched.** A
   database prepared by hand has no ledger rows and is reported as unprepared
   rather than as drifted. S24–S26 must make the runner the only apply path
   exposed through the operations core.
6. **The 10 second AI guard timeout still needs the caller**, unchanged from S07:
   S11's transaction wrapper and S15's AI handlers must issue
   `SET LOCAL statement_timeout` per transaction.
7. **Two test-only login roles** (`app_ai_client`, `app_readonly_client`) exist
   only so the harness can reach the `NOLOGIN` `app_system` and `app_readonly`
   principals from a real session. They are created identically in all three
   clusters so the inventory snapshots stay comparable, and they are not part of
   any portable artifact or of the production role contract.
8. **The inventory snapshot excludes what is legitimately volatile** — OIDs,
   sequence `last_value`, row data and ledger timestamps. Sequence values, row
   counts and ledger rows are reconciled separately, which is the only place they
   must match.
