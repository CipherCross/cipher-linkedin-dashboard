## The design calls

### 1. The browser sends lead ids; the server derives the object key

This is the slice's central decision and the one the forbidden-key tests exist to
pin.

The Supabase path hands every lead row a `photo_path` and lets the browser ask
Storage for a URL. That is safe *there* because the request carries the user's own
JWT and Storage applies RLS to it — the browser naming the object costs nothing,
because naming it is not what authorizes it.

On this path the credential is the server's and is scoped to a **bucket**. If the
browser named the object, the only thing between a signed-in member and any key in
the class would be string validation — and the failure would be quiet: `keys.ts`
would still refuse traversal and still refuse another tenant, so every test would
pass while the hole sat *inside* the tenant.

So `GET /api/activity-daily?op=leads.photoUrls&lead_ids=…` takes ids, a registered
read (`leads.photoObjects`) answers with the paths **RLS let this actor see**, and
`leadPhotoObjectKey` derives the key. A client cannot ask for an object it cannot
ask for a lead. Mutation S1 — sign the column's value directly instead of deriving
it — reddens five tests.

### 2. One request per page of avatars, not one per avatar

`MAX_PHOTO_BATCH = 100` and the browser coalesces. The Supabase path spends one
Storage call per avatar, which is a direct call to a purpose-built service; the
equivalent here would be one *serverless invocation* per avatar, each repeating the
~200 ms actor resolution S12 measured, on a plan with a concurrency cap.

The coalescing window is a **microtask, not a timer**: every avatar of one render
pass lands in the same tick, so a `setTimeout` would delay the first paint by its
own duration to buy nothing, and a test would have to wait on wall-clock time to
observe a batch. A lead arriving while a batch is in flight starts the next batch
rather than joining the current one, which is what stops a long scroll from growing
one unbounded request.

### 3. The endpoint's request validation lives in the service, not the handler

`parseLeadPhotoRequest` is a function over a `URL` rather than ten lines inside
`handle`, and the reason is coverage rather than tidiness: **nothing in the offline
suite can call that handler** — it resolves an actor against the database first — so
a rule written there is checked by `tsc` and the live suite and by nothing that runs
on every commit. A mutation to the batch cap inside the handler would have been
silent. As a function, every rule is a test (mutations S4, S5 redden).

### 4. The photo flag needs three conditions, and the middle one is a correctness rule

`deploymentPhotoPath` answers `neon` only when `NEON_PHOTOS_DEFAULT=neon` **and**
the read path is already `neon` **and** the storage configuration resolves.

The second condition is the subtle one. The browser asks for photos by `lead.id`,
and a lead id means different rows in the two providers — `N-B2.md` records that the
id spaces name different people. A dashboard reading Supabase leads while asking
Neon for their photos would render one person's face against another's name. It
would look like a caching bug and it would be a privacy incident. The rule is
enforced on **both** sides — the server refuses to report `neon`, and
`fetchDeploymentPaths` refuses to believe it — because the failure is silent and a
reload does not fix it.

The third exists so that setting the opt-in before the bucket exists degrades to
initials rather than to an endpoint that can only answer 503.

`photoPath` rides along on the existing `config.readPath` response rather than
taking an operation of its own: the browser needs both before it renders anything,
they are decided by the same deployment, and two lookups could disagree.

### 5. The content type is sniffed from magic bytes, never from the filename

`sync-agent/agent.py` writes every object as `<instance_id>/<slug>.jpg` while
uploading it with whatever `content-type` LinkedIn returned. So a `.jpg` in the old
bucket is routinely a PNG or a WebP, and a copy that derived the type from the
extension would relabel it — which is not cosmetic: `policy.ts` signs
`content-type` precisely because an object stored under an image key and served as
something else is a script delivery channel.

`sniffImageContentType` reads the first twelve bytes, and a file it cannot recognise
as JPEG, PNG or WebP is **refused rather than guessed at**. That is also what
catches the HTML error page that a scraper saved with a `.jpg` name — which the
fixture tree contains, because the real bucket will.

The committed fixtures are a real 1×1 PNG and a real 1×1 WebP, both named `.jpg`.
There is deliberately **no JPEG fixture**: `sips` cannot decode or write images in
this sandbox, so a JPEG could not be verified to be one, and the alternative was to
commit a header-only stub that claims to be an image no decoder accepts. JPEG magic
bytes are covered in memory instead. A fixture that lies is worse than a fixture
that is absent and named as absent.

### 6. The copy reads a directory, not Supabase Storage

The obvious shape is a source adapter that speaks Supabase Storage. Rejected:

* **It could be written here and never run.** This session may not copy production
  bytes or add a credential, so an unrun transport is exactly the code that turns
  out to be wrong during a freeze window.
* **The export is already a supported operation.** Supabase's CLI and `rclone` both
  mirror a bucket to a directory, and S27 wants the bytes on disk anyway: a
  provider-to-provider stream cannot be resumed without re-listing both ends and
  cannot be checksummed before the destination is written.
* **A directory is the widest source.** The same tool copies from a Supabase export,
  an S3 sync, or a laptop holding a partial recovery.

`ObjectSource` stays a port so a streaming adapter can be added by whoever can run
one. What the tool owns is the part nothing else does: the deterministic mapping,
the checksums and the refusals.

### 7. "Verified" means a checksum somebody else computed

The copy hashes each file and sends the hash as a **signed** `x-amz-checksum-sha256`
header; the store recomputes it over the body that arrived and refuses a mismatch. A
tool that hashed the bytes it read and then declared success would have proved only
that it can read a file.

Two consequences the report does not paper over:

* **`checksumUnverified` is its own status.** A destination that returns a size and
  no checksum cannot be *proved* identical, only shown to be the same length, so the
  verdict is `sizeOnly` — a weaker claim with its own name. Collapsing it into
  `matched` would let a reconciliation report green having compared integers.
  Whether R2 returns a stored SHA-256 at all is unproven (no bucket), which is
  exactly why this degradation path exists rather than being assumed away.
* **The `ETag` is never reported as a SHA-256.** For a single-part upload it is an
  MD5 and for a multipart one a hash of hashes; `base64ChecksumToHex` returns `null`
  for anything that is not 32 bytes.

### 8. A dry run is the mode this session can grade, and it is not a degraded one

`copyObjects({dryRun: true})` reads every source byte, derives every key, computes
every checksum and builds the manifest — it only skips the writes. The manifest a dry
run produces is the *same artifact* a real run produces, so count, byte total and
digest are gradeable with no bucket in existence, and the same manifest is what
reconciliation later compares against.

### 9. The manifest's determinism is a property of the *set*, not of the run

Entries are sorted by key; there is no timestamp, no provider name and no run id in
the canonical form; a duplicate key is refused rather than merged. A manifest built
from the source and one built from the destination are byte-identical when the copy
was faithful, which is what makes it evidence rather than a log.

It is tab-separated text, not JSON, for two reasons: `JSON.stringify`'s determinism
depends on insertion order, which is true until someone reorders a field; and
`git diff` over two text manifests is line-per-object, which is what somebody
comparing them at cutover actually wants.

The digest is **recomputed on parse, never read**, and the header's count and total
are checked against the entries — an edited artifact must not be able to describe a
set it does not hold.

### 10. `OBJECT_STORAGE_TENANT_ID` has no default

N-S19 known limit 4 left the tenant id sourceless. S20 has the first caller and so
must choose; the environment is right for as long as G0's "private bucket per
tenant" holds, because a deployment already names its tenant when it names its
bucket. A fallback such as `default` would be the value production silently ran on,
and moving off it later means rewriting every key in the bucket. When S21 gives the
schema a tenant id, this becomes the bootstrap value and the request path reads the
column.

### 11. No CLI, and the reason is mechanical

The tooling is a library, not a `bin`. Committing a CLI would need a toolchain this
project does not have: `node --experimental-strip-types` cannot run these modules,
because they import each other with `.js` specifiers that resolve to `.ts` files
under a bundler and to nothing under Node's own resolver. Adding `tsx` or a build
step for one script is a dependency decision this slice does not get to make on its
own. S26 owns the runner that will invoke `copyObjects` and `reconcileDestination`;
until then the tests are the only caller and that is stated rather than implied.

### The findings: two defects, three unreachable guards, five blind tests

**S3 — a `catch` that could not do what it said.** `signLeadPhotoUrls` wrapped only
the key derivation in its `try`, so the `instanceof ObjectKeyError` narrowing below
it could never be false — nothing else can throw there. Turning *every* error into a
refused row reddened nothing: the narrowing was decorative, and the property it was
meant to protect ("a provider outage is not a fact about one row") was unprotected,
because the outage happened outside the `try` entirely.

Fixed by moving the signing inside the `try`, which makes the distinction real: a
grammar refusal drops one row, a provider failure fails the request. That change
turned up a second question immediately — a provider bound to another tenant now
threw *inside* the try and would have been reported as "every path is malformed" —
so the provider/tenant agreement is asserted once, up front, as `copyObjects`
already did (S7).

**`isLeadPhotoSourcePath` was weaker than its name.** Found by a test rather than a
mutation, and worth recording because it is the same shape: the predicate checked
only that a path had two segments, so it answered `true` for
`notebook-1/%2e%2e%2falice.jpg` and for a path containing a NUL — both of which the
mapping refuses. A predicate weaker than the operation it screens for is worse than
none, because a caller uses it to decide something is safe. It now attempts the
mapping itself, so the two cannot disagree (L5 reddens).

**Three guards that could not fire.** Each deleted rather than kept-and-documented,
on `N-S19.md`'s reasoning — a guard that cannot fire is one nobody can maintain:

* a trim check on `photo_path`, unreachable because leading and trailing whitespace
  always lands inside the first or last segment and the segment grammar refuses it
  there;
* an `isSymbolicLink()` branch in the source walk, unreachable because the
  `isFile()` check below it already excludes links. Removing it made the *reachable*
  guard the load-bearing one, and O5 — widening that check to admit symlinks —
  reddens;
* `readPrefix` on the filesystem source, which had no caller at all. S19's own rule
  is that an unused surface is the wrong shape by default.

**Five tests that were passing for the wrong reason**, each fixed by a test that can
fail:

* **O3** — every traversal case is refused by a prefix comparison too. Only a
  *sibling directory whose name extends the root* (`/export` beside `/export-old`)
  separates `startsWith` from `relative`, and nothing created one.
* **C4** — the class policy's content-type half cannot fire (the sniffer returns
  exactly the allowed three), and its size half had no oversized fixture. Now it has
  one; the content-type half stays, because it is the direction that fails when a
  future class's lists drift apart.
* **C8** — the tenant guard threw either way, because the provider refused each key
  a moment later. The test now asserts the source was **never walked**, which is the
  actual claim.
* **B4** — the 503 case's fake response had an empty body, so ignoring the status
  code changed nothing. The test now serves a *valid-looking* body with a non-ok
  status.
* **F4/F5, R10, O6, L7** — combinations nothing exercised: a server reporting
  `photoPath: neon` under a Supabase read path; a failed flag lookup; an object
  uploaded through a signed URL (which must report *no* checksum); reading a
  directory as an object; a non-string `photo_path`.

**Two harness findings, both about the pass rather than the code.**

*A mutation can hang instead of failing.* Removing the listing walk's page ceiling
made the "never terminates" test loop in microtasks only, which starves the timer
queue, so Vitest's own test timeout never fired and the whole run blocked — for ten
minutes, until the pass was killed. A hang is not a red result. Fixed on both sides:
the test's endless provider now yields to the macrotask queue, and the harness caps
each run.

*A killed pass leaves a mutation behind.* The harness restores in a `finally`, which
a `SIGKILL` does not run, so two interrupted attempts left `copy.ts` mutated in the
working tree — and the next suite run was green *because the mutation was the one
being tested for*. Grep for `if (false)` and `// mutation` before trusting anything
after an interruption. Chunk the pass so it finishes: `npx` costs ~1 s per
invocation and 64 × 8 suites through `npx` exceeded the limit; invoking
`node node_modules/vitest/vitest.mjs` directly brought a full pass to about two
minutes.

## Known limits

1. **Nothing here has spoken to R2.** N-S19's largest limit is unchanged and is now
   also S20's: `putObject`, `listObjects` and the checksum-mode stat are graded
   against an injected `fetch` and the fake, so what is proved is the request this
   code builds and the response handling — not that R2 accepts either.
2. **Whether R2 returns a stored SHA-256 is unproven.** If it does not, every
   reconciliation verdict is `sizeOnly` rather than `verified`. The code degrades
   honestly instead of asserting; confirming it is one HEAD request once a bucket
   exists.
3. **The endpoint handler's own branches are not covered offline.** Request
   validation moved into the service to fix most of this (design call 3), but the op
   dispatch, the provider resolution, the 503, the `console.warn` and the response
   body are still reachable only through `handle`, which needs a database. A
   handler-level test needs the endpoint's dependencies to become injectable — a
   refactor with a wide blast radius that this slice did not take.
4. **The UI has never rendered a real photo on this path.** The rendering tests use
   jsdom and a mocked transport; no browser run happened, because there is no bucket
   to fetch bytes from. `N-BROWSER-RUN.md`'s harness is the way to close it once
   there is.
5. **`leads.photoUrls` is not in `READ_OPERATION_NAMES`.** It is dispatched beside
   the allowlist, like `config.readPath`, because it is not a paged read — so the
   client/server equality assertion in `dashboardReads.test.ts` does not cover it,
   and the two spellings of its name (endpoint and browser) are kept in sync by
