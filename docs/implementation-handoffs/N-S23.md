## Design calls

### 1. One credential per notebook, reused across the machine surfaces

`ingest_token` authenticates batch ingest, remote config, photo upload, the
post-sync notify trigger, and release lookup. This keeps revocation and expiry
semantics aligned and avoids putting a second secret in every `config.yaml`.
The credential still names exactly one instance and one tenant; it is not a
fleet-wide secret.

`notify_secret` is no longer emitted by the agent or accepted in its config.
`/api/notify-replies` keeps a server-side `NOTIFY_SECRET` POST compatibility
branch for pre-S23 agents during the dual period. Its cron GET remains guarded
by `CRON_SECRET` and is a separate principal.

### 2. Revocation and expiry gate every authenticated API

The shared `authenticateMachine` helper resolves the credential on every
request. Config then performs a second database statement, and photo/ingest
transactions are subject to the step 009 live policy again. A credential that is
revoked or expires is therefore denied rather than served a cached principal.

Release lookup follows the same request authentication. The returned download
URL is intentionally a short-lived 120-second bearer capability: revocation
prevents a new release URL, but cannot invalidate a URL already issued to the
notebook. Recovery after an accidental revoke is to issue/rotate a credential,
update that notebook's local token, and run the normal shadow rollout.

### 3. Photo upload uses both instance and provider isolation

The agent sends its source `photo_path`, such as
`notebook-1/alice.jpg`, in a header. The API requires the first segment to equal
the authenticated instance, validates the path grammar, and derives the final
tenant-prefixed key. The injected/runtime object provider is also checked for
the resolved tenant. Thus a handler bug that omitted either the source-instance
check or the provider check would still have a second isolation boundary.

No-avatar and permanent avatar failures use an authenticated `absent` operation
to stamp `photo_synced_at` in Neon. For an image, the API writes the new object
first, then records the application path and timestamp in the machine-scoped
database transaction. The old Supabase `lead-photos` upload remains in the
transition path; the agent marks the old candidate complete only after the new
authenticated upload succeeds.

### 4. Release artifacts are separate, signed, and read-only to the dashboard

The release store uses a separate bucket and key grammar:

```text
agent/current.json
agent/<version>/agent.py
agent/<version>/manifest.json
```

The manifest signs the fixed canonical payload
`lh2-agent-release/1`, version, SHA-256, byte size, and release timestamp with
Ed25519. The notebook keeps only the unpadded base64url public key. It rejects
bad signature, version/downgrade, size, hash, HTTPS URL, marker, or compile
checks, and replaces the current file atomically. Any release failure leaves the
current agent in place and cannot break the scheduled sync. A cryptography
wheel is declared in `requirements.txt`; an OpenSSL 3 fallback was smoke-tested
for notebooks before their virtualenv refresh.

`publish_release.py` is operator-side only. It writes immutable versioned bytes
and manifest first, then moves `current.json` last. The dashboard has no release
write method or signing key.

### 5. Remote config uses the authenticated path once a token exists

`fetch_remote_config` uses `agent.config` when the local machine token and
bootstrap `ingest_url` are available. An authenticated API failure does **not**
fall back to the legacy service-role PostgREST read, because that would make a
revoked credential continue receiving configuration. The old direct read remains
only for pre-S23 notebooks that have neither token nor authenticated API URL.
`ingest_token` and `release_public_key` remain local-only; `ingest_url` is a
non-secret remote-config key but must be bootstrapped locally before the first
authenticated config read.

### 6. One rollout flag remains the transport flag

`ingest_mode` still has only `off`, `shadow`, and `dual`. S23 does not add four
independent flags. Config, release, and notify become usable when their URL or
token is configured; the photo mirror uses the authenticated path when the
machine transport is active. The old Supabase write path remains until S27's
whole-system cutover decision.

## What changed

- Added `machineAuth.ts`, the shared token-to-actor resolver used by ingest,
  config, photos, release, and machine notify authentication.
- Added `machineOps.ts` for `agent.config`, `agent.photoUpload`, and
  `agent.release`, all folded into `/api/import?op=...` to stay within the
  Vercel Hobby function cap.
- Added `agent.instanceConfig`, `agent.stampLeadPhotoCheck`, and
  `agent.upsertLeadPhoto` to the machine registry. The config query deliberately
  has no caller-supplied instance filter; step 009 RLS supplies that scope.

  their existing admin guard and are dispatched separately.

  legacy shared-secret compatibility and CRON_SECRET GET behavior.
- Kept `ingest_token` forbidden in `pipeline.ts` remote config and made the
  release public key local-only as well.

  GETs, manifest/pointer parsing, and 120-second download URLs.
- Updated the object-storage contract documentation for the authenticated photo
  writer while keeping release artifacts outside the tenant-object contract.
- Added `sync-agent/publish_release.py` and changed `sync-agent/deploy.sh` to
  publish signed releases with operator write credentials. The deploy script was
  not run in S23.

### Sync agent

- Config fetch, notify, photo upload/check, and release self-update use the
  authenticated machine API when configured; no new agent path logs token data.

- Added `cryptography>=42.0`, release-public-key config, and S23 transport tests.

## Known limits

1. There is no live machine auth, config read, photo upload, release download,
   Slack notify, or revoke/expiry observation yet. The owner gate above must be
   opened and the deployed release must be tested before calling this complete
   operationally.
2. The second agent release bucket, its read/write credentials, and operator
   signing key are not provisioned by this session. `deploy.sh` will refuse to
   run without them.
3. Photo bytes are uploaded before the database path update. A database failure
   after a successful object write can leave an orphan object; the candidate is
   intentionally left pending so the next sync retries rather than declaring
   success.
4. A release URL already issued remains usable for its 120-second TTL after
   credential revocation. Revocation blocks new issuance, not an already-issued
   object-store bearer URL.
5. Pre-S23 notebooks without a local machine token still use the legacy config
   read and old notify compatibility path. Removing those paths belongs to the
   post-dual cutover, not S23.
6. The offline sync-agent tests run from the untracked agent virtualenv and are
   not CI-backed. `deploy.sh` runs them when that virtualenv exists and warns if
   it does not.
