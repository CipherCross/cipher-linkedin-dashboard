## Three design calls, decided and justified

The brief flagged these as genuinely open and allowed the session to decide.

### 1. Domain ownership — split by who performs the effect

Domain assignment is a hosting capability on the canonical port
(`assignDomain`), and `verifyDeployment` reports domain state. `DomainControlPlanePort`
stays a distinct port.

The split is not "hosting versus DNS" as products, but *which control plane
actually performs the effect*. Attaching a hostname to a deployment target is an
operation on the hosting provider — that is literally what today's
`bindProductionDomain(projectId, hostname)` does, despite living in a
DNS-named port. Zone ownership, record delegation and sender-domain verification
are operations on the DNS provider and stay there. Approach section 8 lists
"assign a domain" among hosting capabilities, and this reading satisfies it
without pretending the platform runs its own registrar.

Consequence for S10: `DomainControlPlanePort.inspect` remains the preflight
authority for the zone, while the *binding* moves from
`DomainControlPlanePort.bindProductionDomain` to
`HostingControlPlanePort.assignDomain`. S09 did not move the executor's call
site, because that is the concrete-runtime rewiring S10 owns.

### 2. Schedule canonicalisation — part of the pinned release manifest

Schedules are neither a catalog entry nor a free-form plan input. They are
pinned to a release:

- `ReleaseBuildRequest` carries `scheduleManifestDigest`;
- `ScheduleRegistrationRequest` carries a `releaseHandle`, and the fake refuses
  to register schedules against a release that was never built;
- `verifyDeployment` reports `schedules.manifestMatchesRelease`, which is false
  when the registered set belongs to a different release than the active one.

A schedule that calls `/api/briefing?kind=weekly` is meaningless without the
revision that serves that route, so binding the two is the only honest model. A
catalog entry would let the schedule set drift independently of the code; a bare
plan input would let an operator type an arbitrary recurrence into a plan.

This decides the open question about `frontend/vercel.json`: it becomes
**derived output** rather than the canonical source. `CANONICAL_TENANT_SCHEDULES`
in `ops/src/providers/hosting.ts` is now the canonical statement of the four
schedules; S10 must prove the manifest matches it. S09 did not touch
`frontend/vercel.json`, which remains the active deployment manifest and S10's
concern.

### 3. Rename versus alias — coexist, and S10 removes the old port

`HostingControlPlanePort` is introduced alongside `VercelControlPlanePort`,
which is marked `@deprecated` with a pointer to its replacement and to S10.

It is worth being precise: this is **not** a type alias. The two are different
contracts — the canonical port is capability-shaped, takes no project or team
ID, and adds two operations that do not exist today. A `type VercelControlPlanePort =
HostingControlPlanePort` would have been a lie that broke every caller.

Renaming in place would have meant rewriting `StrictVercelAdapter`,
`p4c-runtime.ts`, `p4c-sdk.ts` and four test files onto a contract whose
provider parity has not been demonstrated yet — which is exactly S10's diff,
written blind and without its evidence. The cost of coexistence is two names in
the tree for one session; the deprecation comment states who removes which.

## The canonical contract, capability by capability

`ops/src/providers/hosting.ts`. Handles (`HostingTargetHandle`,
`HostingReleaseHandle`, `HostingRolloutHandle`) are opaque strings issued by
whichever adapter is in use; the canonical layer never parses them.

| # | Capability | Port method(s) | What the canonical result carries |
|---|---|---|---|
| 1 | `tenant_deployment` | `createDeploymentTarget` | target handle, deterministic name, workspace class, runtime profile ID, ownership-marker digest, lifecycle, `adopted`, and the two safety invariants `automaticPromotionEnabled: false` / `isolatedPreviewsEnabled: false` |
| 2 | `environment_binding` | `bindEnvironment` | target handle, scope, and per value **name + value class + source kind only**, plus a `bindingDigest` computed over those descriptors — never a value, never a key-store label |
| 3 | `pinned_build` | `buildRelease` | release handle, 40-character `revisionId`, `revisionPinned: true`, build recipe ID, public value names, `scheduleManifestDigest`, `artifactDigest`, status |
| 4 | `domain_assignment` | `assignDomain` | target handle, hostname, `assigned`, `certificateReady`, certificate mode, ownership-marker digest |
| 5 | `schedule_registration` | `registerSchedules` | target handle, release handle, the registered schedules in canonical order, manifest digest |
| 6 | `release_rollout` | `promoteRelease`, `rollbackRelease` | rollout handle, `rolloutKind` (`promote`/`rollback`), active and previous release handles, monotonic `rolloutSequence`, `reasonCode` (null for a promotion) |
| 7 | `deployment_verification` | `verifyDeployment` | `status` plus four sub-reports: `runtime`, `schedules`, `domain`, `build`, and a `rollout` block |

`inspect` is an eighth, read-only method that keeps preflight working. It is
capability-shaped throughout — `rollbackSupported`, `scheduleCapacityAvailable`,
`serverValueBindingSupported`, `automaticPromotionCanBeDisabled` — never team
access or function counts.

`HOSTING_CAPABILITY_METHODS` maps every capability to its methods, and
`HOSTING_RESULT_SHAPES` pins the exact key set of every result. The suite
asserts both directions, so the map and the interface cannot drift apart.

### The two real gaps that are now closed

- **Schedule registration did not exist as a capability at all.** It now does,
  pinned to a release, with the four known schedules stated canonically.
- **There was no rollback.** `rollbackRelease` exists, is separately reachable,
  and is constrained: only to a release that was actually active, only from the
  release that is currently active, never to itself, and never on a target where
  nothing was promoted. The reverse hole is closed too — `promoteRelease`
  rejects a return to an already-superseded release and tells the caller it is a
  rollback. Without that check the effect cache would have silently replayed the
  original promotion, which is the kind of thing a fake gets wrong quietly.

### Verification report contents

`runtime` — reachability, active release handle, whether it matches the
expected one, passed and failed check IDs.
`schedules` — the registered set, expected IDs, missing IDs, unexpected IDs,
manifest digest, and whether the manifest belongs to the active release.
`domain` — hostname, assigned, certificate readiness, match against expected,
whether it serves the active release.
`build` — release handle, revision ID, `revisionPinned`, match against expected,
build recipe ID, artifact digest, public value names, schedule manifest digest.
`rollout` — kind, sequence, previous release handle.

There are no timestamps anywhere in the canonical results. Ordering is carried
by `rolloutSequence`, so results stay deterministic and digestible without a
clock.

### Canonical plan

`buildHostingCapabilityPlan()` emits a pure-JSON, snake_case plan with a
`target` / `release` / `environment` / `domain` / `schedules` block and eight
ordered steps covering deployment, env, build, domain, schedules, promote,
rollback and verify. Effect inputs are `inputs_ref` references to fields already
declared in the plan — no URL, payload, command or environment value is ever
embedded. The rollback step is `planned_only: true`: it declares the reversal the
approved plan authorises, so a rollback during an incident is something the owner
already approved rather than an improvisation. A revision that is not a full
40-character SHA is rejected with `invalid_plan`.

## Proof that canonical surfaces carry no Vercel IDs or SDK types

Asserted structurally, not by grep:

- **Value walk.** Every node of every canonical result and of the canonical plan
  is checked for vendor-shaped keys (`vercel`, `teamId`/`team_id`,
  `projectId`, `deploymentId`, `buildId`, `crons`, `functionRegion`, `aliases`,
  `edgeConfig`) and vendor-shaped values (`vercel`, `team_…`, `prj_…`, `dpl_…`,
  `vc_…`, `sbp_…`).
- **Prototype check.** Every object encountered must have `Object.prototype` or
  `Array.prototype`. An SDK type instance would not, and no grep can see this.
- **Pure-JSON check.** `JSON.parse(JSON.stringify(x))` must deep-strict-equal
  `x`, so nothing non-serialisable survives in a canonical result.
- **Import-specifier check.** Module specifiers are extracted from the source of
  `hosting.ts` and `hosting-fake.ts` and compared against an exact allowlist
  (`node:crypto`, `../core/canonical.js`, `../core/errors.js`, `./interfaces.js`,
  `./fakes.js`, `./hosting.js`). Anything else fails the test.
- **Single importer.** The same specifier extraction over every `.ts` file in
  `ops/src` and `ops/test` finds exactly one importer of `@vercel/sdk`:
  `src/providers/p4c-sdk.ts`. Asserted as an exact list, so a second importer
  fails rather than passing a threshold.

A caveat, stated rather than hidden: `ops/test/hosting.test.ts` contains the
literal string `"@vercel/sdk"`, because a test that asserts the SDK has one
importer has to name it. A naive repo-wide `grep` therefore reports two files.
This is the same reasoned exemption class S08 recorded for three of its files.
The import-specifier parse — which distinguishes a string constant from an
import — reports one.

### Secret handling

`bindEnvironment` returns names, value classes and source *kinds*. It does not
return values, and it does not return key-store labels either. The proof is not
a shape assertion alone: the fake genuinely resolves secret material into a
private vault (`resolvedSecretCount >= 3` is asserted, because a fake that never
held a secret proves nothing), and then three canaries are searched for in every
result of every method, in the verification report, in the canonical plan, and in
the error path of a failed binding — via `JSON.stringify` and via
`Redactor.assertSecretFree`. `ops/src/core/redaction.ts` was not modified and
therefore not weakened.

## Known limits

1. **The canonical port has no caller yet.** `OnboardingProviders` still has a
   `vercel` member and the executor still calls it. Wiring the hosting port into
   the bundle, the executor, `provider-preflight.ts` and `StrictVercelAdapter`
   is S10's work; doing it here would have been S10's diff without S10's parity
   evidence.
2. **Domain binding has two homes until S10.** `assignDomain` exists on the
   canonical port, but the executor's step 8 still calls
   `DomainControlPlanePort.bindProductionDomain`. Both are correct today; only
   one should survive S10.
3. **`frontend/vercel.json` and `CANONICAL_TENANT_SCHEDULES` are not yet checked
   against each other.** They agree today — verified by reading both — but
   nothing fails if they diverge. That assertion belongs to S10, which owns the
   manifest side.
4. **`HOSTING_RESULT_SHAPES` pins keys, not value semantics.** It will catch a
   Vercel adapter that returns a different field set; it will not catch one that
   returns a plausible but wrong `artifactDigest`. S10 needs behavioural parity
   cases on top of the shape contract.
5. **No JSON Schema for the hosting plan.** The canonical plan is a typed
   `JsonValue` with a pinned digest, not yet a Draft 2020-12 closed schema
   alongside `onboarding-plan.v1`. S24 owns the provider-neutral schema and
   registry migration and should add it there rather than growing a second
   schema location now.
6. **`ProviderKind` still contains `"vercel"`**, and `resource_refs` rows still
   record a `vercel` provider kind. That is registry vocabulary, which S24 owns;
   S09 deliberately did not migrate persisted rows.
7. **The runtime profile and build recipe are opaque IDs.** `web-node22-1x` and
   `spa-plus-http-handlers-v1` are placeholders used by the tests; the real
   values must come from the approved catalogs, which S24 defines.
8. **S08's session-scope static assertion now fails for any ops-touching
   session**, as described above. It is a harness-ownership issue, not a defect
   in either session's artifacts.
